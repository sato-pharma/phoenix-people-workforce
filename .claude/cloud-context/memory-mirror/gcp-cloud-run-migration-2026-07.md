**BRIDGE ROOT-CAUSE INVESTIGATION (read-only, 2026-07-11):** Bridge = `createSupabaseAuthSession` → GoTrue `signInWithPassword` with synthetic email `phx-<hex loginId>@auth.phoenix.local` (src/lib/auth/supabase-identity.ts:343). Config fine (URL/keys set, 15s timeout). Prod `auth.users`: all 143 phoenix bridge users EXIST, are email-confirmed, have passwords — so NOT a provisioning gap. Exact failure is swallowed into `supabaseBridgeWarning` (unlogged) so the precise GoTrue error is unknown (likely password-sync mismatch on Cloud Run, see [[supabase-auth-bridge-password-resync]]). **BLAST RADIUS IS TINY:** the user Supabase session is consumed only via `getSupabaseRlsClientIfAvailable` (best-effort, null-safe) in exactly 2 files — `src/lib/payroll/expenses.ts` + `src/lib/payroll/service.ts` — both degrade gracefully. `getSupabaseRlsClient` (strict) has 0 feature call sites. That's why the app ran fine for weeks with the bridge down. **ROOT CAUSE FOUND + FIXED (2026-07-11):** The exact bridge error was `"Database error checking email"` (captured from `audit_logs.new_values->>'supabaseBridgeWarning'`, entity_type='auth_session' — NOT in `auth_login_attempts`, which only has id/login_id/ip/success/attempted_at). Cause = the classic Supabase/GoTrue NULL-token bug: **127 of 143** `phx-…@auth.phoenix.local` users had NULL `confirmation_token`/`recovery_token`/`email_change`/`email_change_token_new` (created via admin API); GoTrue's Go scanner can't read NULL (expects '') → signInWithPassword fails for those users. The app's auto-repair only resets password/email, never these token columns, so it never recovered them. **FIX APPLIED to prod auth.users: `set <token cols> = coalesce(col, '')` where NULL — 127 rows, verified NULLs now 0.** After this the bridge sign-in can proceed (password mismatches still handled by the existing repair path). Diagnostic technique: probe GoTrue directly — `curl $URL/auth/v1/token?grant_type=password` (anon key) and `/auth/v1/admin/users` (service key, status only) confirmed endpoint+keys healthy, isolating it to per-user data. **ACTUAL ROOT CAUSE (token NULL was incomplete): `auth.users.instance_id = NULL` on the same 127 users** (16 good users had `'00000000-0000-0000-0000-000000000000'`). GoTrue filters internal queries by instance_id, so NULL rows are invisible to id-lookup/listUsers/email-uniqueness → sign-in can't self-repair → "Database error checking email" / admin updateUserById returns "User not found". FIX APPLIED to prod: `update auth.users set instance_id='00000000-0000-0000-0000-000000000000' where instance_id is null and email like 'phx-%…'` (127 rows; verified 143/143 correct, 0 null). Confirmed via re-running admin updateUserById on a-1 → was 404 "User not found", now HTTP 200. Both fixes together (token NULLs→'' + instance_id NULL→default) fully repair the bridge. Diagnostic gold: `instance_id` distribution query + direct GoTrue probes (signInWithPassword anon, admin updateUserById service-role) reproduced/bisected the failure without a real login. **Strict gate stays OPT-IN (off) regardless — don't make login depend on the bridge.**
