Owner wants an AI **Payroll Copilot** in the payroll module (negotiated 2026-07-06, design LOCKED; Phase 1 design doc written, awaiting build approval).

**The flip:** existing payroll is *validate-an-uploaded-Excel* (human builds sheet → upload → `salary-import.ts` validates vs `employee_compensation` → stores `salary_batches`/`salary_records`). Copilot *builds* the sheet from modules instead, then feeds the SAME batch→approval→lock→payslip machinery. System is ~70% built already; missing 30% = the assemble+negotiate layer.

**Agreed behavior:** CEO says "Start [month] payroll" → seed every eligible employee from `employee_compensation` + `allowance-policy.ts` + pull already-approved feeders → anyone **100% green auto-filled silently**; **not-green → chat ask-queue**. 8 flag rules: pending/unapproved · joiner/leaver · attendance conflict · salary/role change · unpaid leave · off-system one-off · big-swing-vs-last-month · missing data. Off-system items (bonus/penalty/loan/advance) typed in chat. Recurring items remembered + counted down. Draft **editable until Lock**. Outputs: master + bank file + payslips + statutory summary. **CEO + Super Admin only.**

**4 decisions locked (all recommended options):** in-system run + xlsx export · auto-include-green/ask-exceptions · statutory = **new sibling module, NEVER touch locked `policy.ts`** · **phase it** · chat = deterministic questions + Claude parses free-text replies (LLM parses/explains only, **all money math deterministic**).

**Phases:** P1 = Copilot core (assemble + 8-flag engine + chat + materialize into existing `salary_batches`; statutory CARRIED as today, not computed). P2 = statutory engine (Egyptian tax brackets + insurance subject-wage + dependents/marital — all NEW schema). P3 = bank-transfer file + payslip PDFs + statutory summary. P4 = recurring memory + anomaly polish.

**Key codebase facts (from 2026-07-06 mapping):** `salary_batches` has 9-state workflow + working lock (`workflow.ts`, `service.ts`); `salary_records` has every needed column; `salary_flags` = existing flag concept; salary math (gross/net/two-part) lives in LOCKED `policy.ts` (`resolveFixedSalaryAmounts`, `calculatePayrollParts`) — call only. Feeder import RPCs already exist: `phx_import_deductions_governance_to_payroll`, `phx_import_approved_expenses_to_payroll`, `phx_create_salary_batch`. Tax+insurance today are UPLOADED amounts, not computed. Refactor needed: extract pure `validateSalaryRows` from `validateSalaryWorkbook` so Excel + Copilot share validation; add "deductions ≤ net" guard.

**Open inputs still needed:** LLM provider (reuse normalizer's OpenAI vs Claude) · per-group cutoff dates ("varies by group"; P1 defaults calendar month) · big_change threshold (default ±25%) · P2: tax brackets/rates + insurance base + dependents/marital.

**BUG (top priority fix):** `assemble.ts` currently treats Gross as fixed anchor and derives `baseSalary = gross − newSI − newTax` when insuranceWage is set — WRONG, backwards. Owner: "base basic and net cannot be changed from stored database... ever" (basicSalary=base×70% feeds the LOCKED incentive scheme, so drift there is dangerous). CORRECT model: Base + Net are ALWAYS carried unchanged from employee master, never touched by statutory math. SI unaffected (still from insuranceWage). Tax must be computed **on Base** (annual taxable = Base×12 − exemption) not on Gross — achieved by feeding `monthlyGross = baseSalary + SI.employee` into the existing `computeIncomeTax(monthlyGross, monthlyEmployeeSI, config)` so it cancels to Base×12 (no calculator signature change needed). **Gross becomes the only value allowed to move**: `Gross = Base + newSI + newTax` (forward calc, matches existing `calculateGrossSalary` in locked policy.ts) — Gross only feeds statutory-summary/bank reporting, never `calculatePayrollParts`/actual bank payout (confirmed that fn anchors on netSalary, not gross). Fixing this also kills the ~100 false-positive `salary_role_change` flags seen in the first live July run (they were 100% an artifact of this bug, not real base changes) — proof: legacy stored SI was a flat ~4,175/mo for anyone capped (=16,700×25%, an old formula), vs new correct 11%-capped SI (~1,837) — a real, confirmed-different number, not "basically the same."

**Universal proration principle (owner-confirmed, applies to ALL scenarios — joiner/leaver/unpaid-leave):** daily rate = **Base Salary ÷ actual calendar days in month** (real 28-31, never flat 30). ECOL/Fuel are "extras," NEVER part of the daily rate, ever. This also means the CURRENT Copilot `prorate` adjustment (assemble.ts ~155-161) is a bug today — it uses netSalary (Base+ECOL+Fuel) as the proration base, must change to Base-only.

**Unpaid leave (continuing employee):** deduction = `(Base÷days-in-month)×unpaid days`; only Base-derived pay reduced, ECOL/Fuel always paid in full untouched.

**Resignation Rule 1 (compute month total) — two branches by last-working-date vs day 25:**
- last working day ≤ 25th: `total = (Base÷calendar-days-in-month)×daysWorked, then ± deductions/additions`. NO ECOL, NO Fuel at all (not prorated-to-zero, literally excluded).
- last working day > 25th: `total = Base FULL (unprorated) + ECOL full + Fuel full, ± deductions/additions`. Owner's exact words: "no prorate and +additions -deductions".
- `daysWorked` = simple calendar-day count from the 1st to last-working-date, **then subtract** any unpaid-leave days that fall inside that span (owner: "simple calendar day count then deduction of unpaid n leaves").

**Resignation Rule 2 (Part1/Part2 clawback) — TWO-PART payment-mode employees ONLY** (one-part employees just get the Rule-1 total paid once, no clawback logic needed):
- Fixed Part1 = Basic Salary (Base×70%), same anchor as a normal month.
- Rule-1 total ≥ Basic Salary → Part1=Basic Salary (unchanged), Part2=Rule-1 total−Basic Salary.
- Rule-1 total < Basic Salary → Part1=the whole Rule-1 total, Part2=0 (paid once). Owner's example: fixed Part1=10,000; total=12,000→Part1=10,000/Part2=2,000; total=9,000→Part1=9,000/Part2=0.
- KEY INSIGHT: the EXISTING `calculatePayrollParts` two_parts branch (`firstPart = min(basicSalary, totalPayable−forcedSecondPart)`) may already implement this exactly for free, IF fed the correct Rule-1 total as netSalary input with forcedSecondPart=0 — likely no new split-logic code needed, just correct total-feeding. Confirm in the Plan-agent output before building.

**Joiner (new hire mid-month) ECOL/Fuel rule (different shape than resignation — a day-15 threshold with a HALF option, not zero):**
- hired ON or BEFORE day 15 → ECOL+Fuel in FULL.
- hired AFTER day 15 → ECOL+Fuel at HALF (ecol/2, fuel/2).
- Base still follows the universal day-rate proration (B) — owner hasn't explicitly re-confirmed this for joiners specifically but it follows from the general principle; flag as an assumption if building before an explicit re-confirm.
