SoS brick resolver (`src/lib/sales/normalizer/resolvers.ts`, `resolveBrick`). Precedence: (1) sheet direct brick id, (2) territory-text alias→brick-or-area, (3) area-text alias→area+region brick="", (4) customer-code→stored brick (fallback only). **Bug:** steps 2/3 `return` immediately with `brickId:""` (lines ~109 and ~114), so step 4 never runs even when the customer's exact brick sits inside that area → the vaguest signal (area) beat the most specific (customer→brick), violating the SMALLEST-BRICK rule [[sos-owner-standing-rules-from-session-369dd08d]]. `engine.ts:310`: a row is "resolved" only if `deriveHierarchy` succeeds, not merely if a brick is found.

**Fix = PR #1458** (merged `6f6b9779`, 471/471 tests, `tests/sos-resolve-brick-precedence.test.ts`): area hits are *remembered, not returned*; the customer's stored brick wins **when it's inside that area**; a **cross-area guard** keeps the sheet's area if the stored brick is in a *different* area (never silently move a sale across areas). Impact: PS 90.1%→~100%, ~3,282 rows/month stop landing at area level. Jan repaired (3,282 area-level→0), June re-checked clean (only DIRECT unmapped, by design).

**Diagnosis correction:** Jan/June area-level unmapped rows were caused by THIS resolver-precedence bug, NOT the pagination bug [[sos-unordered-pagination-lost-mappings]] (#1446). Both were real; the symptom was mis-attributed. Tell: 733/1,356 Jan failures were the SAME customers as June (58% overlap) — random paging loss would repeat on only ~2%.
