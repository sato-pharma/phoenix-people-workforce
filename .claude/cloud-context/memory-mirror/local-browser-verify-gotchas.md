Browser-verifying portal/admin pages locally (preview_* tools or `npm run dev` + dev-auth) in this repo:

**SAFETY — local `.env.local` targets PRODUCTION Supabase (`ozucdzovmcqvepbozvqf`).** A local dev server reads/writes **production** data. dev-auth (`GET /api/dev-auth?role=<Role>&hrId=<seat>&next=/employee-portals`, `NODE_ENV=development` only) just sets a session cookie — page LOADS are read-only and safe, but any **write action** (approve/return/reject, submit, save) hits prod. Keep verification strictly read-only: confirm rendering + honest empty states + expand client-only inputs (e.g. the inline reason textarea), but NEVER click Approve / Confirm / Submit against the prod-pointing dev server. See [[one-prod-deploy-per-task]], [[vercel-preview-env-and-branching]] (Vercel previews lack env and 500; prod is the only place with keys).

**Worktree dev server:** worktrees have NO `.env.local` (copy primary's in, it's gitignored; delete it after). preview_start reads `.claude/launch.json` in the PRIMARY cwd and flattens `runtimeExecutable+args` into a shell string SPLIT ON SPACES — a path with spaces (`F:\Phoenix Workforce\...`) breaks it ('C:\Program' error). 8.3 short names are disabled on F:. Workaround: a wrapper `.cmd` in the scratchpad (no-space path) that `cd /d "F:\Phoenix Workforce\_wt-..."`, `set PORT=3007`, `call npm run dev`. Next honors `PORT` env. Port 3000 is often held by a parallel session — use 3007.

**Headless preview can't finalize React streaming Suspense.** Pages using `<Suspense>` + async server components (e.g. MM cockpit's 4 streamed intel sections) render their content SERVER-side into `<div hidden>`/`<template>` parking spots, but the client reveal-swap script does NOT execute in the headless preview browser (dev-mode Fast-Refresh churn + headless). Symptom: skeletons (`.animate-pulse`) persist, duplicate section h2s, resolved h2 has `offsetParent===null` / height 0, `div[hidden]` count stays >0. This is NOT a bug — verify streamed sections by reading **`element.textContent`** of the hidden subtree, not visibility/geometry/screenshots. Also: preview viewport starts **0×0** — call `preview_resize` (e.g. 1280×900) before any geometry check (screenshots may still time out in this env; rely on DOM text, which the preview guidance prefers anyway).

**Root cause of the stuck-Suspense-reveal symptom, precisely:** this headless preview tab reports `document.hidden === true` / `visibilityState === "hidden"` even while it has focus (confirmed via `document.hasFocus()`); per spec this suppresses `requestAnimationFrame` (confirmed: a raw rAF call never fired in a 3.7s test, had to fall back to `setTimeout`). React's client-side commit that reveals a streamed Suspense boundary (the `$RC("B:n","S:n")` swap) appears to depend on this, so the boundary can get stuck showing `loading.tsx` forever on a given navigation. It is **inconsistent, not universal** — a subsequent fresh `window.location.href` navigation to the exact same URL sometimes resolves cleanly with no workaround needed, so don't assume every stuck page needs intervention; retry a plain navigation first. Monkey-patching `document.hidden`/`requestAnimationFrame` via `preview_eval` on an already-stuck page did NOT unstick it (the original native rAF call was already queued before the patch existed).

**Fastest ground-truth check when rendering looks wrong or is stuck:** don't trust the DOM/screenshot — run `fetch(url, {credentials:'include'}).then(r=>r.text())` from `preview_eval` and grep the raw RSC HTML for the string in question. This bypasses client rendering entirely and tells you definitively what the server actually produced, independent of whether the browser ever finishes painting it.

**Caveat found 2026-07-18 — this raw-fetch grep gives FALSE POSITIVES for conditionally-rendered UI driven by an always-passed prop.** Checking whether a role-gated tab (e.g. a "Company Plans" tab, prop `companyRequests: X | null` plus an always-passed label string like `companyRequestsTabLabel="Company Plans"`) was correctly ABSENT for a non-privileged role: `fetch().then(t => t.includes("Company Plans"))` returned `true` even though the tab was confirmed genuinely absent (via screenshot + `read_page` interactive-elements list showing only 3 tabs, no 4th button). Cause: the RSC/flight payload serializes ALL props passed to a "use client" component, including string props that are only conditionally rendered client-side (`Array.isArray(companyRequests) ? <Tab label={companyRequestsTabLabel}/> : null`) — the label string travels to the client regardless of whether the condition is true. **Fix:** for presence/absence of a conditionally-rendered element, trust `read_page` (interactive elements) or a screenshot — the actual post-hydration DOM/accessibility tree — not a raw-text/RSC-payload grep. Reserve the raw-fetch-grep trick for checking what data a component RECEIVED, not what it ultimately RENDERED.

**2026-07-25 — repeated rapid `navigate` calls on the SAME tab race each other and never let hydration complete; a real screenshot capture also failed outright this session ("Browser pane is not displayed").** While restyling Automated Payroll: called `navigate` → `read_page`/`read_network_requests` back-to-back many times, always landing on the stuck "Loading workspace" skeleton with NO `/api/automated-payroll/runs` fetch ever recorded. **2026-07-07 — dev-auth session can get force-logged-out mid-verification by `SessionSecurityGuard`'s heartbeat.** A dev-preview cookie (`/api/dev-auth?role=...`) is not a real `app_auth_users` session, so when a first-load route takes a while to compile in dev mode (webpack first-compiles ran 7–13s each in a fresh worktree dev server), the client's `POST /api/auth/heartbeat` fires during that window, the app treats the dev-preview cookie as invalid, and auto-triggers `POST /api/auth/logout` → redirect to `/login?reason=session-timeout` — even though nothing was wrong with the page under test. Symptom: a route you just verified loads fine suddenly bounces to `/login` on the next navigation, or a `navigate` immediately followed by a screenshot lands on a blank `chrome://newtab`-then-`/login`. **Fix:** re-hit `/api/dev-auth?role=...` immediately before navigating to the page you want to check, and prefer hitting already-compiled (warm) routes for the actual check — visit once to trigger compilation, then re-auth + revisit for the real verification pass, so the request completes before the heartbeat's timeout window.
