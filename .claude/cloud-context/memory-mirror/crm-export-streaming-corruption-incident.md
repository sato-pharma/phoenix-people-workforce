**What happened:** PR #1464 rebuilt `/admin/crm`'s export as a streaming, uncapped XLSX writer (fixed a real OOM). It passed typecheck/lint/474 tests/build, including a new regression test proving the streamed output was a valid, complete workbook — and was merged + deployed to production same-day. Within hours the owner hit "Excel cannot open the file... file format or file extension is not valid" on the full unfiltered Visits export (~110k rows). Reproduced it locally against real prod data: the export took **3-6 minutes real-world**, long enough that something in the network path (Cloud Run's default timeout, or another link) cut the connection before the workbook's closing zip bytes were written — a classic truncated-zip corruption. Root-caused via direct instrumentation (temporary `console.log` timers around each phase — pure reasoning about "which query is slow" burned real time and was WRONG twice before pulling actual numbers). Two compounding causes:
1. Minor: a per-export-page correlated DB query (checkins) that didn't hit its target index cleanly, multiplied across ~20-100+ pages.
2. **Dominant** (~80% of the time): `master-cell-format.ts`'s date formatters constructed a **brand-new `Intl.DateTimeFormat` object on every call** — 400k+ throwaway formatters for the full export. `Intl.*` constructor cost is a well-known but easy-to-miss JS perf trap; the fix (hoist to module-level singletons — formatters are stateless across `.format(date)` calls) was a 15-line, zero-risk change once found, but took real instrumentation to find because the DB-query hypothesis was much more "obvious" and wasted the first two fix attempts (page-size tuning made it *worse*, not better — 5.1min).

**Why the original regression test didn't catch it:** it synthesized 4,500 rows in-memory with an instant fake page generator — it proved the ExcelJS stream mechanics were correct (valid zip, uncapped, aborts cleanly on error), but never exercised realistic row counts (100k+) or a real network round-trip, so it could never have surfaced either the query-shape cost or the Intl-construction cost. Both are pure runtime-performance characteristics, not something a fast synthetic unit test can catch — they only show up under real data volume + real I/O latency.

**How to apply — general lesson, not just CRM-specific:**
- A regression test that proves *correctness* of a streaming/batch pipeline (valid output format, right row count, error handling) is necessary but NOT sufficient for anything performance-sensitive. Before calling a "make it scale" fix done, run it once against *real* data at *realistic* max volume, over a *real* network hop (not an in-process/synthetic generator) — this is the only way timeout-adjacent bugs surface. See [[local-browser-verify-gotchas]] for the parallel lesson about `preview_start` silently testing the wrong worktree — same root cause pattern (a check that looks like verification but isn't exercising the real path).
- When something in a per-row/per-page hot loop looks "obviously" DB-bound, verify with actual timers before optimizing — the instinct ("it's the network query") was wrong here twice in a row (page-size tuning made total time *worse*: 5.1min). A single well-placed `console.log(Date.now()-t0)` around each phase (fetch / derive / consumer-write) found the real 80%-cost culprit in one pass; guessing didn't.
- Audit any `formatCell`/`renderRow`-style function that runs per-row in an export/report path for `new Intl.DateTimeFormat(...)`, `new Intl.NumberFormat(...)`, or similar constructed-per-call objects — hoist to module-level singletons. This is a generic, reusable perf check for this codebase's other export builders (weekly, marketing ROI, payroll, etc. — not audited yet as a follow-up).
- Committing a fast-follow fix on a branch whose PR was already **squash-merged** produces a phantom GitHub "conflict" (squash breaks the commit-ancestry chain back to main, so git treats the whole branch as diverged from before the original PR even existed). Fix: don't try to reconcile it — create a fresh branch off current `origin/main`, `git cherry-pick` just the new commit onto it (this applies cleanly since main's content at those files is byte-identical to the fix commit's own parent), push that as a new PR, close the old one referencing the new one. Confirmed working exactly this way for PR #1472 → #1473.
