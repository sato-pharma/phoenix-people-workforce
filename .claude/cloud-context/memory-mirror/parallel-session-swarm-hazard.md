On 2026-06-15 the primary working tree (`F:\Phoenix Workforce\phoenix-workforce`) went from 2 → 7 git worktrees mid-session — a swarm of parallel agent sessions (db-data-model-hardening, weekly-sales, workflow-integrity-cas-registry→ceo-sod-matrix, a3-office-calendar-rule, etc.). One of them wrote vacation/resignation changes directly INTO the primary tree's working dir, then a concurrent git op **reverted my uncommitted `vacation/workflow.ts` edit** so my `git commit --only <paths>` silently dropped that file (committed 8 of 9). Caught it via diffstat (8≠9) + empty `git status`.

**Why:** several sessions editing the same checkout = lost-edit + index races (exactly the AGENTS.md § Parallel Session hazard).

**How to apply:** (1) Before staging, diff the staged file COUNT against what you edited — a mismatch means a concurrent revert. (2) For any side-task, work in an ISOLATED `git worktree add` off origin/main, junction `node_modules` from primary to run tests (`cmd /c rmdir` to unlink the junction before `git worktree remove` — never `Remove-Item` it). (3) Commit with explicit pathspec and PUSH immediately so origin holds the truth. (4) Don't touch other sessions' worktrees/branches — they're live. (5) >3 worktrees normally means cleanup (Rule 7) but NOT when they're active.
**2026-07-01 correction:** noticing sibling worktrees (other sessions working other rows of the same security-findings table, see [[sales-permission-security-audit-2026-07]]) and reporting their state (uncommitted files, unpushed commits) in a summary was unwanted — user said "focus on ur work only." Don't `git log`/`git status` into other sessions' worktrees or offer to finish/push their in-progress work unless explicitly asked; stay scoped to the task you were given, even when you stumble on evidence of parallel work while investigating something else (e.g. `git worktree list`).

**2026-07-02 escalation:** the reset can hit an already-ISOLATED `.claude/worktrees/<name>` session too, not just the primary tree — advice #2 above ("isolate in a worktree") is necessary but not sufficient. Mid-session on a resignation-scope-check fix, 3 tracked-file edits + 1 new untracked test file (all confirmed present via Read tool moments earlier) were silently wiped back to a clean `git status` matching HEAD exactly, with zero error and no destructive command run by me. `git worktree list` at the time showed a sibling worktree (`_wt-contract-resignation-hr-scope`) working the *same task* on a different path — plausibly related if worktrees here share underlying storage (junctions, per [[worktree-junction-breaks-turbopack]]), but not confirmed as root cause. **Refined practice:** after every `Edit`/`Write` in a multi-edit task, immediately verify via a Bash `grep`/`git diff --stat` on that same file (not just a re-Read, which can itself reflect the same stale/diverged view) — don't wait until all edits are done to check. If a reset is caught, redo the edits, re-verify each one immediately again, then commit right away — an uncommitted diff is the thing that gets lost; a commit is not.

**2026-07-16 bulk-cleanup addition:** ran a "remove the N merged worktrees" pass (branch/PR cleanup, not code edits) without first checking for other active sessions. Mid-run, discovered via changing `git worktree list` output that a concurrent session (relaxed-euclid, `.claude/worktrees/cloudrun-tag-cleanup`) was doing the *same* worktree-cleanup pass simultaneously — about half the target list was already gone by the time I got to it. Recovered fine (re-verified merged status via GitHub API before each force-delete, `git worktree prune` for entries whose `.git` link broke mid-race) and the owner confirmed the recovery was correct, but flagged the root cause: **check for other active sessions (SessionStart hook warning) and recent scratch-folder/worktree activity *before* starting any bulk destructive git pass (branch -D sweep, multi-worktree removal), not just before single-file edits.** Bulk cleanup ops are exactly the kind of action a second session is also likely to be doing unprompted (both sessions independently decided "these look stale, clean them up"), so the collision risk is structural, not incidental — proactively call it out to the user before starting, or at minimum re-check `git worktree list` between every few removals rather than only once upfront.

**2026-07-16 duplicate-cleanup incident:** ran a bulk merged-worktree cleanup (~26 `_wt-*` folders, `git worktree remove` + stray folder deletes) while a second, independent session ("Open PRs merge strategy") was doing the identical audit-and-delete pass at the same time — neither session checked for the other first. By the time the second session reached its list, roughly half the worktrees were already gone. End state was fine (both sessions independently verified merge status before deleting, and both correctly left actively-in-use worktrees alone), but the race left 4 worktrees with corrupted `.git` links (needed `git worktree prune` instead of a clean remove) and one orphaned skeleton folder with a locked `node_modules`. Reported cross-session by a third session (`cloudrun-tag-cleanup`) auditing the day's activity, at the owner's request. **Refined practice:** before starting a bulk destructive git pass (`worktree remove`, `branch -D`, mass folder deletes), check `git worktree list` for other recently-touched/active worktrees and consider asking the owner whether another session might be doing the same cleanup — don't assume you're the only one about to do it, even when the SessionStart-hook concurrent-session warning doesn't fire.
