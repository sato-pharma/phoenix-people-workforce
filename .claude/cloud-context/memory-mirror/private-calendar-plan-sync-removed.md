Private Calendar (`src/lib/private-calendar/logic.ts` + `service.ts`) must show ONLY these 5 sources: fingerprint attendance, CRM double visits, vacation (submitted + approved), national holidays, and excuses. The 6th source, "Plan" (synced live from the Weekly/Monthly Planning Calendar's `employee_plan_headers` + `employee_plan_items`), was fully removed on 2026-07-24 at the owner's explicit direction and must never be reintroduced without the owner reversing this decision.

**Why:** The owner found the mixed Plan+real-data display "totally wrong." Before removal, Plan items rendered as chips (e.g. "Office") on the same day-cell as real data, producing confusing combos: a stale/leftover "Office" plan chip sitting next to an already-approved Vacation chip, or an "Office" plan chip sitting next to a red "No Activity Recorded" exception (because desk-type plan activities like Office/Admin never self-proved attendance, while off-site types like Single Visit/Double Visit/Coaching/Travel/Remote silently did, via `planActivityCountsAsAttendance`). This blurred "what the employee planned" with "what actually happened," which is exactly what Private Calendar exists to keep separate from the Planning Calendar. Concrete example verified against production data for HR ID A-7 (Ahmed Mohamed Rabiee Fayk Elkawas, Training Manager, July 2026): real approved vacation + a leftover "Office" plan entry on the same day, and multiple days with only an "Office" plan entry (no punch/vacation/excuse) triggering "No Activity Recorded" right next to the still-rendered "Office" chip.

**What was removed:** `mapPlanRowToPrivateCalendarItem`, `planActivityLabel`, `deskPlanActivityTypes`/`planActivityCountsAsAttendance`, `planSlotLabel`, `PrivateCalendarPlanRow`, `privateCalendarPlanStatuses`, and `"plan"` from `PrivateCalendarSource`/`privateCalendarSources`/`privateCalendarSourceLabels` (logic.ts); `loadPlanItems`, `PlanHeaderRow`/`PlanItemRow`, and the plan branch of the field-visit FP-suppression loop (service.ts); the plan branch of `hasSelfProvingPresence` inside `derivePrivateCalendarExceptions` — self-proving attendance is now CRM Double Visit only. Also removed as a direct consequence: `filterPrivateCalendarActualItems` (its only job was dropping plan items, so it became a dead/type-invalid no-op once "plan" left the source union). The `actualOnly` flag/param was deliberately LEFT IN PLACE across the API route, export route, employee-portal page, and UI component — it is now a documented no-op (nothing left to filter) rather than removed, to keep the change scoped to the Plan sync itself.

**How to apply:** Do not add Plan/Planning-Calendar data back into `src/lib/private-calendar/` — neither as a new `PrivateCalendarSource`, nor as a signal feeding `isCovered`/self-proving-attendance/no-activity suppression — without the owner explicitly saying so in conversation. The "No Activity Recorded" exception must keep deriving only from attendance, vacation, excuse, holiday, and double_visit (CRM). Treat this like the other LOCKED domain policies in memory (e.g. [[sos-upload-block-vs-warn-policy]]) that require explicit owner reversal to change. See also [[private-calendar-hidden-from-portal-nav]] (a separate, still-valid decision: Private Calendar itself stays hidden from the employee portal nav for all roles).
