Owner asked (stepping away 30 min): confirm the new 668-brick/168-block master is "perfectly linked everywhere" and that today's work won't cause wrong findings in SOS sales. Clarification worth remembering: `source_of_sales_customer_map` was **never migrated** this session (only the brick/block MASTER tables were) — but that's exactly what creates the risk, since `customer_map.brick_id` is a plain TEXT column with **no FK** to `source_of_sales_bricks` (confirmed via information_schema). See [[reallocation-668-bricks-full-plan-live]] and [[customer-mapping-file-audit-and-fix]] for the reallocation itself.

**Quantified staleness (direct SQL against prod, all traced to the exact same known 103 retired brick_ids from today's plan — zero unexplained/mystery staleness):**
- `source_of_sales_customer_map`: 7,832 / 49,712 active rows (15.75%) reference a retired brick_id.
- `source_of_sales_fact_rollup`: 32,734 / 188,899 rows (10.43% of `effective_units`).
- `source_of_sales_customer_directory_rollup`: 30,422 / 178,441 rows (17.05%).
- `source_of_sales_import_rows`: 47,565 stale brick rows; only 36 rows / 2 distinct blocks stale on `block_code` (block-level barely affected).
- `sales_ops_fact_rows/rollup_by_brick/rollup_leaf`, `direct_order_pharmacies`, `ireports360_crm_region_brick_resolutions`: all 0 rows currently — no risk yet, but same no-FK pattern exists, worth re-checking once populated.
- **Red herring caught before reporting it:** a first pass showed `direct_value` 100% stale in fact_rollup — turned out to be `brick_id=''` (empty string) on all 148 `is_direct=true` rows, a pre-existing Direct-Order-Request data gap unrelated to today's reallocation. Always check for empty-string vs NULL vs genuinely-stale before alarming on a scary percentage.
- **Critical mitigating fact, verified twice (once for the 124-row action list, once for the full stale-brick set found live in customer_map):** zero of the 103 retired bricks changed `area_code`/`region_code` as part of the reallocation. So every stale row's stored `area_code`/`region_code` (denormalized on all these tables) is still geographically correct — **area/region-level rollups were never at risk**, only brick/block grain.

**Verdict on "wrong findings in SOS sales" (from a dedicated Explore-agent code audit, cited file:line throughout):** **No dashboard, report, or RPC currently produces a wrong revenue/units/customer-count total anywhere.** Root cause of the safety: `phx_exec_brick`/`phx_exec_customers`/`phx_closing_*`/`phx_customer_directory`/`phx_territory_area_pharmacies` all read from the two **snapshot rollup tables** (`source_of_sales_fact_rollup`, `source_of_sales_customer_directory_rollup`), populated once per import batch via `phx_refresh_sos_fact_rollup` (`monthly-distributor-import.ts:2738`, `normalizer/service.ts:415`, `normalizer/customer-map.ts:635`) — never a live join to the bricks/blocks master. `loadSalesReferenceData()`'s `active=true` filter is used ONLY to attach a display *label*; an orphaned brick just shows its raw code instead of a name (`sos-dashboard.ts:809`, `customer-directory.ts:224-227`, `monthly-closing-comparison.ts:589-591`) — cosmetic, not a wrong number.

**Two real issues found, not yet fixed (owner has not approved a fix, this is audit-only):**
1. **Territory Drilldown tree silently drops these customers.** `territory-tree-desktop.tsx:555,583,594` iterate only `skeleton.bricks` (active-only, from `territory/skeleton.ts:148-197`) to render lanes — a pharmacy keyed to a retired brick_id is in the payload map but rendered under NO node, no "unmapped/other" catch-all. The Area-header total/count (`:248-253`) still reduces over the FULL payload so it's numerically correct — meaning the header says e.g. "150 pharmacies ✓ reconciled" but the tree the user clicks through shows fewer, with no way to find the missing ones. Misleading UX, not a wrong number.
2. **Forward risk for the NEXT SOS import cycle.** `monthly-distributor-import.ts:1358-1370` auto-fills brick/area/region from `customer_map.brick_id` for raw/hybrid sheets, then looks it up in the active-only `brickById` map (`:1245`). For these 7,832 customers the lookup fails, auto-fill is skipped, and `:1498-1501` raises a **blocking** "Area/Brick/Region code is required" issue — lands in "Rows to Fix", not silently wrong, but WILL start blocking otherwise-normal imports for these specific customers starting with whichever period is uploaded next, until remapped. Coded sheets (brick already in-cell) only get a non-blocking warning.

**Diagnostic blind spot:** `reference-gaps.ts:38-54`'s `masterCodeSet` builds from `source_of_sales_bricks` WITHOUT an active filter — the existing "Reference Gaps" health-check tool will NOT flag any of these 103 codes as gaps. Don't trust that tool's "all clear" for this class of problem; it needs an `active=true` filter added to actually catch it.

**Fix EXECUTED same day, owner said "go-ahead" on return.** Two-part live UPDATE against `source_of_sales_customer_map` (project `ozucdzovmcqvepbozvqf`):
1. 102 old->new brick_id pairs, `brick_id` only (area/region confirmed unchanged for all 102) — single VALUES-joined UPDATE, fixed 7,745 rows in one statement.
2. B25-43's 87 rows (the "Split" case) needed brick_id **+ area_code + region_code** together — its OLD stored area (CA5/Cairo) was itself a pre-existing data bug: "مديرية التحرير" (Al-Tahrir governorate district, a real rural Beheira/Menoufia development zone) had been misfiled under Cairo, purely by name confusion with Cairo's Tahrir Square. Re-classified each of the 87 live rows fresh by customer_name+address text (same rule set as [[customer-mapping-file-audit-and-fix]]'s B25-43 split, re-run against the ACTUAL live rows, not the external file's): 79 resolved (59 Badr/B157-2, 20 Sadat/B69-11, 6 Kom Hamada/B156-2, 1 Buraijat/B156-3 roughly — all correctly landing in area AB4/region AB or area D13/region D1), 8 left untouched as genuine unresolved outliers.

**Result, independently verified:** 7,824 of 7,832 stale rows fixed (99.9%). Exactly 8 remain, all still `B25-43`/`CA5`/`CA`, confirmed via spot-check untouched. Total row count unchanged (49,712 — no rows created/lost). Audit log written by hand (`entity_id='bulk-brick-repoint-2026-07-24'`) since this bypassed the app's own `writeAuditLog` call sites, matching this session's established convention for hand-run SQL mutations.
