**Root causes (verified):**
1. **Cold start = ~18s Next.js first-request init, NOT image pull** (image pull off critical path; 450MB Chromium image had zero measured effect). The TCP startup probe passes at 1.5s → Cloud Run routes traffic to app-cold instances on every deploy rollout + scale-up. HTTP probe on /api/healthz = the top FREE fix (healthz first-call measured to pay the full 18s init, then /login 0.2s). Cloud Run constraint: timeoutSeconds ≤ periodSeconds.
2. **min-instances=1 actually costs ~$13/mo, NOT ~$68/mo** — service is request-billed (no cpu-throttling annotation); owner's =0 decision was made on ~5x-inflated numbers. But min=1 fixes few observed cold starts (they're rollouts/burst scale-ups; the 5-min cron keeps 1 instance warm anyway). Must be SERVICE-level (--service-min-instances) — 4 sha-tagged revisions exist.
3. **Region topology**: users Cairo (146ms→Iowa), app us-central1, DB Supabase eu-central-1 Frankfurt (110ms/query; auth chain alone = 3 sequential queries ≈ 330-500ms floor on EVERY authenticated request; admin shell ≈ 10-11 sequential RTs ≈ 1.1-1.2s before first byte). Target: europe-west3 (1.2ms to DB) via global ALB + serverless NEG (domain mapping UNSUPPORTED in ew3 + pre-GA; ALB ~$18-25/mo, Tier2 +<$10/mo). Fallback: europe-west1 (8.5ms, Tier1, mapping supported, but cert re-provision window). satopharma.com NS is already Cloudflare (TTL 300) → clean DNS flip; Cloudflare proxy/CDN only AFTER ALB (orange-cloud over ghs.googlehosted mapping breaks cert renewal). Blast radius: 8 code files hardcode us-central1/run.app (incl next.config.ts allowedOrigins baked at BUILD time), 2 Cloud Scheduler jobs pinned to regional URL (phoenix-process-notifications, phoenix-ireports360-sync — silent-death risk), staging uptime check, AR repo must be created in ew3.
4. **Builds**: cloudbuild.yaml has `--no-cache` (~100s wasted/build), default 2-vCPU machine. Validated in-project: BuildKit --cache-from deps tag → 240s vs 330s; + E2_HIGHCPU_8 → ~150-180s code-only builds. NEXT_PUBLIC build-args CANNOT bust deps cache (ARGs only in builder stage). Kaniko measured WORSE (405s) + archived project — don't use.
5. **Pipeline**: each merge = 2 full builds (staging rebuilds same SHA), serialized; merge→prod 10.5-11m quiet / 18m burst; merge→staging 19-22m. Build-once-deploy-twice is nearly free: only 2 Maps NEXT_PUBLIC vars are truly inlined in client code (3 files); Supabase URL/key read at RUNTIME server-side; staging already runs no-build-arg images (its Maps are already broken — key referrer allowlist excludes staging origin anyway). 429 root cause: gcloud polls ~60 GET/min vs quota 59 (global, project-wide) — fix = free quota bump to 300+ AND/OR `builds submit --async` + 30s polling.
6. **App code**: auth chain 3 queries→1 RPC (~300-360ms/request saved); sidebar getEffectiveSidebarModuleIds up to 7 sequential probes→1 IN-query (prod sidebar_module_assignments has 0 rows — worst case is universal); approvals pending-count endpoints (2.2s median!) materialize the FULL inbox (vacation fetches responder dataset TWICE) just to return counts — need dedicated count queries + batch 4 polls→1; poll is 30s via src/lib/nav-badge-store.ts.
7. **Region move will NOT fix**: pg_stat_statements shows multi-second pure-Postgres RPCs (phx_exec_sos_trend 2s mean/14.4s max, phx_exec_customers 692ms×2k calls, payroll_expenses ~2.2s) — separate DB optimization track needed.
8. Cron collision: notifications process (16-24s) + ireports sync both fire at :00 on the user-serving pool. Chromium+puppeteer now in serving container (1vCPU/1Gi/conc40) — OOM/saturation risk when PDF renders during traffic; check utilization before raising concurrency.
