Owner-reported 2026-07-19: an Anti Infective probationer's in-app notification (case created / manager feedback / pass / terminate) reached Pedia and CNS NSMs — and, on investigation, also District Managers and Medical Reps of unrelated lines.

**Root cause:** `notifyProbationWorkflow()` in `src/lib/probation/service.ts` called `createSystemNotification` with no explicit recipient → fell through to the generic cross-module governance resolver (`resolveNotificationRecipientsWithGovernance` / `src/lib/notifications/policy.ts`). The `"probation.*"` policy uses `recipientStrategy: ["direct_manager", "permission_based"]`; `permissionBasedRecipients()` matches ANY active user holding `probation:read` (granted broadly to nearly all `phoenixRoles`) whose org-scope overlaps the subject via line **OR department OR area OR team** (`hasOrgScope`, any-match OR logic). In this org **`employees.department_id = 1` covers 124 employees — the entire field-sales org across every product line**, not per-line. Net effect confirmed live: **up to 98 active users company-wide** could receive another line's probationer's HR-sensitive case-status update. Verified against the real case (AI-0004): 12+ leaked recipients (DMs/reps in line_id 1/2/3) shared ONLY department_id=1 with the subject.

**Fix (PR #1199, branch `codex/probation-workflow-notify-scope`, MERGED+LIVE 2026-07-19, commit 080e7dbe, prod deploy promoted+verified 200):** `notifyProbationWorkflow` now resolves an explicit, line-scoped recipient list itself — reusing `resolveFeedbackExtraRecipients`'s already-correct NSM management-chain walk (same file, already used for SLA reminders) instead of the department-based broad match — and sends one notification per resolved recipient (DM + NSM-via-chain-walk + Super Admin + CEO). An explicit `recipientHrId` never invokes the governance resolver (see `system.ts` `createSystemNotification`), so this bypasses the leak entirely for this call site. Re-verified against AI-0004: fix resolves exactly `{AI-0001 (real DM), B-157 (real NSM), CEO, Super Admin}`.

**Also confirmed probation-clean:** `feedback-service.ts` (feedback_submitted) and the day-30/60/90 `reminder_due` legacy reminder both already use explicit/metadata-driven recipients (never hit the governance `permission_based` path) — only `notifyProbationWorkflow`'s `workflow_updated` event was affected.

**NOT fixed (deliberately out of scope):** the underlying `permission_based`/department-scope logic in `policy.ts` is shared by 7+ other modules (payroll, contract_renewal, offers, recruitment, resignations, vacation, employee_import) — narrowing it generically needs its own audit; this PR only stops the probation leak at its call site. **Flag for a future audit**: any of those 7 modules could have the same department-scope leak if their subject/candidate department_ids are similarly broad.

Gate green: typecheck, 423 tests (added source-assertion regression guards), lint. Owner has separately paused all probation EMAIL (`email_notification_policies.probation.enabled=false`, 2026-07-19) — that does NOT cover in-app, which is what leaked; this PR is the actual fix for the in-app channel.

**CLEANUP DONE 2026-07-19 (owner-approved, executed):** the ACTUAL scope was far larger than "Pedia/CNS NSM" — `notification_events.employee_hr_id` is (by design, `system.ts:570/600`) set to that ROW's own single recipient, NOT the probation subject (the true subject lives only in `metadata->>'employeeHrId'`). So the governance fan-out created ONE SEPARATE `notification_events` row per resolved recipient, each independently visible in THAT PERSON's bell via the `employee_hr_id === viewer` match (see `recipients.ts` `canViewerSeeNotification`) — no `recipients`-array trick needed. Inventory (recursive-CTE recomputing the correct DM/NSM/CEO/Super-Admin/self set per true subject): **206 total `module=probation, event_type=workflow_updated` rows → only 14 legitimately scoped → 192 wrongly delivered to 97 distinct employees company-wide**, for just 2 real probationers (Abdelrahman Alaa, Soaf Atef — newly-provisioned med-rep cases, burst-fired 2026-07-19 ~18:43 UTC). Deleted the 192 wrong rows by id (FK CASCADE auto-cleaned `notification_deliveries`/`notification_user_states`/`notification_event_reads`; `attendance_weekly_digests` FK is SET NULL, unaffected). Verified post-delete: 14 remain, 0 wrong.

**CLOSED.** PR #1199 merged + deployed 2026-07-19 (commit 080e7dbe; smoke-tested, promoted to 100%, prod verified 200) — the fix is now live, so the NEXT probation case-status change resolves an explicit, correctly-scoped recipient list instead of fanning out company-wide. Combined with the historical-backlog cleanup above, both the ongoing leak and its prior damage are resolved.
