When a TA adds a Medical Rep, one employee could end up recorded filling **TWO** `position_vacancies`: their correct-area seat AND a resigned predecessor's DIFFERENT-area replacement vacancy. The org seat layer (`au`) then binds them to the wrong area while `employees.area_id` stays correct, so screens disagree (directory reads `area_id`; seat/vacancy/organogram read the seat) and the correct area vanishes from the open-vacancy-driven edit dropdown (`employee-management.tsx` ~757/785).

**ROOT CAUSE — corrected 2026-08-01 via live prod (the earlier attribution was WRONG).** The cross-area match does NOT come from `phx_autofill_replacement_vacancy_from_employee_insert` or app-code `closeVacancyOnHire` — BOTH already filter on area (verified against `pg_proc` + source; the autofill trigger correctly filled AI-0005's Cairo-West seat). The real culprit is **`phx_reconcile_stale_replacement_vacancies()`**, run by the *second* AFTER-INSERT trigger `phx_employee_insert_reconcile_stale_vacancies` on `public.employees`. It scans ALL open replacement vacancies on every insert and matched a "replacement" on **manager + line + job_title ONLY — no area, no single-seat check**. So any hire sharing a resigned person's manager/line/title got recorded as that person's replacement in another area. Trigger firing order matters: `autofill` (alphabetically first) fills the correct seat, then `reconcile` cross-fills the wrong one.

**Fix (authored 2026-08-01, migration `20260801150000_fix_reconcile_stale_vacancy_area_and_single_seat.sql`, regression test `tests/reconcile-stale-vacancy-area-guard.test.ts` — proven-fails, wired into run-tests.ts):** add two guards to the candidate select — (1) `a.area_id is not distinct from r.vacancy_area_id` (candidate must sit in the vacancy's own area); (2) single-seat `not exists` on `filled_by_hr_id` (status='filled' only, since 2 cancelled rows carry a stale filled_by). **APPLIED to staging + PROD 2026-08-01** (both via MCP `apply_migration`; verified live on prod: both guards present, `service_role` keeps EXECUTE, anon/authenticated revoked, still SECURITY DEFINER). PR [#1587](https://github.com/it-gawish-hr/phoenix-people-workforce/pull/1587) MERGED to main (squash 4a6e54d2). Do NOT "fix" `closeVacancyOnHire`/autofill — they are already correct and their one caller never passes `vacancy_id`. **Remediation of the 5 pre-existing mis-fills authored as guarded/idempotent data migration `20260801160000_reopen_cross_area_misfill_vacancies.sql`, PR [#1591](https://github.com/it-gawish-hr/phoenix-people-workforce/pull/1591) MERGED to main (squash 979e98ba); **APPLIED to prod 2026-08-01 + verified: 5 vacancies (173,248,263,297,299) reopened, 0 cross-area mis-fills remain, au seats unchanged (AI-0003 CA3, B-189 UE8). Backup `public.pv_bak_reopen_misfills_20260801` (drop once confirmed).** KEY: reopening only touches position_vacancies; the au/organogram is UNCHANGED (verified: the mis-fills never reached au for these three — AI-0003→CA3, B-189→UE8 already correct, AI-0006 no wrong seat, departed absent from au; and filled→open fires no seat trigger). Fixes only the vacancy report + hire dropdowns.**

**Pre-existing prod damage from the same area-blind reconciliation (still present, needs separate approved remediation):** cross-area filled vacancies — **248 & 297** (AI-0003 Soad Atef, area 1096, seats area 1094 "for B-174"), **263** (AI-0006 Mohamed Yasser, area 1103, seat 1104 "for B-97"), **173 & 299** (B-189 Ghada, area 1130, seats 1128 "for B-150"). Those replacement seats read filled when the real seats are vacant. Note the `au` seat layer shows each person in ≤1 live seat, so remediation is mostly reopening the phantom `position_vacancies` rows (unlike AI-0005 whose `au` seat also needed a transfer). Detect with: `note ilike '%stale-replacement-vacancy reconciliation%'` AND filler `area_id` != vacancy `area_id`.

**Incident 2026-08-01 (already fixed):** AI-0005 (Mahmoud Abdelreheem, area 1099 Cairo West) recorded filling vacancy 1 (Cairo West, correct — autofill) AND vacancy 300 (`VAC-AI0004-EQD`, Nasr City area 1095 — reconcile cross-fill). Fixed with `au.transfer_occupant('AI-0005','SEAT-AIF-REP-CA2','SEAT-AIF-REP-CA6', current_date, reason, 'AA')` then reopened `position_vacancies` id 300. Backups: `au.occ_bak_ai0005_20260801`, `public.pv_bak_ai0005_20260801` (drop once confirmed). Owner-approved.

**Org/seat model = schema `au` (source of truth):** `au.occupancy_history` (seat↔occupant, temporal; current span = `effective_to is null`; key cols `seat_id`, `occupant_hr_id`, `area_code`); `au.seats` (seat_id → area_code); `au.line_area_map.area_state` STORED ("occupied"/"vacant_will_hire"); views `au.v_org_tree`, `au_v_line_area_map`, `au_v_canonical_areas`. Primitives (SECURITY DEFINER — use these, never hand-edit): `au.hire_into_seat`, `au.resign_occupant`, `au.transfer_occupant`, `au.sync_area_state_for_seat`. `public.position_vacancies` DRIVES seats via AFTER-UPDATE trigger `trg_position_vacancies_hire_into_seat` (fires when a vacancy becomes filled) — which is why a bogus reconcile-fill propagated into the seat layer. Areas were re-seeded 2026-07-18 → duplicate names exist (old `line_id`-scoped `is_active=false` vs new canonical `line_id=null` codes like CA2/CA6); match by the active canonical id, not the name. See [[sos-areas-must-never-be-deleted-au-linkage]].

**Also learned:** a TA (not Super Admin) creating an employee writes **NO `audit_logs` row and provisions NO login account** — `upsertAccessUser` throws `assertSuperAdminUserAdminActor` for non-SuperAdmin and it's swallowed to `status:"failed"` (HTTP still 200). So a TA-added employee leaves almost no trace. See [[app-visibility-is-application-scoped-not-rls]].
