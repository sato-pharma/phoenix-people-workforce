Weekly Sales upload for distributor **PS / Overseas** (`/sales/weekly`) takes **two files** (POS sales matrix + POS stock matrix, both sheet "Data", header row 1, Mat. Code col3 / Mat. Desc col4). Region resolution differs by side (see `src/lib/sales/weekly/parser.ts` adaptPS + `branch-region-map.ts`):

- **STOCK matrix** locations (cols 7..N) are matched to a region **ONLY by column index** (`weekly_sales_branch_region_map.branch_column_index`, `source_file_type='stock'`). Name/`any` rows do NOT apply to stock. If a column has no stock-type column-index row → "PS stock column N is not mapped" → the WHOLE batch blocks. There is also a header-drift check (stored `branch_header_raw` must `normalizeKey`-match the uploaded header) so the Arabic header must be stored verbatim.
- **SALES matrix** outlets (cols 5..before "Total Qty") are matched **by name**: parser looks up `sales|<normalizeKey(header)>` then `any|<...>`. Headers carry a trailing `_ك` and `normalizeKey` KEEPS it, so the stored key must include `_ك`.

**Gotcha that caused the 2026-06-19 "system can't recognize it":** prod had **0** stock column-index rows (so all 79 stock locations blocked) and the 107 existing `sales` rows had **scrambled regions** (Tanta→AB, Mansoura→AB, Imbaba→OT…). Fix applied directly to prod (ref `ozucdzovmcqvepbozvqf`) via Supabase MCP: deleted PS `sales`+`stock` rows (kept `any`), inserted **79 stock** (col-index, regions derived from the correct Arabic `any` geography rows) + **113 sales** (correct regions). Region codes: AB=Alex-BHR, CA=Cairo, GZ=Giza, D1=Delta (1), D2=Delta (2), UE=Upper Egypt, OT=Others. created_by/updated_by stamped `system:ps-fix`.

Generator + the two ready-to-import templates were built from the user's 13-Jun POS files; Arabic was passed to SQL as base64 via `convert_from(decode(...,'base64'),'utf8')` to avoid transcription corruption. If a future PS week adds a NEW outlet/location, it must be mapped (sales=by name, stock=by column index) or it blocks. Any prior PS weeks uploaded under the old scrambled map have wrong regional totals and should be re-uploaded. **PERMANENT FIX SHIPPED 2026-06-19 (PR [#343](https://github.com/Phoenix-HR/phoenix-people-workforce/pull/343), squash-merge `f24dc486` to main → prod):** `resolveRegion` in `src/lib/sales/weekly/parser.ts` now resolves PS **stock by NAME** (`stock|<name>` → `any|<name>`) when a column-index mapping is absent — column-index still wins when present. This means PS stock no longer breaks when the mapping is rebuilt by name or the export reorders columns (the recurring "980 blocked rows" cause).
