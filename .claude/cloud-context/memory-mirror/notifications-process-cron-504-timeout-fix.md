**Incident (2026-07-15 21:30 UTC → 2026-07-16 18:11 UTC, ~20h):** `GET /api/notifications/process?limit=50` (Cloud Scheduler cron, every 5 min, drains the notification outbox — see [[gcp-cloud-run-migration-2026-07]] and CLAUDE.md's cron section) returned HTTP 504 at exactly ~300.000s (the Cloud Run request cap) on **every single invocation**, confirmed continuously for 6+ hours of Cloud Logging history before the fix. `runScheduledNotificationProcessing` (`src/lib/notifications/scheduled-processing.ts`) runs ~15 steps fully serially with no per-step or overall timeout budget; since each run exceeded the 5-minute scheduler interval, invocations also overlapped and compounded. Found while checking Cloud Logging for errors after an unrelated Cloud Run deploy (the tag-cleanup fix in [[cloud-run-stale-tag-cpu-quota-exhaustion]]) — the 504s predated that deploy by many hours and were unrelated to it.

**Root cause (now known precisely, thanks to the fix's own diagnostics):** two steps — `probation-feedback-sla` and `probation-milestones` — are the actual slow/hanging ones; they now hit a 30s soft cap and get skipped with `(timeout)` in the per-run log line. Everything else in the chain is fast (sub-3s). This is a **mitigation + diagnostic**, not a full root-cause fix for why those two specific steps hang — that's open follow-up work if wanted (look at `src/lib/probation/` query paths feeding those steps).

**Fix:** [PR #1067](https://github.com/Phoenix-HR/phoenix-people-workforce/pull/1067) (merged, `fix(notifications): bound cron steps with a timeout budget + overlap guard`), spawned via `spawn_task` into a separate session which investigated, fixed, tested, opened the PR, and merged it (user approved merge inside that session) — all in about 30 minutes end-to-end. Adds `src/lib/notifications/step-runner.ts`: per-step soft cap (30s, `Promise.race`) so a hung step yields its fallback instead of blocking the chain (steps are idempotent — safe to skip one for a run), plus a global 240s deadline so the handler always returns before the 300s Cloud Run cap. Also adds an overlap guard (module-level in-flight timestamp, self-healing) to stop compounding. Logs one line per run: `[cron:process] finished in …ms — reap-outbox=…ms … probation-feedback-sla=…ms(timeout) …` — check this in Cloud Logging for the current slow-step breakdown.

**Verified live in production:** post-deploy, the cron went from 504-at-300s-every-time to 200-in-~71s, confirmed across two different revisions (`phoenix-hr-00171-ven` from the normal CI/CD pipeline, and `phoenix-hr-00102-cnz` from an unrelated manual deploy that landed minutes later — see below). Both showed the same `(timeout)` pair and the same ~71s total.

**Unrelated observation from the same verification window:** while watching this, a second production revision (`phoenix-hr-00102-cnz`, no `sha-*` tag) took 100% traffic at 18:11:02 UTC via a bare local `gcloud run deploy` (creator `phoenixx.oag@gmail.com`, not the GitHub Actions WIF identity) — bypassing the deploy-then-smoke-test-then-promote pipeline entirely. Traced to a concurrent session ("google cloud health" title, worktree `strange-northcutt-768bd0`) doing legitimate IAM least-privilege hardening on the Cloud Run build service account, which appears to have run a real end-to-end deploy against **prod** (not staging) to verify its narrowed IAM permissions still allow builds. Confirmed no regression (that revision also had the fix), and the user said to leave that session alone — but it's a live example of prod being deployable outside the safety pipeline via local credentials; worth keeping in mind if a future prod incident doesn't match what the pipeline's own history would predict.

**How to apply:** if `/api/notifications/process` (or `/api/notifications/daily`, `/api/notifications/contract-renewals`, `/api/notifications/holiday-confirmation` — same `runScheduledNotificationProcessing` call, per the PR body) ever times out or is slow again, check the `[cron:process] finished in …ms` log line first — it names the exact slow step directly, no need to re-diagnose from scratch.

**Follow-up (2026-07-16, same day): root-caused and fixed the two named slow steps.** [PR #1068](https://github.com/Phoenix-HR/phoenix-people-workforce/pull/1068) (`perf(probation): parallelize per-recipient notification dispatch`). Root cause was O(tasks × recipients × channels) **serial** `for...await` dispatch in `feedback-sla-reminders.ts` (62 open feedback tasks in prod) and `probation-emails.ts` (14 active cases, ~5-8 stakeholders each) — `createSystemNotification` does several Supabase round-trips plus a synchronous inline email send per call, so the serial fan-out alone exceeded the 30s step cap even with nothing new to send (the idempotency check is itself a full round-trip per recipient per channel). Fix: `Promise.all` instead of serial loops in three places — safe because `claimDelivery`'s dedup is an atomic `upsert(..., onConflict)`, so concurrent claims can't race, and it matches the existing convention one step earlier in the same cron chain (`processDueProbationReminderEvents` in `src/lib/probation/service.ts` already fans out with plain `Promise.all`). Deliberately did NOT touch `src/lib/notifications/system.ts`'s synchronous-inline-email-send behavior — shared by every other notification call site, out of scope for this fix. Caught two source-text-pattern-matching regression-guard tests via `npm run test` before they'd have silently broken; preserved one's literal text, updated the other (R10 in `probation-audit-fixes-round2.test.ts`) since its loop construct necessarily changed shape. All validation (typecheck/lint/384 tests/pre-push gate) passed before commit+push+PR.
