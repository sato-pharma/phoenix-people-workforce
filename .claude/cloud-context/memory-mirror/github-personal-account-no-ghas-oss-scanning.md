Confirmed 2026-07-25 via API: `gh api users/Phoenix-HR` returns `type: "User"`, `plan.name: "pro"` -- not an Organization (`gh api orgs/Phoenix-HR` 404s). `repos/{owner}/{repo}` returns `security_and_analysis: null`, and `code-scanning/default-setup` 403s with a generic "enable in repository settings" message that looks like a toggle but isn't one.

**Why:** GitHub Advanced Security (native code scanning + secret scanning *alerts*) is only sold to GitHub Team/Enterprise Cloud accounts -- confirmed against GitHub's own docs, not just inference. It is not purchasable on an individual Pro account for a private repo at any price. Dependabot alerts are unaffected (free on every plan regardless of account type) -- that's why Dependabot alerts (see [[brace-expansion-audit-fix-trap]]) work fine while code-scanning/secret-scanning API calls 403/null.

**What exists instead:** `.github/workflows/security-scan.yml` (PR #1326) runs two free OSS scanners on every PR + push to main, both installed directly (CLI binaries/pip, not marketplace Actions, to avoid trusting a third party's own supply chain -- `gitleaks-action` itself went proprietary at v2.0.0, though still free for personal-account repos specifically):
- **gitleaks** (secrets), config at `.gitleaks.toml`. Extends the default ruleset; allowlists `node_modules/`/`.next/`/`dist/`/`pnpm-lock.yaml` by path, plus a line-targeted regex for this codebase's `key:`/`stepKey`/`templateKey` identifier-naming convention (e.g. `key: "p1_resignations"`, `templateKey: "probation_day30"`) which otherwise trips the generic-api-key rule on every occurrence -- verified false-positive by reading every flagged line; real secrets get an inline `# gitleaks:allow` instead (e.g. the documented-public Supabase anon key in `ci.yml`).
- **Semgrep** (SAST): `p/security-audit` + `p/owasp-top-ten` + `p/javascript` + `p/typescript` + `p/react`. First run found 4 genuinely-worth-fixing pre-existing issues (fixed in PR #1327: unpinned `getsentry/action-release@v3` in both deploy workflows, missing Dependabot `cooldown`) plus false positives on the `workflow_run`+checkout pwn-request pattern (safe here because the trigger is scoped to `branches: [main]` only -- it only ever checks out already-merged commits, never an arbitrary PR head) and on dynamic `urllib` usage in an internal GCP ops script with no untrusted input reaching the URL.

Both jobs were **originally non-blocking** (gitleaks `--exit-code 0`, semgrep without `--error`) -- findings showed in the job step summary + a downloadable SARIF artifact either way.
