**Incident (2026-07-18, RESOLVED same session):** owner reported "the filters in all modules are not working" on production (phoenix-hr.satopharma.com). Turned out to be a real, live, unrelated-to-any-current-branch production bug (not caused by the concurrent [[analytics-open-to-all-scoped-plan]] rebuild, which was still unmerged in a worktree).

**Symptom:** every filter dropdown across `/admin/analytics/*` (Source of Sales, Weekly Sales, Monthly Closing — Distributor, Line, Region, Area, Product, Product Family) opened fine and showed "No options." Meanwhile KPI cards, trend charts, and data tables on the SAME pages showed completely normal real data (e.g. a Line-contribution donut showing CNS/Pedia/Anti Infective with real values, while the Line filter dropdown right next to it said "No options").

**Root cause:** `loadAnalyticsDimensions()` (`src/lib/analytics/service.ts`) populates every filter dropdown via DIRECT table selects — `getSupabaseAdmin().schema("analytics").from("dim_areas"/"dim_distributors"/"dim_products"/"dim_products_all"/"dim_periods"/"dim_weeks")...` — against Supabase's REST API (PostgREST), not a raw SQL connection. The `analytics` Postgres schema was **never added to the Supabase project's Data API "Exposed schemas" setting** (Project Settings → API → Data API) — only `public, graphql_public` were exposed. PostgREST rejects any request against a non-exposed schema with `{"code":"PGRST106","message":"Invalid schema: analytics"}` — this happens BEFORE any grant/RLS check. supabase-js does NOT throw on this — it returns `{data: null, error: {...}}`, and the code does `(x.data ?? [])`, silently coercing to an empty array with no exception, no log, no visible failure. `Promise.all` never rejects, so the `.catch(() => demoAnalyticsDimensions())` fallback never triggers either — real KPI/chart data (which comes from a totally different path, see below) still renders fine, masking the bug.

**Why the KPIs/charts worked but dropdowns didn't:** `loadSosByPeriod`/`loadSosByLine` (and equivalents for Weekly/Monthly Closing) call `db.rpc("analytics_sos_by_period"/"analytics_sos_by_line", ...)` — Postgres **functions**, exposed via `/rest/v1/rpc/*` in the `public` schema (which WAS exposed). RPC calls don't require the schema containing the function's internal queries to itself be exposed — only the function's own schema (`public`) needs exposure. So the fact-data path worked while the dimension-lookup path (direct table access to `analytics.*`) was completely broken. This split — "the numbers are right but the option lists are empty" — is the diagnostic signature of this exact class of bug.

**Diagnosis method (fully remote, no login required):** reproduced the app's exact failing request directly against the REST API using the public `anon` key: `curl .../rest/v1/dim_areas?select=... -H "Accept-Profile: analytics"` → got the `PGRST106` error live, proving the schema-exposure gate was the cause (not RLS, not a code regression — grep confirmed no recent commit touched the filter/dimension code, and `information_schema.columns` confirmed the table schemas matched the app's query columns exactly, ruling out a migration-caused rename).

**Safety check before fixing:** confirmed via `information_schema.role_table_grants` that only `service_role` has SELECT on any `analytics.*` table — `anon`/`authenticated` have zero grants. So exposing the schema does NOT broaden what any end user or the public API can read; it only lets the app's own already-fully-trusted service-role backend reach data it was designed to reach. Verified this is genuinely a bug fix, not a security trade-off, before recommending the change.

**Fix:** Supabase Dashboard → Project Settings → API → Data API → "Exposed schemas" field, changed `public, graphql_public` → `public, graphql_public, analytics`. This is a **project-level platform setting**, not a database change — no MCP tool (`execute_sql`, `apply_migration`) can reach it; `ALTER ROLE authenticator SET pgrst.db_schemas = ...` did NOT appear to be how this particular project stores the setting (`pg_roles.rolconfig` for `authenticator` had no `pgrst.db_schemas` entry before the fix), so the SQL-role-config approach some self-hosted Supabase docs describe was not attempted — owner did the fix via the Dashboard UI directly. Owner-executed since it's a production API-surface change requiring explicit approval (per [[ai-tool-damage-prevention]] / AGENTS.md stop-conditions), and because I had no reliable tool to do it myself.

**Verified fixed:** re-ran the same curl reproduction after the owner's change — error changed from `PGRST106` (schema not exposed) to `42501` (permission denied for schema analytics) when tested with the `anon` key — confirms the schema is now reachable, and `anon` correctly still has no access (security boundary intact). Confirmed via `has_schema_privilege('service_role','analytics','USAGE')` = `true` (and `anon`/`authenticated` = `false`) that the app's actual runtime role has full access to read dimension tables. Did not re-test the live authenticated UI myself (no login credentials); asked owner to refresh and confirm dropdowns populate.

**How to apply:** if ANY new backend code queries a NEW schema directly via `getSupabaseAdmin()`/`getSupabaseUserClient()` (`.schema("some_schema").from(...)`) instead of via an RPC function, that schema MUST be added to this same "Exposed schemas" Dashboard setting or it will silently return empty results (not throw) in production — this is a schema-level gate checked before any grant/RLS, completely separate from `GRANT`/RLS-policy configuration. RPC-based access (`.rpc(...)`) does not have this requirement as long as the function itself lives in an exposed schema. If a future "X data is empty/missing but nothing errors" report surfaces for anything under `au.*` or other custom schemas used by the app, check this same setting first — `au` schema tables were also seen without confirmed REST exposure during this investigation and were NOT checked/fixed (out of scope — no reported symptom for `au.*` at the time).
