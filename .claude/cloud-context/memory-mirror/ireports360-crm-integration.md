The company's current field-force CRM is **iReports360** (vendor EGYDEV, branded "Everything & More 360"; SQL Server backend), used by medical reps ("agents") visiting doctors/clinics/hospitals ("contacts"). The owner wants to pull two datasets into Phoenix automatically: daily **visits** and GPS **check-ins** (the anti-"ghost visit" proof), then cross-match them so any visit with no nearby check-in is flagged.

The CRM developer provided a **read-only Reporting API v2.0** (cannot modify the CRM): `POST /api/ReportsApi/login` ({username,password}; admin agent Priv=3, IsWorking=1) → JWT valid 30 days; `GET /api/ReportsApi/visits?startDate&endDate`; `GET /api/ReportsApi/checkins?startDate&endDate` (Bearer). Visit types are signed ints (0 Regular, -1 Conference, -8 Campaign, -9 Training, -12 Traveling, etc.). Reference files live locally on the owner's machine (API HTML doc + Postman collection on `F:\`, a Visits xlsx export with 8 cols Date/Agent/Contact/Speciality/Region/AM-PM/Place/Products ≈6.4k rows, and 2 CRM screenshots) — they contain real PII (rep + doctor names, GPS coords); keep them OUT of git/email.

**Reachability — RESOLVED (verified live 2026-06-05):** production base URL is `https://hmaxhmax-001-site7.rtempurl.com` (SmarterASP.NET public hosting). End-to-end test from this machine succeeded: `POST /api/ReportsApi/login` → 30-day JWT; `GET /visits` and `GET /checkins` returned real data. So the API is **publicly reachable → Phoenix/Vercel can pull directly on a daily cron; NO local agent needed.**

Real-data notes for the build: stable keys are `agentID` + `contactID`; non-doctor visit types (e.g. Conference, visitType -1) return contactID 0 / null contactName / empty customerName; `visitDate` is date-only (midnight) while `saveDate` carries the real timestamp; check-in `address` is often empty but lat/lon are present (reverse-geocode ourselves).
