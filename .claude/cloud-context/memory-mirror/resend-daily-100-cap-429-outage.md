2026-07-13 incident: a manager (CEO Anwar Gaweesh / AA) got no email or Telegram for an NSM's weekly-plan submission (B-157 Sameh, plan 7a7dab6d). Investigation found the weekly-plan notification code fired correctly — this was NOT a code bug.

Root cause: **Resend free-plan daily cap = 100 emails/UTC-day.** `notification_outbox` showed exactly `sent_today_utc = 100`, last success 02:30 UTC, then EVERY subsequent email = `failed`, `last_error = "Resend rate limited (429)."` (label from [send-phoenix-email.ts](src/lib/email/send-phoenix-email.ts) line ~286, which only reads HTTP status, not the body — so per-second limit AND daily-quota both show as this one string). `sent_this_month` was only 171, so it's the DAILY cap, not monthly. An overnight **payslip "Payslip Available" batch (~00:26 UTC / module=payroll)** consumed most of the day's 100 allowance; the outstation digest (03:30) and the CEO's plan-review email (13:03) then 429'd.

Key diagnostic tell: a **lone** email hours after any burst still 429s → it's a sustained daily/monthly cap, not a transient per-second burst (which would recover on retry).

Misleading signal: `notification_deliveries` audit row shows the email channel as `status='sent'` even when the real send failed — because `safeSendNotificationEmail` hands off to the outbox and reports "queued". **The authoritative send status lives in `notification_outbox` (dedupe_key, status, provider_message_id, last_error), NOT `notification_deliveries`.** Always check `notification_outbox` to confirm a real send. `provider_message_id = null` on a "sent" delivery row = it never actually left.

Telegram side (secondary): the CEO's Telegram was not `connected` at submit time (`telegram_connections` for AA reconnected 28 min later at 13:31); other managers show status `pending` or "Bad Request: chat not found" (stale chat id). Telegram is broadly unreliable for the manager tier — most have no working connection, and default `notification_preferences.telegram_enabled` is false.

RESOLUTION (mostly already in place): the payslip-available EMAIL was disabled in code the SAME morning — PR #1038 / commit 328f4332 `fix(notifications): drop email channel for payslip-available notice`, merged to main **04:48 Cairo 2026-07-13**, ~22 min AFTER the offending batch fired at 04:26 Cairo (that's why the batch still emailed). It edits `src/lib/notifications/policy.ts`: `payroll.payslip_available` channels → `["in_app","telegram"]` (telegramGenericOnly, no salary figures), email dropped. So going forward a payroll approval no longer enqueues ~123 emails, and daily transactional volume fits under 100/day.
