**The problem it fixes** (see [[whatsapp-silence-alert-is-a-weekend-false-positive]] for how it was found): intake applied only the identity triple and parked the rest as a proposal, but the review UI is reachable ONLY from the two manual paths, so auto-intake candidates' proposals were never surfaced. 39 of 41 extractions unapplied; 1 of 9 WhatsApp candidates enriched.

**Design — new pure module `src/lib/recruitment/cv-auto-apply.ts`, applied in `cv-intake-service.ts` from the extraction already in hand (NO second AI call).** Four gates:
1. `confidence === "high"` only (the enum is just `high`|`low`).
2. Only schema `storage === "column"` fields — driven off the **existing `cv-field-schemas.ts` discriminator**, not a hardcoded list, so future positions participate automatically. `jsonb`/`position_specific_fields` deliberately out of scope.
3. **Never** the identity triple `fullName`/`email`/`phone` — `createCandidate` owns it, and intake sometimes MATCHES an existing candidate rather than creating one, so re-applying identity could repoint someone else's record and its dedupe norms.
4. **Gap-fill only, never overwrite** — a human edit or earlier extraction always wins.

Booleans: a recorded `false` is a deliberate answer, NOT a gap — `isBlankCandidateValue` treats only null/undefined/empty-string as blank. Declared field `type` is enforced against the runtime value so a malformed response can't put a string in a boolean column.

**🔴 KEY DECISION — `applied_fields` is deliberately NOT written by auto-apply.** `cv-extraction-analytics.ts` reads "`applied_fields is not null`" as *"Talent Acquisition reviewed and saved this"* and derives the AI's correction rate from the extracted-vs-applied diff. Writing auto-applied values there would fake a 0% correction rate and destroy the only extraction-quality signal that exists. **Do not "fix" this by populating applied_fields.** The cost is that you can't tell from the extraction row alone whether a value was auto-applied or typed; adding that needs a marker column + migration as its own change.

**🔴 Generalizable trap: a backfill run BEFORE the deploy leaves a seam.** Anything that arrives between "backfill finished" and "code serving traffic" is covered by neither. Always re-run the gap inventory *after* the deploy is confirmed live, not just before. The gap-count query (9 `count(*) filter (...)` columns over `ats_candidate_cv_extractions` joined to `ats_candidates`) passes the MCP classifier fine — it is the multi-CTE form that gets blocked.

Backfill specifics worth keeping:
- 39 extractions belong to only **24 distinct candidates**; **7 candidates have multiple extractions**. Rule used: newest-extraction-first, first non-null wins per field.
- **No `medicalRepEmployer`/`medicalRepExperienceFrom`/`medicalRepExperienceTo` values existed at all** (hasMedicalRepExperience is false everywhere), which dissolved the real hazard that `medical_rep_experience_from/to` are **`date`** columns while extraction values are free-text strings. If a future backfill DOES hit those, a naive `::date` cast will error or write garbage — guard it.
- The `UPDATE ... FROM` matched **18 rows but only 16 changed values**; the other 2 already had every field populated, so the CASE kept existing values and only `updated_at` was bumped. Harmless, but it means "rows returned" ≠ "rows meaningfully changed" — verify by field counts, not row count.
- **Rollback is exact** (gap-fill only ever wrote into NULL/blank columns, so re-nulling those pairs is a true inverse). Saved SQL: `…/scratchpad/cv-backfill-rollback-2026-07-31.sql` (session-scoped — re-derive if gone).
- `applied_fields` was NOT written by the backfill either, for the same analytics reason. It stays at 2 of 41.
- The Supabase MCP **classifier blocked a large multi-CTE verification SELECT** — split verification into small simple SELECTs instead.

**How to apply / gotchas:** `updateCandidate(id, input)` leaves omitted keys untouched and clears on explicit null, which is what makes gap-fill safe. Candidate camelCase keys map 1:1 to extraction keys. The apply step is best-effort + `logError` — the candidate and file already exist and are the point of the function, so enrichment must never fail an intake. `check:harden` green (exit 0, **484** test files — was 483; the +1 proves the new test file is wired into `run-tests.ts`, which is mandatory or it silently never runs).
