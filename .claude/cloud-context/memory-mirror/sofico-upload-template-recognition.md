The canonical **SOFICO (code SF)** monthly Source-of-Sales upload is the distributor's raw export with the Phoenix coded columns **appended** (`Product ID`, `Brick ID`, `Area ID`, `Region ID`, `Distrub ID`), which the user fills. File sample: `C:\Users\satoh\OneDrive\Desktop\Phoenix Sales Upload\sofico-April.xlsx` (Sheet1, 317 rows; Sheet2 is a manual territory→brick alias table).

**Before the fix `/sales/import` REJECTED it** (`unsupported_distributor_template`) because: (a) SOFICO had no dedicated coded template — only the generic `NORMALIZER_TEMPLATE` fallback, whose customer field is `Customer` not `CUSTOMERCODE`; (b) the date header is `BILLINGDATE`, absent from `INVOICE_DATE_HEADER_ALIASES`; and (c) the coded importer's `invoicePeriod` parsed `DD-MM-YYYY` per-row, misreading days 1–12 as months → "sheet contains multiple invoice months" block (the SOFICO date bug, same class the normalizer engine already fixed with `detectDayFirst`).

**Fix — all in `src/lib/sales/monthly-distributor-import.ts`:**
1. Added `SOFICO_SF_TEMPLATE` (key `sofico_sf`) reading the coded columns directly; customer = `CUSTOMERCODE`/`ORDERACCOUNT` + name `CUSTOMERNAME`/`CUSTOMERNAME0013`; qty = net `qty` (returns already signed, NOT `SOLDQTY` which zeroes returns); productName `ITEMNAME`; value RECOMPUTED (no `valueField`). Registered in `DISTRIBUTOR_SALES_TEMPLATES`.
2. Appended `"BILLINGDATE"` to `INVOICE_DATE_HEADER_ALIASES` (last, so canonical names still win).
3. Added `detectDateColumnDayFirst()` (column-level DD-MM vs MM-DD, mirrors the engine) + a `dayFirst` param on `invoicePeriod`, pre-scanned once per sheet and threaded into the parse loop. Backward-compatible: only changes ambiguous days when the column has a decisive day>12; benefits ALL coded distributors.

**Verified** via `validateDistributorSalesWorkbookBuffer` (the exact fn the upload route calls, no DB write): SF April → **validated**, period **2026-04**, **317/317 importable**, qty **1710**, value **EGP 99,531** (recomputed from factory price, so ~2% below SOFICO's own TOTALVALUE 101,973 — expected per the [[source-of-sales-rebuild-rules]] locked rule). Non-blocking warnings: Area ID codes (AB1/D24…) not in the area master ("kept for allocation"; area/region are derived from the brick master anyway); product names differ from master (official used); 1 brick `B121-12` not in the brick master.

**GOTCHA — coded sheets: the `Distrub ID` column value MUST equal the selected distributor code**, else a per-row `severity:"failure"` "Distributor code must be EP-R for the selected distributor" blocks EVERY row (not just an advisory). When the user's template hard-codes a distributor code, register the distributor under THAT exact code. A NEW distributor needs (a) a `source_of_sales_distributors` row (dropdown + import_rows FK), (b) its template/profile under the matching code, (c) optionally a `SYSTEM_DISTRIBUTORS` (import-service.ts) entry so a reset can't drop it — EP-R got all three.
