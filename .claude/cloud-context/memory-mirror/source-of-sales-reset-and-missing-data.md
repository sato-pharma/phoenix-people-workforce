On 2026-06-08 the user reset all Source-of-Sales data to re-upload clean, then asked for a "Missing Data" tab.

**The data layers (key mental model):** Source-of-Sales = (1) a FOUNDATION/reference layer — geography hierarchy **regions→areas→blocks→bricks**, plus **distributors** and the **products** catalog (with factory_price) and the customer→brick map; managed on **`/sales/database-mapping`** (each master has bulk Import + Export and one-at-a-time add; importer at `src/lib/sales/master-data/import-service.ts`, defs in `master-data/definitions.ts`, masters MASTER_ORDER regions→areas→blocks→bricks→products→distributors, codes are LOCCKED join keys, child rows blocked if parent code missing) — and (2) a TRANSACTION layer — the monthly distributor sheets → `source_of_sales_import_batches` + `_import_rows`, uploaded on **`/sales/import`** (`monthly-distributor-import.ts`), messy formats normalized first on **`/sales/normalizer`**. **Reconciliation is LIVE at read time**: dashboards/`phx_exec_*` RPCs left-join the masters and recompute value `qty*(1-discount)*coalesce(factory_price,0)`, so adding a missing master row makes held rows reconcile automatically — no re-upload/re-process.

**The wipe:** backed up all **17 `source_of_sales_*` tables = 106,109 rows** to `F:\Phoenix Workforce\source-of-sales-backup-20260608\` (one JSON/table + _manifest), then `TRUNCATE ... RESTART IDENTITY` all 17 (verified 0). No external module FKs into these tables. **Tooling (uncommitted in `scripts/`):** `backup-source-of-sales.mjs` (self-loads .env.local; **PostgREST caps reads at 1000 so it MUST page by PK** — single select silently truncates), `restore-source-of-sales.mjs` (dry-run default, `--commit` to write, FK parent→child order, **drops `id` on the 8 IDENTITY tables** so DB reassigns — region_aliases/area_aliases/product_aliases/territory_aliases/customer_map/import_rows/import_summaries/reference_issues; aborts if tables non-empty or backup files missing; prints rollback TRUNCATE on failure), `validate-source-of-sales.mjs` (read-only: geography orphans, missing factory_price, dup validated batches, and import_rows orphan product/distributor/geography with the Direct-channel guard). Scripts were adversarially reviewed (10-agent workflow, 5 confirmed findings) before use.

**Missing Data tab — SHIPPED (PR #117, merged to main `bb98562`, 2026-06-08):** new **`/sales/missing-data`** ("Missing Data" under Sales & Performance). Read-only: `loadSalesReferenceGaps()` in `src/lib/sales/reference-gaps.ts` diffs reference codes in validated import rows vs masters LIVE (Direct-channel rows excluded from geography), grouped Products/Bricks/Areas/Regions/Distributors with affected-row counts + distributors + periods, each with a "Fix in Database Mapping" link + Rescan (router.refresh). No migration, no API route (server page loads the service). Add the missing master → gap auto-clears + rows reconcile via the live joins. NOTE: the gap scan pages every validated import row (1000/page) so it's ~seconds and `maxDuration=60`; an RPC is the perf follow-up if import_rows grows large. The in-progress re-upload at ship time had **270 rows pointing at bricks missing from the master + 1 orphan area** — exactly what the tab surfaces.

Built in isolated worktree (parallel sessions + active upload churn the primary tree). Verified vs prod data via the validate script; prod render confirmed post-deploy. **GOTCHA — the reset/re-seed dropped the "Direct (Company)" distributor (fixed 2026-06-11).** The Upload Sales distributor dropdown is DB-driven (`listSalesImportDistributors` → `loadSalesReferenceData().distributors` ← `source_of_sales_distributors`). The reset's re-seed restored only the **10 normalizer distributors** (= RAW_DISTRIBUTOR_PROFILES in profiles.ts: CP/EG/EP/EP-S/IS/IS-S/MC/PS/RM/SF), so the **`Direct` / "Direct (Company)"** company-direct channel (a coded-template-only distributor, NOT a normalizer profile; its special rule = region-only + value taken straight from the sheet's `Value` column via `valueField`, `is_direct=true`) silently vanished from the dropdown. Its schema/functions survived the data TRUNCATE (`is_direct` col + `phx_monthly_closing_direct`/`phx_exec_distributor_product` all verified present) — only the reference row was gone. Fix: re-seed the one row (idempotent insert from 20260604101304_direct_channel.sql), applied to prod via MCP apply_migration (recorded version 20260610220700) + committed as `supabase/migrations/20260610220700_restore_direct_distributor.sql` (e91c86b). **Reset-proofing SHIPPED 2026-06-11** (commit `93f7ac9`): `import-service.ts` now has a `SYSTEM_DISTRIBUTORS` guard — after every **distributors-master import**, it idempotently upserts the code-defined channels (currently **Direct** + **EP-R / EPDA Bulk**) that aren't in the user's file. Gated to the distributor master, non-fatal, audited (`systemEnsured`). So a future reset + re-import auto-restores them; no manual step. To protect a NEW code-defined distributor, add it to `SYSTEM_DISTRIBUTORS`. Note: raw service-role upserts to prod are blocked by the auto-mode classifier — use the migration tool (apply_migration), not a manual patch.
