Field Workforce Compliance archived-month view has two report-only Excel export buttons (PR #883, branch `codex/fwc-godmode-export`, off origin/main 2026-07-06 — awaiting review/merge):
- **Export Month Sheet** → single Monthly Summary sheet.
- **God-Mode Book** → one workbook, sheet-per-tab: Summary, Monthly Summary, visual color-coded **Calendar Grid**, Review Queue, Recommendations, Final Actions, pivot-ready Day Data, Diagnostics, Legend.

Generators live in `src/lib/field-workforce-compliance/export.ts` (`generateFieldWorkforceSimpleSummaryWorkbook`, `generateFieldWorkforceGodModeWorkbook`). Route `GET /api/admin/field-workforce-compliance/archive/[id]/export?variant=summary|godmode` mirrors the recommendations-export route and MUST be registered in `src/lib/security/access-registry.ts` with `audit.classification: "export"` — the `access registry coverage` test fails any export/download route that isn't.

**ExcelJS hard limits (recurring gotcha for export requests):** it CANNOT author native charts, sparklines, or PivotTables. Deliver in-cell conditional-formatting heatmaps + a flat pivot-ready sheet instead. It DOES support: color fills, conditional formatting (colorScale/cellIs/containsText — note `CellIsOperators` only allows `equal|greaterThan|lessThan|between`, no `greaterThanOrEqual`), freeze panes, auto-filter, SUBTOTAL formulas, number formats, hyperlinks, defined names, print setup.

**CRITICAL — ExcelJS `writeBuffer()` succeeding does NOT mean Excel will open the file.** Two constructs produced well-formed, byte-valid XML that Excel still flagged as corrupt and silently stripped the sheet (Excel error: "Removed Part / XML error, Line 2 column 0"):
- `type: "dataBar"` conditional formatting — ExcelJS emits an invalid empty `<x14:id/>` inside an `<extLst>`. Avoid data bars entirely; use `colorScale` instead.
- Cell comments (`cell.note`) PLUS mid-data merged rows PLUS row `outlineLevel` grouping on the same sheet — some combination of ExcelJS's VML/comments + merge + outline emission corrupted the sheet even after comments alone were removed. Root cause not fully isolated; the fix was to strip all three (comments, mid-data merges, outlines) and rebuild using only constructs already proven to open cleanly elsewhere in the same workbook (fills, frozen panes, top-row-only merges, plain values) — sort-by-team instead of visually-grouped rows.
- **Neither `saxes` (ExcelJS's own strict XML parser) nor Python's `openpyxl` catch this** — both happily load the Excel-rejected file. There is no reliable local oracle; real Excel is the only ground truth. When debugging "Excel says repaired/corrupt" for an ExcelJS export, don't trust "it parses" as proof — get the user (or a real Excel/LibreOffice install) to open it, and isolate by testing which sheet-level features already opened clean elsewhere in the same workbook.
- Test hardening added: unzip the produced buffer and grep every `xl/worksheets/sheet*.xml` for `<x14:id/>` and for `comments*.xml`/`vmlDrawing` parts — catches the two known triggers without needing Excel, but is not exhaustive proof of Excel-validity.

**2026-09-04 — the same failure from the OTHER direction: NEVER re-serialize an existing workbook's `styles.xml`, even with a plain XML library.** Marking up the owner's own Anti-Infective August workbook, I added two fills by parsing `xl/styles.xml` with Python's ElementTree and writing it back. Excel opened it with an XML error and **no colour at all** — it had discarded the entire stylesheet and rebuilt a default one. Cause: the `<styleSheet>` root carries `mc:Ignorable="x14ac x16r2 xr"`, and those three prefixes appear **nowhere else in the document**, so ElementTree (like every namespace-aware serializer) emitted no `xmlns:x14ac`/`x16r2`/`xr` declarations for them — leaving `mc:Ignorable` naming undeclared prefixes, which is invalid, which makes Excel repair-by-discard. `openpyxl` and every local parser read the broken file fine; again, only real Excel sees it.
**The fix that works: treat the part as TEXT, never as a tree.** Splice `<fill>` elements in before `</fills>` (bumping the `count`), clone an existing `<xf>` **verbatim as a string** and edit only its opening tag's `fillId`/`applyFill`, then rewrite only the `s=` attribute on target `<c>` elements. Same rule as [[premium-closing-export-fills-the-xlsm-engine-never-rebuilds-it]] — the engine there is pivots and VBA, here it is the stylesheet, and both die the same way.
Two traps inside the text approach: a regex like `<xf\b.*?(?:/>|</xf>)` **truncates on a nested `<alignment/>`** and yields `mismatched tag`, so scan for element spans handling self-closing vs paired forms; and the only honest proof is a **byte comparison** — the part's header and everything after `</cellXfs>` must be byte-identical to the original, and every untouched sheet part byte-identical too.

**2026-09-05 — and the third failure, which was not a file defect at all: CONDITIONAL FORMATTING OUTRANKS A CELL FILL, and the colour was already his.** After the styles fix above, the owner still reported *"not coloured at all."* The file was perfect. Two things were wrong with the MARKUP:
- His Data tab carries **612 `uniqueValues` conditional-format rules covering 5,139 ranges over column A**, and CF wins over a direct cell fill in Excel. Every mark on that column was painted over.
- Their `dxf` fill is **`FFFFC7CE`** — the exact light red I had chosen. So even where the fill did survive, it was invisible against a sheet already full of that shade.
**Before choosing a highlight colour, read the target workbook's OWN palette** (`<fills>`, and every `<dxf>` behind its CF) and pick something absent from it — violet `FF7030A0` with a white bold font here. **Then check the sheet for `<conditionalFormatting>`**; where it exists, a fill alone cannot be trusted. The fix that works: renumber every existing `priority="N"` upward (they were 1–261,479 → +10,000), then splice your own `<conditionalFormatting sqref="…"><cfRule type="expression" dxfId="…" priority="1" stopIfTrue="1"><formula>TRUE()</formula></cfRule>` ahead of them, with a matching `<dxf>` appended to `<dxfs>` (dxf fills use `bgColor`, cell fills use `fgColor` — mixing them up paints nothing).
**A local oracle DOES exist for this class of bug, and it is LibreOffice.** `soffice --headless --convert-to xlsx` round-trips the file as an independent reader — it kept all 8 sheets, the violet on exactly the marked cells and the priority-1 override — and `--convert-to png` on a cut-down copy renders an actual picture of the marks. It cannot certify Excel-validity (see above), but it answers *"will anything visible come out the other end"*, which is the question two of these three failures turned on.
