### Applying what the MCP declines (moved from `database` on 2026-11-01)

- 🔴 **`supabase-production` DECLINES DESTRUCTIVE SQL ON PRODUCTION — a `drop function`, a `delete` — AND THE ACCOUNT CONNECTOR `mcp__b345e47e-…` IS NO LONGER A SECOND DOOR: IT NOW ANSWERS `-32600 You do not have permission to perform this action`.** Measured on the identical SQL twice: `{"status":"declined"}` on 2026-10-03 and again 2026-10-07, `{"success":true}` through the connector the owner allowed on 2026-10-05 (AGENTS.md §8 pre-authorizes both). 🔴 **The connector's half STOPPED being true by 2026-10-15**, measured on a `create or replace function` whose body merely CONTAINS `delete` and whose grants carry a `revoke` — production declined it, the connector refused it `-32600`, and **both doors were shut**. The route that worked is the repo's own explicit apply step, which is not an MCP at all and so passes through neither review: `node scripts/apply-sql-file.mjs <file.sql> production`, with `PHOENIX_POOLER_HOST=aws-1-eu-central-1.pooler.supabase.com` prefixed, because the env URL is the direct `db.<ref>` form and the script's default `aws-0` rewrite is the wrong region. 🔴 **It writes NOTHING to `supabase_migrations.schema_migrations`**, so a missing ledger row after it is CORRECT and not a discrepancy — `md5(pg_proc.prosrc)` against the file's own body is the authority, and `postgres_logs` is what attributes the single run. A decline is that server's own guardrail, **never the owner's decision and never evidence the change is forbidden** — and with both MCP doors shut, `scripts/apply-sql-file.mjs` is the STANDING route for that same production write, pre-authorized with no per-migration word since 2026-10-15 (AGENTS.md §8) (`a-declined-tool-call-is-not-proof-the-change-did-not-land`). 🔴 **And never leave "this is not applied" written in a migration header as the plan**: `20261003075838` said exactly that, nothing watched the sentence, and its two functions sat on production for four days as the only two `function_search_path_mutable` advisor findings. Account: `docs/agents-owner-rules.md`, "What the probe left behind, and why".

### The migration ledger (moved from `database` on 2026-11-01)

- 🔴 **A MISSING LEDGER ROW IS ANSWERED BY `md5(pg_proc.prosrc)` AGAINST THE FILE'S OWN BODY — NEVER BY WHETHER THE OBJECT EXISTS**, because almost every one is `create or replace` / `if not exists`, so an OLDER generation passes a catalog probe exactly as well as the current one (all 10 production misses "existed" on 2026-10-08; two were superseded and re-applying either would have REVERTED production). 🔴 **COMPARE THE FILE'S BODY IN FOUR SHAPES BEFORE CALLING A DIGEST MISMATCH DRIFT — as-is LF, as-is CRLF, comment-stripped LF, comment-stripped CRLF** — because some apply routes normalise the text they send: production's `prosrc` for `20261012132430`'s three deduction functions carries **CRLF**, and two of them arrived with every full-line `--` comment removed, so a raw md5 read as three drifted bodies when all three were byte-faithful (4,102 vs 4,191 chars, 2,462 vs 2,508 — a delta of a few dozen characters is the tell). A file annotated after it was applied is the other benign difference, and `phoenix_crm_seat_reference` was 669 bytes of pure comment away from its live body. 🔴 **And `length(prosrc)` differs from the file body's JS `.length` by one per emoji with the md5 IDENTICAL** — trust the digest. Ask the ledger what it really ran via `unnest(statements)`; a populated `statements` means `apply_migration`, null means the direct-connection path that writes no row at all. Accounts: `docs/migrations.md`, "The 15 October production sweep" (the four shapes, measured), and `docs/security/migration-ledger-reconciliation-2026-10-08.md` (the ten misses that established the digest rule).

- 🔴 **`-- SAFE:` IS MATCHED FILE-WIDE, SO IT GOES IN THE HEADER — NEVER INSIDE A FUNCTION BODY.** `check-migrations.mjs` warns per FILE when `DROP TABLE`/`TRUNCATE` appears with no `-- SAFE:` anywhere in it, and it matches the STATEMENT, not the schema: `drop table if exists pg_temp.<scratch>` inside a refresh function warns exactly like dropping a public table — **6 of the 7 files annotated 2026-10-13 were only that** (scratch tables `public.crm_contact_master_refresh` creates and drops in its own call), and the 7th dropped eight real `public` tables as its whole purpose. 🔴 **A comment inside the body changes `pg_proc.prosrc`** and breaks the `md5(prosrc)` correspondence the bullet above depends on — `20261012184500` records that md5 in its own header, read off production. 🔴 **The suppression is the whole file, for ever**: a destructive statement added later will not warn, survivable only because an applied migration never gains statements — a new change is a NEW file. Account: `docs/migrations.md`, "The `-- SAFE:` annotation, and where it goes".
- 🔴 **`scripts/apply-sql-file.mjs` IS THE STANDING ROUTE FOR A MIGRATION THE MCP REFUSES — NO PER-MIGRATION WORD** (owner, 2026-10-15: *"make apply-sql-file.mjs the standing route when the MCP refuses a migration"*), reversing the 2026-10-08 correction that demanded one and superseding `a-declined-supabase-mcp-apply-is-not-a-no`. Both pre-authorized doors refuse a `create or replace function` whose BODY merely CONTAINS a `delete` or a `drop table pg_temp.…` — the classifier reads it as the statement being run — so #5923 merged with its fix live only in code while production kept the old body. Production needs `PHOENIX_POOLER_HOST=aws-1-eu-central-1.pooler.supabase.com` (default aws-0 answers "Tenant or user not found"). It writes NO ledger row, so it ends in an evidenced `ACKNOWLEDGED_EXCEPTIONS` entry carrying `md5(pg_proc.prosrc)` against the file's own body — **never a ledger write**. §8's announcement condition is unchanged. Measured twice on 2026-10-15 — this file and `20261015164459_marketing_resubmit_audit_id_uses_stored_requester.sql`. Account: `docs/migrations.md`, "The standing route when the MCP refuses a migration".
- 🔴 **A SWEEP IS NOT THE DAILY CHECK — STAND THE 48h GRACE WINDOW DOWN, OR IT REPORTS CLEAN ABOUT A SET IT NEVER LOOKED AT.** `scripts/check-migrations-applied.ts` deliberately ignores anything merged inside `GRACE_WINDOW_MS`, because a PR's own migration is *supposed* to read unapplied at review time; so "sweep production for merged migrations never applied" (owner, 2026-10-15) is **`pnpm run check:migrations-swept`**, and the other database is **`check:migrations-swept-staging`** — `check-migrations-applied.ts --no-grace [--staging]`, added at his instruction the same evening so a sweep is one command instead of a scratchpad script. It takes its credentials from the process environment first and then from `.env.staging.rls.local`, `.env.production.rls.local`, `.env.local` (the `apply-sql-file.mjs` order), so it runs in a shell and not only in CI — **the environment always wins, or a file in the checkout could point a CI leg at the other project** — and it PRINTS which name came from which source, never the value. 🔴 **An unknown flag is REFUSED, before any connection opens** (`parseDriftCheckFlags`, pinned by `tests/migration-drift-check-flags.test.ts`), because a dropped flag answers the narrow question in the wide question's words, or points a run at the wrong database. On 15 Oct the window hid **four more production files** — as many as the check reported — including `20261014140000_marketing_resubmit_atomic.sql` and the three money migrations from #5918/#5921. 🔴 **And `ACKNOWLEDGED_EXCEPTIONS` is PROJECT-AGNOSTIC**: an entry justified on production silences the same file on staging, so check the other project's ledger before adding one. Account: `docs/migrations.md`, "The 15 October production sweep".

### The schema baseline (REC-041, 2026-11-13)

- 🔴 **AFTER APPLYING A MIGRATION TO PRODUCTION, REFRESH `supabase/schema/production.sql` WITH `node scripts/schema-baseline.mjs --write` AND COMMIT IT IN THE SAME PR — NEVER EDIT THE FILE BY HAND.** It is production's schema written down (a normalised schema-only pg_dump 18 of six schemas, 7,944 objects on 13 Nov 2026). The nightly leg dumps production again: drift a newer migration names is a warning, drift nothing names is red (a hand change, or a migration applied whose PR has not merged). A dump on the home network can hang on connect; the 240 s guard ends it, so re-run. Account: `docs/schema-baseline.md`.

- 🔴 **A ONE-OFF SQL SCRIPT GOES IN `supabase/scripts/`, NEVER THE ROOT OF `supabase/` — ONLY `seed.sql` STAYS THERE** (config.toml loads it). 62 hand-run scripts sat at the root reading like unapplied migrations until 13 Nov 2026 (F-ENG-016); `tests/supabase-folder-layout.test.ts` refuses a new one. A schema change is a migration. Edge function source lives in `supabase/functions/` (Deno: out of the app's typecheck and lint); `summarize-thread`, the only one production ran, was deleted from production on 13 Nov 2026 (owner) — production now runs none; never redeploy it without him. Account: `supabase/scripts/README.md`, `supabase/functions/README.md`.
