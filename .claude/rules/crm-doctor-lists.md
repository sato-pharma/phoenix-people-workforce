## Rules

- 🔴 **THE DOCTOR LIST FOLLOWS ITS OWN TEAM'S START IN ALL THREE PLACES THAT ASK — the apply function, the hourly refresh and the SERVICE — and they fail in OPPOSITE directions, so they move together.** `crm_cutover.cutover_date` is NULL on production and a team start never sets it. One rule: `doctorListOwnedByPhoenix` = his team's start OR a global date, mirroring `v_phoenix_owns`, asked per REP by every write and read path; **all four vendor assignment passes skip a started rep, the INSERT above all.** 🔴 **A FIFTH PASS THEN WRITES HIS PHOENIX LIST INTO `crm_contact_assignments` AS A DATED PERIOD, so the SCREENS read it** — vendor period closed at `counted_from - 1`, Phoenix period opened at `counted_from`, **nothing deleted**, and still NO `crm_contact_assignments_unified`. **A rep with NO Phoenix list KEEPS his vendor list** — the hand-over is driven by the LIST, never by the started set. It owns only `source = 'phoenix_crm'` rows and never touches a `source = 'phoenix'` one, and `crm_contact_list_change_apply` mirrors an approved removal or regrade into `phoenix_crm_customers` or the next hourly run undoes it. `20261004120000` + `20261007200000`, pinned by `tests/doctor-lists-follow-team-starts.test.ts` and `tests/doctor-lists-everywhere.test.ts`. Account: `docs/phoenix-crm-switchover-2026-10.md`, §1.

- 🔴 **THE HOURLY REFRESH'S FIFTH PASS HOLDS ONE ROW PER (REP, DOCTOR, LIST) — THE UNIQUE KEY UNDER `crm_contact_assignments` IS THE DOCTOR, NEVER THE CUSTOMER** (production, 2026-10-12). A rep who adds a doctor and re-adds him next day by reference leaves TWO `phoenix_crm_customers` rows; 5b inserted one key twice and the whole transaction rolled back every run for ~26 hours. A live row beats dropped, active beats pending, earliest start wins. 🔴 **Read a failing refresh by running it in a `DO` block that catches `unique_violation` and always re-raises** (`pg_exception_detail` names the key); `describeContactMasterError` now logs PostgREST's `details`. A call whose `timeoutMs` IS its deadline passes `maxRetries: 0` — the SDK retries with a fresh budget (signboard: 8 s became 16.4 s). Account: `docs/phoenix-crm-switchover-2026-10.md`, "A doctor added twice".

- 🔴 **A REP WITH NO IREPORTS360 ACCOUNT AT ALL GETS HIS PHOENIX LIST WITHOUT WAITING FOR HIS TEAM — THE DOOR IS `phoenix_crm_doctor_list_reps()`, NEVER THE VISITS DOOR** (owner, 2026-10-15: *"all those should be opened for them, the Phoenix now"*). Shahd Mohamed (`PD-0026`) had an EMPTY droplist with 112 built rows on her seat: no vendor pass can key on a rep with no `crm_id` and no `crm_username`, and the fifth pass covered started teams only — nine October hires, 1,223 rows, invisible on every list screen. `phoenix_crm_list_only_reps()` names a rep with a Phoenix list, no vendor identity, no open vendor row and an unstarted team, opening from the later of his seat day and his list's build day; the refresh, `crm_contact_list_change_apply` and the SERVICE ask the union. 🔴 **`phoenix_crm_started_team_reps()` is UNCHANGED, so every reader that decides whether somebody WORKED — the views, compliance and its deduction recommendation, the KPI boards — counts whom it counted before.** `20261015215500`, pinned by `tests/doctor-lists-follow-team-starts.test.ts` block 9. Account: `docs/phoenix-crm-switchover-2026-10.md`, "A rep with no vendor list".

- 🔴 **THE REFRESH READS `phoenix_crm_customers` IN EXACTLY ONE STATEMENT, AND BOTH PASSES READ THAT SNAPSHOT** (production, 2026-10-15). It is plpgsql at READ COMMITTED, where every statement takes a FRESH snapshot, and it read the customer table twice: the name-row pass that creates a Phoenix-born doctor's `crm_contacts` row, then the fifth pass that writes his assignment. A doctor a rep added BETWEEN them reached 5b without reaching the name pass, so the foreign key aborted the run for every rep in the company — eight `scheduled_job_stranded` alerts since 25 Sept. `pg_temp.crm_refresh_phoenix_customers` makes the fifth pass's set a subset of the name pass's BY CONSTRUCTION. 🔴 **Nothing on the add path writes `crm_contacts` — this function is its only writer.** `20261015132445`, pinned by `tests/crm-contact-master.test.ts` block 9. Account: `docs/phoenix-crm-switchover-2026-10.md`, "The customer table was read twice".

- 🔴 **THE CONTACT-MASTER REFRESH KEEPS ITS STARTED REPS IN TWO ARRAYS, SKIPS THE REGION-FROM-NAME SCAN WHEN NO CONTACT CAN USE IT, AND FEEDS ITS TWO `crm_contacts` UPSERTS ONLY ROWS THAT WOULD CHANGE — NEVER THE OLD SHAPES BACK.** A temp-table join on an `OR` of two conditions cannot be hashed (675,218 comparisons, 1.2 s), the unconditional scan read 209 MB of visits to serve 0 contacts, and `ON CONFLICT DO UPDATE` locks every conflicting row before its `WHERE` runs (11,900 WAL records to change 112 rows). Production 3,055 ms became 1,139 ms with identical counts and checksums of both tables. `20261016233000`, applied by `apply-sql-file.mjs` (no ledger row, so an evidenced `ACKNOWLEDGED_EXCEPTIONS` entry); rollback re-applies `20261015215500`. Pinned by `tests/crm-contact-master-refresh-speed.test.ts`. Account: `docs/crm-contact-master-refresh-speed.md`.

- 🔴 **THE COMPANY CONTACT ROSTER AND THE CONTACT SYNC'S REP-TO-CRM-ACCOUNT LOOKUP ARE EACH ONE STATEMENT — never back to OFFSET pages or chunked `.in()` reads** (production load audit, 2026-10-25). The roster's page walk was 28% of all database time (2,357 pages × 222 ms: an embed joins every row the OFFSET throws away); `phx_crm_contact_roster()` returns it in one hash join (~180 ms) and the roster is kept in the shared read cache, dropped by `bustListSummaries`. The sync's lookup scanned 198,723 plan entries per chunk and PostgREST cut each chunk at 1,000 rows; `phx_crm_agent_crm_ids_by_hr(text[])` answers from two index-only scans. Both return ONE jsonb value so no row cap applies, and both fall back to the old read on PGRST202. `20261025231000` + `20261025233000`, pinned by `tests/crm-reports-read-phoenix.test.ts` and `tests/crm-contact-lists.test.ts`.

- 🔴 **THE HOUSEKEEPING TIMER IS ONE PROCESS (the `crm-housekeeping` job lease) AND SKIPS THE CONTACT-MASTER REFRESH WHEN `crm_contact_master_inputs_stamp()` MATCHES ITS LAST SUCCESSFUL RUN** (owner, 2026-10-27, the afternoon stalls: every process ran its own timer, so the 1.1 s refresh ran about 8 times an hour). The stamp is read BEFORE the refresh. The daily activity pass, an unreadable stamp and a last refresh two hours old still refresh. 🔴 **A new input to the refresh goes into the stamp in the same PR**, or a change to it waits up to two hours. Pinned by `tests/crm-cutover.test.ts`. Account: `docs/crm-contact-master-refresh-speed.md`, "The 27 October pass".
