### The railway CLI, its two keys, and each service's source and trigger

- **`railway variables --stdin` stores a BOM** inside the value.
- **`railway ssh` JOINS argv and lands as ROOT.**
- 🔴 **`railway service source connect` is NOT environment-scoped — `--environment staging` REPOINTED PRODUCTION.** Never use it to preview; staging a branch needs a separate service.
- 🔴 **`railway service scale <region>=1` ADDS a region, it does not MOVE one** — it answered `EU West (1) · sfo (1) — 2 replicas`, i.e. two live copies of an MDM server writing one database (2026-09-28, Headwind EU cut-over). **Pass the old region `=0` in the SAME command**, and read the region map the call prints back before believing a move happened. A new service is created in `sfo`, so every one needs this explicitly (§3, "it must stay in Europe").
- **The `railway` CLI is linked to `production` — every variable command needs `-e staging`.** Setting a variable redeploys (unless `--skip-deploys`). 🔴 **THAT NAMES THE ENVIRONMENT; THE LINK ALSO NAMES A SERVICE, AND IT MOVES — so always pass `--service <name>`.** The primary was linked to `phoenix-headwind`, so `railway run` there injected the wrong service's variables and `CRON_SECRET` read as ABSENT, which looks like a half-rotated secret and sends a session hunting a rotation §2.3 forbids; on 2026-11-18 it was linked to the website. The CLI walks up the folders, so every worktree under `.claude/worktrees` inherits that PRODUCTION link (read 2026-11-18); `No linked project found` comes only from a folder outside the primary. Read `railway status` first. `railway-cli-is-linked-to-phoenix-headwind-not-the-app` Account: `docs/agents-production-hooks.md`.
- 🔴 **A FOLDER OUTSIDE THE REPO CAN BE LINKED TO ANOTHER PROJECT'S PRODUCTION — THE WINDOWS TEMP FOLDER WAS LINKED TO THE FUTURE TALENTS PORTAL'S `production`** (2026-11-18 Railway audit). The laptop's `AppData\Local\Temp` held a link to the `ftp-portal` project, and the session scratchpad lives under it, so a scratchpad `railway` command reached that portal, not Phoenix. The link was removed that day (`railway unlink`). From any folder outside the repo, read `railway status` first and pass `--project`, `--environment` and `--service` explicitly.
- ✅ **RESOLVED 2026-09-30 — the second undocumented project (`superb-smile`) is GONE, so the deploy gate IS now assertable: ONE project deploys this repo.** 🔴 **All SIX of its triggers read `checkSuites: false` since Wait for CI went off on 2026-10-20 — this line said `true` for production until then.** (Four until the code backup service, 3 Nov, and the robot service, 14 Nov; read live 2026-11-18.) Read the trigger, never a doc. Account: `docs/agents-production-hooks.md`.
- 🔴 **“TRACKS `main`” IS A SOURCE BRANCH *AND* A DEPLOYMENT TRIGGER — LOSE THE TRIGGER AND EVERY DEPLOY STOPS WHILE EVERY READING STILL SAYS `main`** (staging, 2026-10-23: no trigger at all, so nine days and ~180 merges never built it; newest deployment `REMOVED 14 Oct 11:48`). 🔴 **The edge answers `404 Application not found` — the ROUTER finding no service for that Host, which reads like a DELETED DOMAIN rather than a stale service** (a stale one answers 200 with an old `revision`); `railway status`, the dashboard, CI and the drift check were all green and correct, and there is no failed deploy to find because there was no deploy. **`scripts/check-railway-deploy-triggers.mjs`, the 4th leg of `secret-drift-check.yml`, now catches it from a DERIVED invariant — every GIT-sourced service instance must have a trigger in its OWN environment, an IMAGE instance is exempt** — and is read-only by assertion. Fix it by creating the trigger: never `railway redeploy` and never a source repoint, neither of which makes one. Account: `docs/deployment.md`, “Staging stopped deploying because its trigger was gone”.
- 🔴 **CHANGING THE REPO'S VISIBILITY DISCONNECTS RAILWAY'S GIT SOURCE FROM EVERY SERVICE, SILENTLY, AND CHANGING IT BACK RECONNECTS NOTHING** (27 Nov 2026: private at 08:18 Cairo; the last build was 07:47; PRs 820 and 821 merged and never deployed). Railway logged no error and no SKIPPED row; `railway status` showed `source.repo` null on all five git services, and `check-railway-deploy-triggers.mjs` read "no git-sourced service instance at all" (CANNOT TELL, not red). The owner then kept the repo PUBLIC. Recovery: the web and worker through `fallback-image.yml` deploy=restore (its `serviceConnect` must select a field, `{ id }`, or Railway refuses it), the robot, headwind and code backup by `railway service source connect` — denied to sessions in settings, so the owner runs it. Account: `docs/deployment.md`, "The five failure modes".
- 🔴 **THE TWO RAILWAY KEYS ARE TRIED APART, NEVER MERGED — `RAILWAY_TOKEN` IS A PROJECT KEY, `RAILWAY_API_TOKEN` A WORKSPACE KEY, AND A CLI STEP NEVER READS `RAILWAY_API_TOKEN || RAILWAY_TOKEN`** (2026-10-27). The merge meant only the first was ever tried, so each swap of one key broke a different job: 21–23 Oct the workspace key failed the secrets check, 23 Oct a production-only project key fixed it and broke the fallback rehearsal, 27 Oct the workspace key came back and broke the check again. `scripts/lib/railway-cli-credentials.mjs` tries each under its own name and prints each attempt's first error line, so a dead key is named; pinned by `tests/railway-cli-credentials.test.ts`. The trigger check (`scripts/check-railway-deploy-triggers.mjs`) refuses any source or trigger owner but `GITHUB_OWNER`, across `RAILWAY_PROJECT_ID` and `vars.RAILWAY_PROJECT_IDS`. Minting either key is the owner's. Account: `docs/ci-self-hosted-runner.md`, "The Railway key fix".
- **`railway environment edit --service-config` ANSWERS "No changes to apply" AND WRITES NOTHING** (14 Nov 2026, the robot service; every form tried). A healthcheck is GraphQL `serviceInstanceUpdate` and a rename is `serviceUpdate`, both through `railway api`; variables are `railway variable set --skip-deploys`, a domain is `railway domain -s <service>`, and the read-back is `railway environment config --environment production --json` (never print a value). From Git Bash, start `railway.exe` from node with an args array: MSYS rewrites `/api/readyz` into a Windows path and mangles `${{service.NAME}}`. Account: `docs/deployment.md`, "The robot service".
- **That deploy serves in MINUTES — confirm by listing DEPLOYMENTS**, never by probing the app, and never `railway redeploy` to make a variable "take".
- 🔴 **THE SECRETS SYNC ADDS AND CONFIRMS BUT NEVER REPLACES — A PRODUCTION VALUE THAT DIFFERS FROM GITHUB IS HELD, AND RELEASED ONLY BY NAME.** `scripts/sync-railway-production-secrets.mjs` lists production first and plans in `scripts/lib/secret-sync-plan.mjs`: absent is written, equal is left, different writes nothing, ends the run red (exit 3) and is named on Telegram. Release by hand: `gh workflow run sync-railway-production-secrets.yml -f overwrite=NAME,NAME`; a push passes no names. An empty or unreadable list stops the run and never reads as "production holds nothing". Never restore the unconditional write: on 13 Nov 2026 a push that only touched the script put a 4 Nov GitHub secret over the dispatch token set on Railway on 7 Nov and stranded two jobs for nine hours. A value changed on Railway still goes into the GitHub secret in the same turn.
