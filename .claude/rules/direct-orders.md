### Owner rules (moved from AGENTS.md §4)

- 🔒 **THE APPROVAL PANEL READS THE LIVE PHOTO'S OWN TERRITORY FIRST — THE PHOTO IS THE PRIMARY SOURCE OF TRUST, AND A DISAGREEMENT LEADS `geographyCheck.summary`** (owner, 2026-10-18; request 299304bf filed Menoufia 1, photo 0.7 km from منوف / Menoufia 2). `photoTerritory` is the nearest brick centre to the stamped pin (`resolveBrickForPoint`, the same centres the stamp uses); past `PHOTO_TERRITORY_TRUST_KM` (15) it is "not usable", never an accusation, and a brick map that did not load is `brick_map_unavailable`, said in words, never "No live evidence photo with GPS" (2026-10-19). The master (distributor code) check still runs beside it and never hides a photo mismatch. Pinned by `tests/direct-orders-hold-release.test.ts`. Account: `docs/agents-owner-rules.md`.

- 🔒 **THE DIRECT-ORDER MONTH GOLDEN RULE — an order counts in the month Finance books it, at its pharmacy's own brick and area.** The closing is `phx_closing_distributor_product` PLUS `phx_monthly_closing_direct`: quoting the first alone understates, flipping its `not is_direct` double-counts. Blank-area `DIRECT` rows are the retired vintage. `direct-orders-are-counted-in-the-month-finance-books-them`

- 🔒 **A MARKETING REQUEST CAN BE SETTLED AGAINST A DIRECT ORDER'S DEBT — NO CASH MOVES, AND `paid_amount` STAYS CASH ONLY** (owner, 2026-10-15, Zamzam Hospital: 108,056 of 133,056 paid, the hospital keeping 25,000 for its own doctor). The link is `direct_order_marketing_offsets`, one row per request; `remaining_amount` = value − cash − offsets, written only by `phx_record_direct_order_offset` / `phx_remove_direct_order_offset` under row locks, and every collection edit keeps it (`offset-rules.ts`). Finance only (`canRecordDirectOrderCollection`). An offset never stamps `payment_date` — the phantom-pharmacy check reads that as cash — and a settled request is not "missing payment proof". Pinned by `tests/direct-order-marketing-offset.test.ts`.
- 🔒 **THE ADMINISTRATOR HAS A ONE-CLICK PATH FOR A SERVICE FEE THE PHARMACY KEPT** (owner, 2026-10-15: "I accept that it records all six approvals as made by me"): `phx_admin_settle_service_fee` raises the request under the ORDER'S requester, writes every rung of the chain decided by the Administrator with a note saying so — never another person's name — and settles it, no cash and no notification. System admin only (`canSettleServiceFeeAsAdministrator`), never Finance; the requester is read from the order, not the body. Do not widen it to a role or reuse it for a request someone else raised.

### The returned lane

- 🔴 **A `returned` order whose requester has LEFT is CLOSED, never reassigned — `closeOrphanedDirectOrder` (Super Admin only), from Stuck Approvals.** A return is a question addressed to the one person who raised it (`reviseDirectOrder` refuses everyone else by canonical HR_ID), nothing expires `returned`, and it is in nobody's queue — so it ages out of sight for ever. Reassigning is NOT the kinder option: a resubmit reprices on today's basis and resumes at the rung that returned it, so it hands a live manager a money edit. The close writes `cancelled` + `decided_at` and nothing else — no month, no approval step — and it REFUSES while the requester can still log in, and refuses an HR_ID the employee master does not hold at all as a directory problem rather than a departure. `a-returned-direct-order-has-no-reassign-and-no-close-button`
- 🔴 **A CORRECTION KEEPS EVERY PRODUCT ON A RETURNED ORDER — `resolveCorrectionExtraLines` (correction-lines.ts); only each line's quantity and deal change** (code review, 2026-10-19). The form sent line one alone, the route forwarded no lines and the service rebuilt `[line 1, ...(input.items ?? [])]`, so a returned 86,625 EGP Lacto Advanced 1 + 2 order would have gone back at 49,500 with Lacto Advanced 2 deleted. An ABSENT `items` keeps the stored lines; a sent list must name each stored extra product once, and adding, repeating or leaving one out is refused in words. Never default the route's `items` to `[]`. Pinned by `tests/direct-orders-second-review-fixes.test.ts`.
- 🔴 **"Left" is `isActiveLifecycleStatus` — `active` and `on_leave` ONLY, a blank reading `active`.** A friendlier filter (probation, notice_period) returns an empty stranded list for the wrong reason and reads exactly like a real all-clear; that happened while verifying the 2026-10-08 clear-up.

### The customer search

- 🔴 **A ONE- OR TWO-CHARACTER PROBE IN `phx_search_direct_order_customers` IS ANSWERED FROM THE `phx_direct_order_search_keys` GIN INDEX — THE PROBE BOUND (`{1,2}`), THE KEY FUNCTION'S LONGEST PIECE (2) AND THE `c:`/`n:` PREFIXES MOVE TOGETHER, NEVER ALONE** (16 Oct 2026; a trigram index cannot narrow under 3 characters, so `'10'` re-checked all 81,016 rows at ~2 s). A bound longer than the pieces returns an empty list that reads as "no such customer". The short alphabet is digits, ASCII letters and U+0621..U+064A — never `%`, `_` or `\`. `phx_normalize_arabic`'s removal class is NOT widened to reach a letter (the probe empties and every row matches). The search stays `SECURITY INVOKER`. Pinned by `tests/direct-order-search-short-probe-fast-path.test.ts`. Account: `docs/direct-order-search-speed.md`.

### The nightly totals audit

- 🔴 **FOUR DIRECT-ORDER CHECKS RUN IN THE 04:40 CAIRO RECONCILIATION CRON, AND ALL FOUR PAGE — NONE MAY SIT KNOWN-OPEN** (owner, 2026-10-19: "build the nightly direct-order and approval-panel totals audit"). `src/lib/reconciliation/checks/direct-orders.ts` compares the order's value with the sum of its lines, each line with the locked formula on its own prices (`priceBasketLine`), the panel's working (`computeDirectOrderPricingBreakdown`) with the value, and `remaining_amount` with value − cash − offsets. The comparisons live pure in `src/lib/reconciliation/direct-order-totals.ts` and call the module's own pricing functions, never a copy. The panel check shipped known-open (the panel priced the order ROW, line one only, discount to 3 decimals: 11 orders) and was tightened to `holds` the same day, when the panel began pricing every line. Pinned by `tests/reconciliation-harness.test.ts`.
- 🔴 **THE APPROVAL PANEL'S PRICING ROW WORKS OUT EVERY LINE, THEN THE TOTAL — `computeDirectOrderPricingBreakdown(request, detail.items)`, never the request alone** (owner, 2026-10-19: "fix the direct-order approval panel to show every line's pricing"). The order row is line one only on a basket and keeps the discount to 3 decimals where the line keeps 4, so a breakdown built from it prints a working that does not reach the value. Each line is priced by `priceBasketLine` on its own snapshot; the total is rounded once, as the server stores it; a line with no price leaves no total. Called with no lines it falls back to the row as one line. Pinned by `tests/direct-orders-approval-detail-names.test.ts`.
