## Rules

- 🔴 **THE SYSTEM AUDIT DAILY MESSAGE IS NEVER RE-ASKED THE SAME CAIRO DAY, AND `--apply` NEVER MARKS A LIVE FINDING AS TOLD** (23 Oct 2026). A re-run of `/api/cron/system-audit-sweep` reads `system-audit-daily:<day>:<HR ID>` first and skips anyone already told: the idempotency key stops the second delivery but the refused call still rewrites the stored notice the in-app bell shows (the 10:56 365-issue message became "3 issues" at 11:53). The historical `--apply` marks only the issues IT made waiting; one already waiting before the run stays for the next message. Never "simplify" either back. Account: `docs/system-audit.md`; pinned by `tests/system-audit-daily-message.test.ts` and `tests/system-audit-historical-runner.test.ts`.
- 🔒 **EVERY BLOCK OR FAILED REQUEST A PERSON MEETS LEAVES A SCREENSHOT — SHOWN AS-IS TO THE SUPER ADMIN ONLY, KEPT 90 DAYS** (owner, 23 Oct 2026). `screen-capture.ts` wraps `window.fetch` once, production builds only: a same-origin `/api/` 4xx is a refused request, a 5xx or no answer a failed one; a crash is photographed by #6358's crash screenshot instead, never twice. Never blur it, never show it to another seat, and never put a request a person made on purpose on `SCREEN_CAPTURE_SKIP_LIST` (it holds the capture's own path, sign-in and background polls only). The 90-day removal runs in the nightly System Audit sweep (`user_screens`), never a cron of its own. 🔴 **The crash pictures' 90 days are kept the same way: `pruneOldAppErrorEvents` removes each expired row's `error-screenshots` object FIRST, then the row** — deleting rows by age alone orphaned every picture in the private bucket for ever (review of #6358, 23 Oct 2026). 🔴 **Both captures keep the freeze guards** — `SCREEN_MAX_ELEMENTS`, the `onScreen` filter and the scroll-offset margin; html-to-image copies every kept node's computed styles on the main thread, and the timeout only stops WAITING, so a big page (the payroll grid, a CRM board) freezes the tab without them. Account: `docs/system-audit.md`, "What the person saw". Pinned by `tests/user-error-screens.test.ts`.
- 🔒 **THE CRASH SCREENSHOT IS UNMASKED, AND THAT WAS THE OWNER'S CHOICE** (owner, 23 Oct 2026 — *"the most important thing, I need a screenshot of the error appear to the employee"*, then "capture everything, mask nothing" when asked about payslips). The browser rasterises its own DOM AFTER the error UI paints, so the picture is the fallback card the employee is sitting in front of, not the torn tree behind it (`capture-screenshot.ts`; a page cannot photograph itself, so cross-origin images, iframes and tainted canvases are absent by construction — not defects to chase). Because nothing is masked, the `error-screenshots` bucket is PRIVATE and the drawer mints a five-minute signed URL per view against the viewer's own Super Admin session — never a URL rendered into the page. Do not add masking back without his word, and do not make the bucket public for any reason.
- 🔒 **THE SYSTEM AUDIT BOARD STARTS AT 23 OCT 2026 16:22 CAIRO AND ONLY GROWS FORWARD — THE HISTORY IS NOT REBUILT** (owner, 23 Oct 2026: *"I don't want old errors or issues. I want starting from when it reaches the live production, this is its start point. And when we're walking along"*). The 370 issues and 2,523 occurrences the historical seed had written were cleared that afternoon and the four time cursors in `system_audit_watermarks` (`app_error_fold`, `sync_runs`, `job_failures`, `visit_lifecycle`) fast-forwarded to `2026-10-23T13:22:38.477Z`, which is why the sweep does not re-fold them. 🔴 **That empty board is the intended state, not an incident to repair** — never re-run `scripts/system-audit-historical.ts --apply` over a past window, never rewind those cursors to recover the old rows, and never read a thin board as a broken detector. `app_error_events` keeps its own 90 days regardless; that table is the raw record, the board is only what has been folded since the start point.
- 🔴 **THE SCREENSHOT COPIES AN OFF-SCREEN BOX EMPTY, NEVER DROPS IT — dropping it took its space, so a scrolled page drew everything shifted up out of the picture** (23 Oct 2026: the first real refusal, Khaled Mohamed Ali Bedair on Phoenix CRM at 18:51 Cairo, was a blank white card inside the sidebar and top bar). Both pictures (`screen-capture.ts`, `capture-screenshot.ts`) pass `filter: pictureFilter()`; `createPictureFilter` in `screen-capture-rules.ts` leaves out only what sits INSIDE a box wholly off screen, and never empties an inline element or a table part (their size comes from their contents). Measured on the live page scrolled 592px: 0 of 960 sample cells differ from a capture that drops nothing; the old filter differed in 298. Never go back to judging a node by its own box. Pinned by `tests/error-screenshot-picture-filter.test.ts`.
- 🔒 **EVERY SCREENSHOT OPENED ON THE SYSTEM AUDIT PAGE WRITES ONE AUDIT ROW, BEFORE THE PICTURE LEAVES** (owner, 23 Oct 2026: "log every screenshot view"). Both routes — `screens/[id]` streaming a block or error screen, `screenshot/[eventId]` minting the crash picture's signed URL — await `recordScreenshotView` after the Super Admin guard and the 404, under `system_audit_screenshot_view`: who looked, whose screen by name, the kind, the page, when it was taken. Never defer it with `afterResponse` (a crash between reply and write loses it), and a failed name read still writes the row. Account: `docs/system-audit.md`, "What the person saw". Pinned by `tests/system-audit-screenshot-views.test.ts`.
- 🔴 **A NIGHT THE SCREENSHOT REMOVAL STOPS AT ITS 1,000 CAP WITH PICTURES STILL PAST 90 DAYS RAISES A BOARD ISSUE, WHICH THE MORNING MESSAGE CARRIES** (owner, 23 Oct 2026). `pruneUserErrorScreens` reports `capped` and counts `remaining` after its removals (null, never 0, when the count fails); the `user_screens` detector writes `buildRetentionCapFinding` — signature `screen:retention-cap`, one occurrence per CAIRO night, cursor null — before the sweep sends the message. Never move it to a log line: the message reads the board, and a log row is folded only the next night. Account: `docs/system-audit.md`, "What the person saw". Pinned by `tests/user-error-screens-retention-cap.test.ts`.
- 🔴 **AN ERROR-SCREENSHOT UPLOAD THE SERVER CANNOT STORE — 5xx, 429 OR NO ANSWER — PAUSES EVERY TAB OF THE BROWSER, BEFORE THE THROTTLE AND BEFORE ANYTHING IS DRAWN** (owner, 23 Oct 2026: "pause screenshot uploads while the server cannot store them"). 5 minutes, doubling to an hour, `Retry-After` honoured up to it, ended by one stored picture; 400, 413, 401 and 403 never pause. Shared through localStorage `phoenix:screen-upload-pause`, the tab's own copy when storage is blocked. Every picture leaves through `uploadScreen` — never a second send that skips the pause. Account: `docs/system-audit.md`, "The outage pause". Pinned by `tests/screen-upload-pause.test.ts`.
- 🔴 **A REQUEST WITH NO ANSWER IS PHOTOGRAPHED ONLY IF ITS PAGE STAYED IN SIGHT FROM SEND TO FAILURE — refusals and 5xx answers are photographed as before** (31 Oct 2026). A locked phone kills the requests in flight and the rejection reaches the page once it is back in sight: the plan board's five "no answer" pictures (29 Oct) never reached the server, and one phone saved with 200 three seconds after its picture landed. `screen-capture.ts` counts each hide (`visibilitychange` to hidden, `pagehide`) and `noAnswerHappenedInSight` skips a failure sent hidden, failing hidden, or whose count moved. Never widen it to answered requests, and never answer it with the skip list. Account: `docs/system-audit.md`, "Never captured". Pinned by `tests/user-error-screens.test.ts`.
- 🔴 **A REQUEST THE PAGE CANCELLED ITSELF IS NEVER A CRASH — `reportClientError` RETURNS ON `isBenignClientDisconnect`, AND "Fetch is aborted" IS IN ITS EXACT SET** (31 Oct 2026). Safari on iOS 16 raises a fetch its own screen aborted as an unhandled rejection worded "Fetch is aborted": 108 rows from two reps in 30 days, every stack the Phoenix CRM screen's own `controller.abort()` as it closed. The skip lives in the ONE reporter every boundary and `window.onerror` reach; the classifier drops old tabs' rows as `benign_disconnect`. A `TimeoutError` is NOT an abort and is still reported; the set stays exact ("Connection closed." is a real fault). Account: `docs/system-audit.md`, "Today's errors, 31 Oct 2026". Pinned by `tests/benign-client-disconnect.test.ts` and `tests/system-audit-noise.test.ts`.
