## Rules

- 🔴 **THE PAGE STARTS THE TAB'S FIRST READ, AND THE TAB TAKES IT ONLY ON ITS OWN ADDRESS** (2026-11-01, "make every Phoenix CRM module tab load its first data from the server"). `src/lib/phoenix-crm/server/first-read.ts` holds each tab's first address and its route's own load call, word for word, and `tests/phoenix-crm-first-read.test.ts` compares both with the tab and the route. **Change a tab's first address or a route's load and change it there too**: the screen falls back to its own read, so nothing looks wrong, and the page's read is simply wasted on every open. Used once and never after 30 seconds, because Back restores the page from the router's copy with the read inside it. 🔴 **"Used" is remembered by the id the page stamps on the read (`randomUUID`), never by the object** (3 Nov 2026): a real browser pressed Back 35 s after Visits drew and got the day from before, no read and no page request, because Back hands over the same read in another object. A test that passes the same object back proves nothing here. Never started on a refresh (`router.refresh()` follows every saved visit) or a prefetch. The page's logged duration rises because the read now sits in its stream, so judge it by the browser's paint and the API call count.
- 🔴 **`useCrmGet(url, key)` AND `crmPost(path, payload, key)` HAND BACK `body[key]` — THE VALUE, NEVER THE ENVELOPE — SO A GENERIC THAT WRAPS THE KEY AGAIN IS AN EMPTY SCREEN THE COMPILER CANNOT SEE** (production, 2026-10-12). `request()` ends in `body[key] as T`, so the type argument is an ASSERTION: `useCrmGet<{ sharedPlaces: SharedPlaceChoice[] }>(…, "sharedPlaces")` read as `data?.sharedPlaces` asks an array for a property it has never carried — `?? []`, an empty venue picker on every phone, and a screen that reads exactly like a territory with nothing in it. 🔴 **It cost the company two days of polyclinic seating and Sherif Medhat nine taps on a Save that could not fire**, with the AM/PM step and the timetable camera never drawn while `seatedDraftProblem` still demanded a session. 🔴 **The touch trail found it, not the logs** (`phoenix_crm_touch_trail`, retired 2026-11-01): the HTTP log carries no identity and a 200 on the read proves nothing. Every `useCrmGet` in the module is swept by `tests/phoenix-crm-shared-place.test.ts`. Account: `docs/phoenix-crm-shared-places.md`, "The picker was EMPTY on every phone".
- 🔴 **A PERMISSION THE BROWSER REFUSES IS NAMED BY THE COMPONENT THAT RAISES IT — a screen's `useBrowserNamed()` covers only the SERVER's refusals** (production, 2026-10-13). Four screens raised their own and named none, so a rep read "Location is blocked for **your browser**" with nothing to search for: Norhan Gamal (AI-0025) met it 5 times on 10 and 12 October, the trail (since retired) held 42 of it and 30 of the camera's across 4 reps, and she has never saved a place, a visit or a venue. 🔴 **A browser refusal reached no board at all until 2026-10-13** — `phoenix_crm_refused_readings` held 0 rows for her and `phoenix_crm_touch_trail` was the only witness; it is REPORTED now (the rule below), so a trail dig is no longer how a blocked rep is found. Name it at the RENDER (`{browserNamed(error)}`), never at each `setError`. 🔴 **A screen showing a SERVER refusal names it too** (owner, 2026-10-22): the validation screens printed place refusals raw, so 180 too-rough readings for 12 reps read "for **your browser**". Pinned by `tests/phoenix-crm-browser-name.test.ts`, multi-line notes included.
🔴 **A DROPPED CONNECTION LEAVES SOMETHING TO PRESS, AND A REFUSAL NEVER DOES** (owner, 2026-10-23: *"add a tap-to-retry to the Phoenix CRM pages when the connection drops"*). `app_error_events` held 1,161 rows of the browsers' own network wordings — `Load failed` on iOS, `network error` on Android, `Failed to fetch` on desktop — over 14 days, across 62 releases, median 12.5 minutes into a visible session: a fetch the rep's network cut off, not a Phoenix fault. READS already offered Try again (`CrmLoadError` + `reload`); a SAVE offered the sentence and nothing to press, so the rep re-filled the form and minted a NEW client id — which can file the visit twice. 🔴 **`useCrmAction` keeps the stopped attempt WHOLE — the same payload AND the same completion** (`run(label, work, then)`): a follow-up left behind the `await` runs on the first attempt only, so a retry that worked would leave the panel open. 🔴 **`isRetryableFailure` admits `code === "offline"` ALONE** — a refusal answers the same way however often the same payload arrives and a signed-out session needs a sign-in first, which is the same split `saveStatusLine` already makes on the plan board (`failed` yes, `blocked` no); keep them agreeing. Every save surface renders `CrmSaveError … onRetry={action.retry}` and `RefreshFailed`'s `onRetry` is REQUIRED, both pinned by `tests/phoenix-crm-tap-to-retry.test.ts`.
- 🔴 **A SAVE FROM SOMEONE WHOSE SIGN-IN ENDED ANSWERS 401 `signed_out`, NEVER 403** (24 Oct 2026, 02:35:58 Cairo: a district manager's session reached its absolute expiry mid-plan; his next save 24 s later read as "not allowed"). `assertPermission` throws `SignedOutRefusal` (`src/lib/auth/signed-out-refusal.ts`) for the guest context only, still worded `Forbidden:`; `phoenixCrmFailure` answers it 401 BEFORE the 403 mapping, and `src/components/phoenix-crm/api.ts` turns any 401 into "You are signed out". Never fix it per route — all 115 CRM routes share the one failure handler. Pinned by `tests/phoenix-crm-signed-out-answers-401.test.ts`.
