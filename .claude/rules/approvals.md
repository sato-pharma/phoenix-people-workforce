## Rules

- 🔒 **MARKETING KEEPS ITS OWN INBOX; THE HUB CARRIES ONE LINE, NEVER ITS ROWS** (owner, 2026-11-03). `getMarketingInboxQueueLink` puts "Marketing inbox · N waiting · oldest D days" on the "Each in its own inbox" strip in both shells, with the badge's own count (gating steps on live requests) and only for a role that inbox admits. A failed read says so in the line; nothing waiting means no line. Pinned by `tests/approver-context.test.ts`.

- 🔴 **THE ORPHANED-REQUEST BOARD NAMES A REMEDY VERB ONLY WHERE A CONTROL EXISTS — a returned VACATION had none until 2026-10-15, so its `requesterRemedy` was `null` and the board said no screen could clear it yet** (2026-10-08). The control is now `closeOrphanedVacationRequest` (Super Admin only, on Stuck Approvals): `returned` to `cancelled`, a written reason, refused while the employee can still log in, nothing deleted and no approval step, decision or balance touched; the `v2_vacation_requests` status check gained `cancelled` in `20261015020238_vacation_close_orphaned.sql`. The vacation item's requester case links to Stuck Approvals (`requesterHref`), its approver case still to Leave Approvals. Build the control first, then set the verb; a module that loses its control goes back to `null`. The reader also lists EVERY terminal status in `NO_ACTOR_EXPECTED` (finished requests keep `pending` steps), and reads the employee master whole, keyed case-insensitively — never `.in("hr_id", rawIds)`. `src/lib/approvals/orphaned-requests.ts`, pinned by `tests/orphaned-requests-reader.test.ts` and `tests/direct-orders-close-orphaned.test.ts`.
- 🔒 **THE HUB'S SURFACES COMPOSE THE SHARED ADMIN TOKENS — `adminPanelClassName` for a panel, `adminSoftPanelClassName` for a list row, a filter bar or an empty state, `adminPanelHeaderClassName` for the dark header band** (premium polish, the owner's 2026-09-08 rule, applied 2026-10-09). Measured before it: the largest module in the app with ZERO shadows, its dominant surface `border border-phx-line bg-white` — the panel token with the shadow taken out — hand-written thirty times across fifteen files. 🔴 **This module has no class constants of its own, so both flat shapes are ratcheted at ZERO by `tests/approvals-hub-premium-depth.test.ts`**: a sixteenth file drawing its own panel or its own `bg-slate-900` band fails there rather than being noticed by eye. The mobile thumb bar's shadow points UP, since it is fixed over the page, and a filled action that can be disabled carries `disabled:shadow-none`. The module's pre-existing `rounded-full` dots and `rounded-sm` buttons were deliberately left alone, not swept.
- 🔴 **THE "OTHER APPROVALS" BADGE COUNTS FROM TWO LIGHT LOADERS, NEVER FROM THE TWO WHOLE DASHBOARDS** (owner, 31 Oct 2026: "the lighter inbox count"). `countAwaitingMyActionItems` (`src/lib/action-center/service.ts`) reads `listVisibleResignationStatuses` and `listVisibleContractRenewalWorkflows` — who is waiting and in which status — not `getResignationsDashboardData`/`getContractRenewalDashboardData`: 2 Supabase requests a count instead of 7, the same answer for six viewers on production. 🔴 **Each loader scopes a viewer line for line as its dashboard does** (the company-reader gate and `canSeeEmployee`; `visibleContractEmployees`), and the list and the count decide what waits by the same `isOpenResignation`/`isOpenOutstation`/`isActiveContractRenewal` — change a scope or a status rule in both or neither. Pinned by `tests/badge-counts-viewer-cache.test.ts` and `tests/badge-poll-stays-light.test.ts`. Account: `docs/observability.md`, "Cut 3".
- 🔴 **AN APPROVALS READ FOR A VIEWER WITH NO EMPLOYEE BEHIND THEM IS NOT AN ERROR — `classifyApprovalsLoadFailure` names it `no_employee_profile` and `logLoadFailure` logs it at DEBUG** (23 Oct 2026, System Audit APP-FEAFFD50: View as Seat on an empty seat logged three false errors, 20 Oct). Only `error` is logged as ERROR and reaches the System Audit board, so a timeout or any other failed read must stay `error`. 🔴 **Classify by the class `VacationViewerHasNoEmployeeProfileError`, never by matching its words** — the same sentence from another module is a real fault. Pinned by `tests/approvals-badge-empty-seat.test.ts`.
- 🔴 **A BUTTON'S ANSWER NEVER WAITS FOR ITS NOTICES — THEY RUN INSIDE `afterResponse`, NEVER BEFORE THE REPLY** (23 Oct 2026, owner: approve, reject and 90% of the buttons were "stale, very long"). Production p50 before: vacation decision 6.1 s, excuse 8.0 s, direct-order decision 7.8 s (22 s at p95), marketing decision 10.7 s — the decision itself was done at 0.8 s and the notices were the other 87%, while Phoenix CRM's decide, already deferred, took 0.4 s. Keep the failure record (`notification_failed`) INSIDE the task, capture only `const`s, leave cron and loop notice code awaited (no reply to be late for), and never defer a notice whose result the caller returns. A failed notice is now logged (`after_response_failed`), not thrown over a saved decision. Every notice call in an interactive handler goes through `afterResponse(label, task)` (`src/lib/http/after-response.ts`). Pinned by `tests/notices-after-the-reply.test.ts`. Account: `docs/buttons-answer-before-notices.md`.
- 🔴 **THE WAITING-APPROVAL REMINDER COUNTS ONLY THE STEP THAT CAN DECIDE NOW, ON AN OPEN REQUEST, AND SPEAKS ONLY FROM THE THIRD WHATSAPP NUMBER** (owner, 3 Nov 2026: "All 25 people", "A new third number"). Leftover pending rows on rejected or cancelled requests never count, a later rung never counts, and the clock starts when the step reached that person. It is off until he says, by three locks that need no merge: the switch on the recipients screen, the number being set up, and Meta's approval. Replies on that number are dropped before the inbox or the applicant bot reads the delivery, and its sends skip the recruitment report. Never add the number to `WHATSAPP_PHONE_NUMBER_IDS`. `src/lib/approvals/urgent-whatsapp-rules.ts`; account: `docs/agents-owner-rules.md`, "The approval reminders on WhatsApp".
- 🔴 **A BULK DECISION IS THE SINGLE DECISION REPEATED — `/api/approvals/bulk-decision` RUNS EACH TICKED LEAVE OR EXCUSE REQUEST THROUGH ITS OWN SERVICE, ONE AFTER ANOTHER, NEVER WITH THE OVERRIDE** (owner, 2026-11-12: "make me able to multi-select and approve"). `bulkDecideApprovals` (`src/lib/approvals-hub/bulk-decide.ts`) calls `decideVacationRequest` / `decideExcuseRequestAsManager`; Approve or Reject only (Return needs its own comment), a reason on every rejection, at most 50 per call, one failure never stops the rest, and only the decided ones are un-ticked. Only a section awaiting the viewer is tickable; Plans stay one at a time. Pinned by `tests/approvals-bulk-decision.test.ts`.
