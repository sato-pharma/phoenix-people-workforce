## Rules

### Design tokens

- 🔴 **`rounded-full` IS THE ONE RADIUS CLASS NO `--phx-radius-*` TOKEN REACHES, SO IT IS SQUARE ONLY INSIDE `.admin-shell` AND `.employee-portal-shell`.** Compiled from the real `globals.css` and measured 2026-10-06: `.rounded-full` emits `border-radius: calc(infinity * 1px)`, a Tailwind literal, while every other step emits a `var(--phx-radius-*)` that `tokens.css` sets to 0. The same badge markup reads **0px inside a shell** — RULE 1 zeroes `[class*="rounded"]` there — and **33,554,432px outside one**, the exact hazard `globals.css` already records for `--radius-3xl/4xl`. 🔴 **So "it looks square on this page" is NOT compliance with the square-edge golden rule**: a `rounded-full` is one mount outside the shell away from rendering a pill, with nothing to catch it. Use `rounded-md`, which is square by token in either context. 🔴 **And a route folder grep for the shell class CANNOT tell you whether a page is shelled** — `app/dev/employee-portals` carries none and still measured 0px, because it nests its badge inside `EmployeePortalChrome`, which applies `employee-portal-shell`: walk the import chain, never the folder.
- 🔒 **THE WIZARD SHELL IS DECLARED IN EXACTLY ONE FILE — `src/components/ui/form-kit.tsx` — and a second copy of the rail or the phone stepper is refused by `tests/form-design-system.test.ts` section 4** (2026-10-07, after Phoenix CRM's `step-form.tsx` carried the whole shell a second time, class for class, so a change to the orange strip reached one of the two screens with nothing going red). A form needing something the kit does not do adds a PROP — `canJump`, `footer`, `panel`, `bleed`, `footnoteIcon` all exist because that copy needed them — never a fork. 🔴 **The ONE exemption is the self spotlight, which HE moved onto the EMPLOYEE PORTAL's look on 2026-09-30**; `tests/spotlight-portal-look.test.ts` holds it there, so converting it to `FormWizard` reverts his instruction — a session did exactly that and that test caught it. **Square is settled INSIDE the portal too**: Report It is a portal page with no corner radius, so a `rounded-sm` on a portal form is a leftover, not the portal's look — section 5 pins the forms already converted.
- 🔒 **A DECISION PAIR WEARS `phxButtonApproveClassName` + `phxButtonDangerClassName`, AND EMERALD EXISTS IN NO OTHER TOKEN** (owner, 2026-10-07: "add an approve-green button token to the form kit", then "sweep the ten lone green buttons too" — 23 hand-written green buttons went onto it, leaving ZERO). The form palette cannot say approve: orange is the one terminal commit and rose is a problem, so an Accept painted orange reads as *submit*. The approve token takes the danger token's geometry deliberately — they only ever render side by side. 🔴 **Green is NOT a second accent**: `identityTests()` scans EVERY exported token, so a green Save/Next/Submit fails by name, and **section 6 refuses a new hand-written green button**, its exception list now EMPTY. **On a dense control use the colour-only `…DenseClassName` twins**: `<Button>` is `h-8 px-2.5` and a row chip brings its own padding, so a full-size token outgrows its neighbour. They carry NO dimension and the test fails if one grows. The amber third decision (*Return*) is not a token.
- 🔒 **EVERY WHATSAPP BUTTON IS `phxWhatsApp{Share,Send}ButtonClassName` IN `src/components/ui/brand-tokens.ts` — `#25D366` fill, `#1DA851` hairline and hover, near-black ink, two sizes and ONE look** (owner, 2026-10-07 — before it, the calendar's share links were emerald-600 while the send buttons used the real hex). 🔴 **NOT in `form-tokens.ts`** — a brand there reads as a fifth accent, and a change to the approve green would restyle WhatsApp. `#1DA851` is `#25D366` darkened, not a second brand colour: WhatsApp's other published greens are teals, and green→teal on hover reads as a different button. 🔴 **THE INK IS A FIXED NEAR-BLACK, `text-slate-900`** (owner, 2026-10-08: "use near-black ink on the WhatsApp buttons") — shown that WhatsApp's own white measures **1.98:1** here, he chose legibility over likeness; slate-900 is **9.00:1** on the fill. **Never `text-phx-ink` or any `var()` ink**: it is near-black in light mode and near-WHITE in dark, so on a fill that cannot follow the theme it restores the 1.98:1 silently. A RESTING `bg-[#25D366]` in a `.tsx` is refused; the organogram's button needs no exception because it paints the hex on text and hover only.
- 🔒 **THE DARK PANEL HEADER BAND IS ONE TOKEN — `adminPanelHeaderClassName`, the hero's own three-stop gradient at band scale with an ORANGE hairline under it** (added 2026-10-09 by the Approvals Hub's premium-polish pass, which carried thirteen hand-written `bg-slate-900` copies). Two reasons it is a token and not a colour: the hero's own note says the warm third stop is what stops a near-black band reading as an unstyled div, and a `border-phx-line` grey under near-black renders as nothing at all. 🔴 **The PADDING stays at the call site** — a band over a table and a band over prose do not want the same one — and the token carries **no radius**, because the portal twin of an admin screen zeroes none. Pinned by `tests/approvals-hub-premium-depth.test.ts`, which reads the token's VALUE: grepping a module that uses it only ever sees the token's NAME, so depth and radius are invisible there.
- 🔒 **DEPTH WITHOUT A GROUND IS FIVE TOKENS — `adminPanelDepthClassName`, `adminSoftDepthClassName`, `adminRecessedDepthClassName`, `adminControlDepthClassName`, `adminChipDepthClassName`** (added 2026-10-09 by recruitment's premium-polish pass). A module built before the rule already draws its own border and background, and `--phx-line` is **#e0dcd4** where `border-slate-200` is **#e2e8f0** — so taking 139 existing surfaces onto `adminPanelClassName` recolours a hundred borders, which is a redesign wearing a depth rule's clothes. These carry the panel tokens' shadows and nothing else. 🔴 **Each is pinned by EQUALITY to the panel token it mirrors** (`tests/recruitment-premium-depth.test.ts`), so "tuning" one cannot quietly split the app into two materials. Choose by where the surface sits, never by how big it is: PANEL on the page, SOFT nested inside one, RECESSED for a read-only well or a dialog's edge strip (an INNER shadow — a surface cut into the page cannot also float above it), CONTROL on a button with `disabled:shadow-none`, CHIP on a pill.
- 🔒 **A FIXED BOTTOM BAR CASTS ITS SHADOW UPWARD, AND THAT IS ITS OWN SIXTH TOKEN — `adminThumbBarDepthClassName`, `shadow-[0_-8px_24px_rgba(15,23,42,0.1)]`** (added 2026-10-09 by direct orders' premium-polish pass; direct orders' mobile submit bar and the Approvals Hub's decision bar are the two bars in the app). A bar pinned to the bottom of the viewport sits BELOW everything it covers, so any of the five downward tokens throws its lift onto content nobody can see and the bar reads as painted onto the page. 🔴 **Pinned by the SIGN of the offset, not just by its value** (`tests/direct-orders-premium-depth.test.ts`): a flipped `0_8px` is the one break that still looks deliberate in a diff. The Approvals Hub keeps the same value written inline on purpose — `tests/approvals-hub-premium-depth.test.ts` reads the class string on that element in `decision-actions.tsx` — so naming it here is what stops a third bar inventing a third spelling, never a licence to "tidy" that copy onto the token.
- 🔴 **A FORM CONTROL THAT PAINTS ITS OWN BOX, OR A FORM TOKEN OVERRIDDEN INSIDE A TEMPLATE LITERAL, IS REFUSED AT THE WRITE — with the `form-tokens` import or the exact `cn()` call in the refusal** (`.claude/hooks/form-design-guard.mjs`, 2026-10-12). Those are the two zero-tolerance halves of `tests/form-design-system.test.ts`: `SELF_SKINNED_CAP = 0`, and the merge-semantics check that empties the override list. Both already redden the required `validate` job on the first new site, so the alternative to the refusal was a full CI round ending in a one-line import — thirteen of the twenty-six red PR runs of 12 Oct 2026 were repo-wide contract gates of that kind. The detector has ONE home, `.claude/hooks/lib/form-design-shapes.mjs`, which also holds the `EXEMPT` list and his rulings that used to sit in the test's doc comments; the ratchet imports `commentMask`, `EXEMPT`, `fileConstants`, `scanControls` and `templateConcatSites` from it and defines none of them, and `tests/form-design-guard.test.ts` fails if either side grows a copy back — **a new exemption joins that module, never a list inside the hook.** It reads only the text being INTRODUCED (so an edit that removes an offender always passes) and resolves a className that is a REFERENCE from the file plus at most 14 imported files, never a sweep of `src/`; an unresolvable reference paints nothing and is allowed, because a hook stricter than the check it fronts for refuses work CI accepts. `PHX_FORM_DESIGN_OFF=1` stands it down. Account: `docs/hook-dispatcher.md`, "form-design-guard".
- 🔴 **NEVER SPELL A WHITESPACE RUN `\s*\n?\s*` IN THE SHARED DETECTOR — IT IS `\s*` WITH AN EXPONENT ON IT** (2026-10-12). `\n` is already inside `\s`, so the pair matches exactly the same text and only adds O(k²) ways to split each gap — and inside `fileConstants`'s `(… + …)*` chain those multiply. `src/lib/phoenix-crm/server/signboard-check.ts`, a 26-term `+` chain whose strings carry ESCAPED quotes that `"[^"]*"` cannot match, therefore cost **209,644ms of the sweep's 210,151ms and 194,342ms of the 313s unit-test step** — on every PR and every `main` push, with `--cpu-prof` putting 97.0% of 242.4s in that ONE RegExp; collapsed to `\s*` the file is 0ms and the whole sweep 369ms, with ZERO capture differences over 3,916 files and 4,275 constants. **On the laptop, `tests/form-design-system.test.ts` alone went from 170.8s to 7.4s** (12 Oct 2026, one run each, 3.2 GB free: a before-and-after, not a benchmark). 🔴 **The hook resolves through up to 14 imported files with this same resolver, so the shape can hang a KEYSTROKE, not just a job.** Pinned by `constantSweepIsLinearTests` in `tests/form-design-guard.test.ts` as a **BUDGET** (500ms on one 11-term chain; 4,787ms with the pair restored) — a budget and not an output, because nothing in the suite ever noticed: the sweep returned the right answer, slowly. Account: `docs/hook-dispatcher.md`, "form-design-guard".
