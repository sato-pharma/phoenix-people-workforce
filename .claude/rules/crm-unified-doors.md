## Rules

Moved out of `crm` on 2026-10-23 so each module's injected pointer stays under the 4,000-byte
margin `tests/module-memory.test.ts` holds. **`crm` keeps every glob it had**, so a session working on
these files loads BOTH — nothing that used to arrive stopped arriving.
- 🔴 **A READER THAT DOES NOT GO THROUGH THE VIEWS MUST ASK `startedWindowCovers` BEFORE IT PICKS A SOURCE.** The views apply the starts in SQL, so a door reader needs nothing — but one that calls the live iReports360 API, or reads the raw mirror, has no `source` column to judge a row by. The GLOBAL `crm_cutover.cutover_date` is NOT that switch and is still NULL: a per-team start never sets it, so gating on it alone lets a started rep through to the vendor, and a live call that SUCCEEDS with zero rows is served as the truth (`rep-day.ts`'s fallback only catches a THROW). Measured 2026-10-04 (Delta (1)): the drill-down read "no visits" for a rep with 22 Phoenix calls, and 3 raw-mirror rows read INSTEAD of a rep's 2 Phoenix visits. Since 2026-10-16 a covered day with no Phoenix entry keeps his iReports360 rows (Phoenix wins the day, `phoenix_crm_rep_entry_days()`). Rule and window type: `phoenix-team-starts.ts`; its ONE RPC read is `src/lib/crm/phoenix-started-reps.ts`, which fails OPEN. Pinned in `tests/phoenix-crm-visits-everywhere.test.ts`.
- 🔴 **THE DEPARTED-AGENT EXCLUSION IS KEYED ON WHO *LOGGED* THE ROW, SO A READ THAT DECIDES WHETHER SOMEBODY *WORKED* USES `scanVisitsForRangeCreditingPartners`, NEVER `scanVisitsForRange`.** `exclusion_crm_id` IS `agent_crm_id`, and a manager's fieldwork lives on the REP's row as its `double_hr_id` — so the day a rep resigned, every double visit his manager did with him vanished and his own day read "no CRM activity": a deduction applied RETROACTIVELY to a month already worked (owner, 2026-10-07). The door rescues such a row only when it names a real partner (`REAL_DOUBLE_PARTNER_OR_FILTER`), nulls `agent_hr_id` and sets `partner_credit_only`, and **keeps `agent_crm_id` — the duplicate-collapse key.** A bounded read naming people on the DOUBLE side passes `creditDepartedAgentPartners: true` to `queryVisits`; a rep's OWN numbers keep the plain scan. 🔴 **The live tier keys on STATUS, not a date, and a resignation sets the status the minute HR records it — so a rep serving notice loses every row of the notice period. A reader that JUDGES that leaver adds `queryOwnVisitsOfDepartedAgents`** (own rows, through the last working day only — a later row on the slot is the successor's); the CRM day map does since 2026-10-18 (`tests/crm-day-map-departed-own-visits.test.ts`). Never make the exclusion itself date-aware: that restates every live board, and the static tier holds owner-excluded ACTIVE people. 🔴 **The exclusion is 119 ids — 71 static + 56 live — and reproducing it in SQL joins the MIRROR's `agent_hr_id`, never `employees.crm_id`: a false clean bill of health.** Pinned by `tests/crm-double-visit-with-departed-partner.test.ts`. Account: `docs/crm-departed-partner-exclusion.md`.
- 🔴 **THE VISITS DOOR CARRIES TWO PARTNER SLOTS, AND SLOT 1 IS `coalesce(manager, product_manager, senior)`.** Slot 1 read `manager_hr_id` alone, which is NULL on a `product_manager` visit, so the visit carried nobody and the day read as a day the rep did not work; a `chain` visit lost its second person entirely. `double2_crm_id` / `double2_name` / `double2_hr_id` are APPENDED (a `create or replace view` takes a new column only at the END, and `crm_visits_checkin_flags` depends on this one), NULL on both vendor branches. PARITY, not new policy. `buildParticipantCrmIdOrFilter`, `buildParticipantHrIdOrFilter` and the `doubleHrIds` filter ask BOTH slots; `doubleOnly` and `requireDoubleHrId` need no second arm, because slot 2 can never be filled while slot 1 is empty.
- 🔴 **NEVER HAND-ROLL THE EXPRESSION, AND THE SECOND HALF IS IN TYPESCRIPT** — `doubleHrIds` already returns the slot-2 row, so a reader that decides "whose visit is this" against one partner column throws it away again. **The presence and money class is SWEPT (the three DEDUCTION connectors among them, where a manager read as absent is a manager the month CHARGES).**
- 🔴 **A PHOENIX-BORN DOCTOR ANSWERS TO `own_contact_crm_id`, FROM THE RESERVED POSITIVE RANGE `crm_contacts_phoenix_id_seq` (1,000,000,000–2,000,000,000), AND ALL THREE DOORS EMIT THE SAME `coalesce(reference_contact_crm_id, own_contact_crm_id)`.** Without it a Phoenix-born doctor has no id and every per-doctor report keys on one, so the visit vanished. **Never a negative contact id** — it breaks three live constraints, one of them an `integer` column that answers `22003`. The doors are pinned EQUAL to each other, because a visit carrying an id against a plan that carries none reads MISSED, worse than a blank. A `before update of reference_contact_crm_id` trigger refuses to re-point a customer who has already carried his own id into a report. The `crm_contacts` name row is `source = 'phoenix'` — the only value that CHECK allows. Account: `docs/phoenix-crm-switchover-2026-10.md`, §3.
- 🔴 **THE COUNTING DOOR IS NOT AN EVIDENCE DOOR — `crm_visits_unified`'s PHOENIX BRANCH IS INNER-JOINED TO A STARTED TEAM (`phoenix_crm_started_team_seats() ON seat_id = p.seat_id AND p.visit_date >= team.starts_on`), SO ANYTHING DECIDING "DID HE WORK THAT DAY" READS `src/lib/crm/phoenix-work-evidence.ts` INSTEAD.** That join is CORRECT for counting — a team the Super Admin has not pressed Start on is not yet scored by the Phoenix rules — but real logged work is then invisible: 121 visits by 6 Medical Reps over 7–12 Oct 2026 reached no reader, and the deduction connectors read a day spent in the field as a day nobody worked. The evidence loader asks the base tables — `phoenix_crm_visits` (never `phoenix_crm_countable_visits`, so an unapproved off-plan visit still proves the day), `phoenix_crm_day_activities` and `phoenix_crm_day_starts` (carried, but a start alone proves NOTHING) — all `is_test = false`, keyed on the `rep_hr_id` the rows carry themselves, so no seat join is needed, and it **throws on a failed read** because a silent empty answer is a charge. `crm-single-source.test.ts` permits it: that guard forbids `ireports360_*` and `crm_*_unified`, not the Phoenix tables. Account: `docs/deductions-phoenix-work-evidence.md`.
- 🔴 **AN OLD-CRM ROW'S `agent_name` IS WHOEVER HOLDS THAT ACCOUNT NOW, NOT WHO MADE THE VISIT — NAME A PERSON FOR A VISIT ONLY BY ITS DATE AGAINST THEIR HIRE DATE** (owner, 2026-10-22: *"check Osama's hiring date. The visits on the old CRM are not related to him"*). The CRM administrator seats a new hire on the leaver's account, and the rename re-stamps every old row with the new name, so a visit dated before the hire belongs to the account's earlier holder; `agent_hr_id` is NULL on those rows because the sync refuses pre-hire attribution (`src/lib/crm/identity.ts`). Before any audit, board or chat answer puts a rep's name against an iReports360 row, read the hire date; seat history is `au_v_seat_occupancy_all`. Memory: `crm-resigned-slot-reused-for-new-hire`.
- 🔴 **THE COUNTABLE VIEW'S CUSTOMER JOIN IS LEFT ON PURPOSE, NEVER INNER** (speed, 2026-10-23). Postgres drops a LEFT join to a unique key that a query never reads, so `phoenix_crm_rep_entry_days()` — which rebuilds every entry day from all history on each read of both unified doors — no longer looks up the customer of every visit ever saved: its buffer reads fell from 18,025 to about 4,500, and the same rows came back (checksum identical before and after). The rows cannot differ: `customer_id` is NOT NULL with the foreign key, and `customer_validated` is coalesced to false so it stays two-state. Inner would be a silent slowdown no figure shows. `20261023040102`, pinned by `tests/phoenix-crm-countable-visits.test.ts`.
- 🔴 **THE ENTRY DAYS ARE A CACHED TABLE, AND `_calc()` IS THE ONE BODY** (speed, 2026-10-23). `phoenix_crm_rep_entry_days()` reads `phoenix_crm_rep_entry_days_cache` and must never fall back to the live computation; the rebuild, the single-key `_touch` and the reconcile all recompute **through `phoenix_crm_rep_entry_days_calc()`**, so a writer that re-types "did this rep record a Phoenix entry" makes a second definition of a golden rule. Four fact tables are triggered on insert, update AND delete, and an UPDATE recomputes the OLD key too; `phoenix_crm_team_starts` rebuilds; `employees` and `au.seats` are deliberately NOT triggered, so the 5-minute `phoenix-crm-rep-entry-days-reconcile` cron is their staleness bound and it repairs and warns. A figure that disagrees with `_calc()` means the cache. `20261023091035`, applied through `scripts/apply-sql-file.mjs` so it lives in `ACKNOWLEDGED_EXCEPTIONS`, not either ledger; pinned by `tests/phoenix-crm-rep-entry-days-cache.test.ts`. Account: `docs/crm-rep-entry-days-cache.md`.
