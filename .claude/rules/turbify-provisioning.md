## Rules

🔒 **`turbify.md` LOADS BESIDE THIS FILE, NEVER INSTEAD OF IT** — its globs are the broad
ones and they were deliberately left that way when this module was split out of it on 2026-10-04.
The CONSOLE's golden rules live there: the console's search is a substring match so one row must be
an identity check and never a count; a coordinate click that reports success is not evidence the
control was clicked; `textContent` glues this console's labels together with no separator; there are
two Turbify login pages whose email fields share no selector. **Every one of those applies to the
create path in this file.** If you are working here and have not seen them, open `.claude/rules/turbify.md`.

The rules below are the PROVISIONING sequence itself — what a create leaves behind, the invitation
that carries the credential, the one window an app password can be minted in, and what a run may
report or record.

- 🔴 **ADOPTION NEVER RUNS ON A SCHEDULE** — it resets a mailbox somebody reads every day, so its only caller is the Super-Admin-only route behind the New Hire Mailboxes card, and `tests/new-hire-mailbox-adopt.test.ts` fails if a cron route or the sweep so much as names it. Wiring it into the daily sweep is the obvious-looking way to "finish the remaining mailboxes" and would lock people out overnight with nobody told. The joiner robot is the scheduled one, because a mailbox it has just created belongs to nobody yet.
- 🔴 **A MAILBOX TURBIFY CREATES LANDS IN `Pending`, AND `Active mailboxes` DOES NOT COUNT IT — so "the count did not move" is NOT proof nothing was created.** Create does not behave like reset: it makes the mailbox Pending and hands the password over by INVITATION, never through the `One-time password` dialog a reset opens, so the robot threw and reported `provisioned: 0` while `ahmed.mohamed@` and `asmaa.zaghloul@` really existed (2026-10-03). A Pending row carries NO `Reset password` button, so counting those reports it absent, and its address must be read from its OWN cell — the display name runs straight into it, so the row's text parses as `Abd-Elnaimahmed.mohamed@satopharma.com`. The post-save view offers `send invite` and `print`; **neither is part of the flow any more** — the robot reads the invitation instead (next rule). Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **THE CREATE PATH IS FINISHED BY READING THE INVITATION, NOT BY A DIALOG — no `One-time password` dialog IS the normal create.** The robot polls `hr.mailbox@satopharma.com` through the mailbox monitor and hands the invitation's **Temp Password** back in the one-time password's place; both are one-use. **The dialog still wins where it exists** — the inbox is the fallback, never read first. `invite-inbox-reader.ts` imposes newest-first ITSELF, sorts an undated message LAST (the hazard is `NaN`, not 1970), opens ONLY a plausible invitation because every body fetch is an audited `mailbox_access` row attributed to `ROBOT_ACTOR`, and returns `retryable` so the poll stops dead on any refusal waiting cannot change. 🔴 **A driver built WITHOUT the reader cannot finish a create at all** — `createJoinerDriverFromEnv` is where it is attached. 🔴 **AND THIS IS NOT AN END-TO-END CREATE:** step 2 still lands on the `Set up your mailbox password` page whose unlabelled, non-`required` checkbox stopped `hr.mailbox@`. Pinned by `tests/new-hire-mailbox-invite-inbox-reader.test.ts` (16/16 breaks fired). Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **THE APP-PASSWORDS PAGE IS CAPTURED BY SIGNING IN WITH A PASSWORD PHOENIX ALREADY HOLDS — NEVER BY RESETTING FIRST.** `POST /api/new-hire-mailboxes/app-password-controls` (`describeAppPasswords`) reads it and changes nothing: no reset, no mint, no remove press. A reset lands on the terms-of-service screen no automation may accept; the only other read runs after minting. 🔴 **A setup screen, or a run stuck on `Bizmail Login`, is an ANSWER and not a missing control** — a mailbox that has never completed its own first sign-in needs his four manual clicks once before anything can be captured, and 🔴 **reading its MAIL proves nothing about that**: an app password survives a password change. 🔴 **A FAILED RUN IS RECORDED — the throw used to sail past the audit**, so one left no row at all; the row carries `failed: true` (written on both paths) and the measured page as `why`, closes the browser first and rethrows. 🔴 **Shipping the capture calibrates NOTHING:** `APP_PASSWORD_CLEAR_CALIBRATED` was turned on (13 Nov 2026) only because the live rehearsal of 4 Oct 2026 19:23 Cairo read all four controls, the confirm included; it may be true only while no control is a placeholder. Pinned by `tests/new-hire-mailbox-app-password-capture.test.ts`. Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **A STEP THAT CLICKS BEFORE IT READS CAN ONLY EVER REPORT "MAY HAVE" — arm the damage flag BEFORE the call, never after it.** `resetAndCapture` clicks Reset and then reads the dialog, so a failure while reading exists *because* Turbify already reset the mailbox — and `invite-inbox-runner.ts`, arming its flag after the call returned, told the owner `hr.mailbox@satopharma.com was not reset` about a mailbox that had been (2026-10-03). He went looking for the wrong problem, and the outstanding one-time password went unmentioned. The flag is `mayBeReset` now: it may only OVERSTATE the damage, which is the right way round for a mailbox Phoenix owns, and a test asserts a reset-step failure can never report the mailbox untouched.
- 🔴 **THE NEW HIRE'S ADDRESS IS THE ONE THE OWNER TYPES — EXCEPT THROUGH THE OFFER JOINING FORM, WHICH GENERATES IT OR SAYS IT COULD NOT** (owner, 2026-10-03; the joining-form door opened 2026-10-08: *"generate it automatically but if it couldn't, it tell it couldn't … and HR can address manual"*). `joiningFormMailboxAddress` in `address.ts` is the ONLY generator: two plain Latin words, neither of the first two a particle (El, Al, Abd, Abdel, Abu…), `first.second` then `first.last`, never a numbered guess; anything else returns a reason, the page tells the candidate HR will send it, and the task opens with no address exactly as a typed-blank hire does. Add Employee and the import still never derive one. The generator that built `first.second` from the name turned "El Sayed Rady" into `el.sayed@satopharma.com` — his first name is **Elsayed**, one word — and the robot created that mailbox on the live domain before anyone read the register; undoing it took a console deletion. The Employee Master now types the local part against a fixed, greyed `@satopharma.com`; `openNewHireMailboxTasks` stores the typed company address **or null**; and `loadJoinerCandidates` SKIPS a task with no address so the robot waits a sweep rather than inventing one. `mailboxAddressCandidates` and `proposeMailboxAddress` are DELETED and pinned absent. Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **TURBIFY'S CREATE HANDS BACK NO PASSWORD — IT EMAILS A `Temp Password:` LINE, AND THAT EMAIL IS THE ONLY CREDENTIAL THE MAILBOX EVER HAS** (measured 2026-10-03). The `One-time password` dialog belongs to the RESET path only, so a create that waits for it strands the mailbox `Pending` for ever — three real ones, while the sweep reported `provisioned: 0`, because `TURBIFY_INVITE_RECIPIENT` was `""` and the email went nowhere. It is now `hr.mailbox@satopharma.com`, a mailbox Phoenix owns and reads, kept as a CONSTANT because `railway variables --set` bypasses the CI deploy gate. `readInvitation` matches the invitation to its mailbox by IDENTITY — one inbox receives every hire's, and `adel.sayed@` contains `el.sayed@` — refuses on a changed label instead of guessing, never reads the body's own `*Password:* {The password you create...}` help line, and never quotes the credential in a refusal. Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **ADOPTING THE INVITE INBOX RUNS A PASSWORD RESET, SO ITS ADDRESS IS COMPARED AND NEVER CHOSEN** — `evaluateInviteInboxAdoption` matches `TURBIFY_INVITE_RECIPIENT` by identity, the route passes the constant rather than the request body, and the card has no address field; the same chain pointed at an employee locks them out of their mail with nobody told. No `force`/`override` parameter, ever — that is how a reset-ONE flow becomes a reset-ANY flow. A missing company password is refused BEFORE the reset, because a reset with nothing set afterwards leaves the mailbox unreachable. 🔴 **And `addMonitor` is what proves it**: it runs `testMailboxConnection` and refuses a credential that cannot open the mailbox, so `adopted` means a real IMAP login succeeded — not that a password was typed and assumed to work. Never scheduled (it would reset the inbox mid-read). Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **THE APP PASSWORD IS OPTIONAL FOR THE INVITE INBOX AND REQUIRED FOR AN EMPLOYEE — THE MONITOR IS WHAT MAKES THAT SAFE** (2026-10-03). `generateAppPassword` sat on the critical path of `invite-inbox-runner.ts` while being the one step nothing in Phoenix had ever reached, so its failure reported *“MAY ALREADY HAVE BEEN RESET”* over work that had SUCCEEDED — reset done, company password set — and sent the owner back to click again, five times. It now falls back to the company password, and that cannot fake a success because `addMonitor` runs `testMailboxConnection` and refuses a credential it cannot log in with (422, nothing stored), so `adopted: true` still means a real IMAP login happened. 🔴 **Scoped deliberately:** the ONE thing an app password buys is surviving a later password change, which is decisive for an EMPLOYEE (they change it at handover) and worth nothing for an inbox Phoenix owns — so `runner.ts` and `adopt-runner.ts` still require it, pinned by a source assertion that they carry no `?? companyPassword`. Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **NEVER `router.refresh()` AFTER A MAILBOX RUN — IT REMOUNTS THE CARD AND ERASES THE RUN'S ONLY ACCOUNT.** Production 2026-10-03, 23:02:13: a live adoption failed, the refresh fired, the card came back with `result` at its initial `null`, and the sentence naming the cause was gone before anyone read it — a card that looked unclicked, over a run that cannot be repeated. **It is worse on success:** `handover` is what the employee must be told, and for a new hire the company password becomes their real password. A queue list one click fresher is never worth either. Pinned by `tests/new-hire-mailbox-result-survives.test.ts` — and its render assertions must match a **braced JSX child** (`{result.handover}`), because these files read each value twice and a bare-property pattern is satisfied by the `x.handover ?` guard while nothing is drawn.
- 🔴 **AN ADOPTION'S AUDIT ROW CARRIES `detail` AND NEVER `handover`.** `refusal` is the pure gate's enum, so it is `null` on every run the gate ALLOWED — which is every run that actually reached Turbify: both failures of 2026-10-03 stored `adopted: false, refusal: null` and nothing else, and the diagnostic had to be copied out of a browser by hand. The adopt route audits each outcome's `address`/`status`/`detail` beside its counts, which alone say how many failed and never why. `handover` stays out for the credential reason above. Pinned in `tests/new-hire-mailbox-invite-inbox.test.ts`, on comment-stripped source because the comments name both fields.
- 🔴 **NEVER READ A CREDENTIAL OUT OF `describePage` — IT REDACTS, AND WHAT IT DROPS IS EXACTLY THE VALUE YOU ARE READING FOR.** The mint-and-remove rehearsal's first draft handed `pickAppPassword` a `describePage` result, and that read could never have succeeded: the redactor drops anything secret-shaped, so the app password was gone before the picker saw the text. **The failure wears the shape of a page problem** — “no app password could be read”, the same sentence a changed console gives — while the real cause is the redactor working correctly, and the cost is a LIVE credential on the mailbox with nothing in `secrets` to keep it out of the report, the audit row and the log. Read the page's own text (`evaluate` on `document.body`), as `generateAppPassword` already does, and feed the value to `secrets` from there. `describePage` is for the `why` of a refusal and for nothing a caller must still parse. An UNREADABLE minted value is never a reason to stop, either — the credential already exists, so returning early is the one outcome the rehearsal exists to avoid. Pinned on what `pickAppPassword` is HANDED (the helper sits two lines away and reads like a tidy-up waiting to happen), in `tests/new-hire-mailbox-app-password-rehearsal.test.ts`. Account — why the failure reads as a page problem: `docs/mailbox-robot-calibration.md`, “The read that could never have worked”.
- 🔴 **`removeConfirm` CANNOT BE CAPTURED BY READING — IT DOES NOT EXIST UNTIL REMOVE IS PRESSED, WHICH IS WHY ONE STEP MINTS A REAL CREDENTIAL.** The read-only capture filled three of `APP_PASSWORD_REVOKE_CONTROLS`'s four placeholders and re-running it would never have filled the fourth. `rehearseAppPasswordRemoval` is the answer and it is **hard-scoped to `TURBIFY_INVITE_RECIPIENT` by its FIRST statement, before a browser is opened** — a guard after the sign-in is still correct and still wrong, because the run has committed to a mailbox by then; the route hands it the constant, never anything from the request body. `outstanding: true` is the field that means a working app password is adrift and a human must remove it by hand: `removed: false` alone reads as “nothing happened”, the opposite of the truth, so both removal failures set it and a throw records it `null` rather than `false`. Never in `JOINER_STEP_ORDER` and never named by the sweep — on a schedule it mints a real credential nightly for a diagnostic nobody asked for. Account: `docs/mailbox-robot-calibration.md`.
