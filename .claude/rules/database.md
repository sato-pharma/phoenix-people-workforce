### Production hooks (moved from AGENTS.md §2.3)

- **NEVER rotate the Supabase DB password with `ALTER ROLE`** — dashboard only. `28P01` is a stale password, `XX000` a wrong host.
- 🔴 **`delete from storage.objects` IS REFUSED — `storage.protect_delete()` raises `42501` "Use the Storage API instead", so a cleanup script that names that table CANNOT WORK and takes its whole transaction down with it.** Measured 2026-10-08: the statement had sat in `docs/agents-owner-rules.md` for five days as the documented way to clear a storage row, and running it rolled back the four valid deletes beside it. Go through `DELETE /storage/v1/object/<bucket>/<path>` with the service-role key — that removes the file and its row together and answers `200 {"message":"Successfully deleted"}`. A `select` on `storage.objects` is fine, and that is how you find the path to pass.
- 🔴 **`supabase-production` DECLINES DESTRUCTIVE SQL ON PRODUCTION — a `drop function`, a `delete` — AND THE ACCOUNT CONNECTOR `mcp__b345e47e-…` RUNS THE SAME STATEMENT.** Measured on the identical SQL twice: `{"status":"declined"}` on 2026-10-03 and again 2026-10-07, `{"success":true}` through the connector the owner allowed on 2026-10-05 (AGENTS.md §8 pre-authorizes both). A decline is that server's own guardrail, **never the owner's decision and never evidence the change is forbidden** — try the other door, announce the change first, then verify live and attribute by `schema_migrations.statements` (`a-declined-tool-call-is-not-proof-the-change-did-not-land`). 🔴 **And never leave "this is not applied" written in a migration header as the plan**: `20261003075838` said exactly that, nothing watched the sentence, and its two functions sat on production for four days as the only two `function_search_path_mutable` advisor findings. Account: `docs/agents-owner-rules.md`, "What the probe left behind, and why".

### Retention

- 🔒 **RETENTION IS THE OWNER'S DECISION, SET 2026-10-04: `audit_logs` 12 months, `email_delivery_events` 6 months, `attendance_raw_punches` 12 months — nothing else is pruned.** `public.phx_prune_retention()` deletes past those ages in 5,000-row batches; pg_cron job `phoenix-data-retention` runs it daily at 01:40 UTC (production only — staging has no pg_cron). Change a period by editing that ONE function in a new migration, only on his word; never add a table to it on your own. Migration `20261004041000_perf_review_indexes_and_data_retention.sql`.
