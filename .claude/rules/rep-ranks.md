- 🔒 **PHOENIX RANKS READS PHOENIX CRM ONLY — NEVER iREPORTS360, THE KPIs BOARD OR EARLY BIRDS** (owner, 2026-10-05: *"all data in phoenix crm not ever any data from old crm"*). One board for every rep of every line, TWELVE equal measures plus a start bonus, no sales: AM and PM call rate (Phoenix CRM's locked 2 and 10, two pillars, never averaged), coverage and frequency (monthly ideas prorated to any window's working days), sticking to plan (`phoenix_crm_report_plan_vs_actual`), AM start as a BONUS of up to 5 points that pressing can only add (owner: *"give it a bonus, but do not make it zero"*), days in the field, field accuracy — and, added the same evening at the same weight (owner: *"each worth the same as the first seven"*), time between visits, products per visit, visit notes, GPS precision and integrity. Time between visits is the owner's own model: walking time at 5 km/h over the straight line × 1.3 (NOT a map API — `geo.ts` records "never buy a map API"), plus 10–30 minutes waiting and 5–10 minutes in the visit; a gap inside that band is 100. It reads `captured_at`, which is the SAVE time, so a rep who saves in batches scores low on it — his decision, knowingly. Leave and holidays come out of the owed days. `src/lib/rep-ranks/`, pinned by `tests/rep-ranks.test.ts`. Account: `docs/agents-owner-rules.md`, "Phoenix Ranks".
- 🔒 **EVERY REP SEES EVERY REP'S WHOLE BREAKDOWN — BUT FIELD ACCURACY IS ONE SCORE, AND THE METRICS NEVER LEAVE THE SERVER FOR A PORTAL** (owner, 2026-10-05: *"for the reps, only accuracy score … the metrics keep in your back end or show it to the admin account"*). `read.ts`'s `PORTAL_COLUMNS` never selects `metrics`; only `/admin/ranks` reads it. **Integrity is IN the score as ONE number, the detail admin-only** (owner, 2026-10-05: *"In the score, admin sees detail"* — this replaced "the detectors stay out of the score"): each save carrying a strong location flag (mock provider, replay, impossible travel, zero jitter) costs 5 times its share; a fix past Phoenix CRM's own coarse line (`COARSE_ACCURACY_METERS`, 500 m) never counts the precision flags (`PHOENIX_CRM_PRECISION_INTEGRITY_FLAGS`), because Android's approximate location raises them by itself. 🔴 **AND A CASE THE SUPER ADMIN HAS SETTLED ON THE INTEGRITY BOARD COSTS THE RANK NOTHING** (owner, 2026-10-09: *"make settling drop the rep-ranks penalty too"*) — `rankCountedFlags` is the ONE function that decides, so `compute.ts` must never call `countedIntegrityFlags` directly, and the read must select all four `settled_*` columns, because the test is `settled_flags = flags`: a column against a column, which PostgREST cannot ask for and `settled_at is null` would get wrong. A fresh finding replaces `flags` in place, so the penalty returns on the next nightly pass with no filer taught that settling exists; ranks are rebuilt nightly, so a settlement never retro-rewrites a closed window. Duplicate photos stay out. The rep's page and certificate never name a check. Never add a distance, a flag or a count to a portal answer. Accounts: `docs/agents-owner-rules.md` ("Phoenix Ranks") and `docs/phoenix-crm-integrity-settlement.md` ("And the rank, from 2026-10-09", and the behaviour gate he ruled on the same evening — all four readers of that table now drop a settled case).
- 🔒 **"TIME BETWEEN VISITS" IS DELIBERATELY NOT A PILLAR** — `captured_at` is the SAVE time, not the arrival (phoenix-crm-boards), so a gap between saves would rank batch-savers, not field work. Re-propose it only with a real arrival clock.
- 🔴 **A STRONG CASE AGAINST A PLACE THE REP VALIDATED COSTS THE INTEGRITY PILLAR TOO — in the NUMERATOR only, never the denominator** (audit, 2026-10-12; his condition met the same day: *"Count place cases, and tell me who moves"*). The pillar read `subject_kind = "visit"` alone, so `signboard` and `capture_trust`, which file ONLY against places, were silent in Phoenix Ranks for their whole lives: a rep whose validation evidence did not hold up kept a clean score while a rep flagged on one visit lost marks. It is a SECOND read keyed by REP (`readIntegrityPlaceCases`) — a place case has no visit for `readFieldSaves` to join to, so widening the filter would key on a place id matching no save and drop silently — and a validation is not a save, so counting it in both halves would let a flagged place IMPROVE a low-volume rep's ratio. Settlements and the coarse-accuracy rule apply exactly as on a visit case (`rankCountedFlags`). 🔴 **The penalty is five saves' worth per case, so a DAY window is a cliff and a rep with very few saves clamps to 0** — the pillar's existing design, not this change. 🔴 **It counted NOTHING on production until the rep key was fixed the same night** — the reader upper-cased `rep_hr_id` while every other index keys on `keyOf`, so the measurement that moved 7 reps was taken BESIDE the pipeline, never through it (next line). Accounts: `docs/phoenix-crm-integrity-settlement.md` §5, `docs/rep-ranks-place-case-rep-key.md`.
- 🔴 **EVERY PER-REP KEY IN PHOENIX RANKS GOES THROUGH `keyOf` — an upper-cased raw `rep_hr_id` matches NO rep on the roster, and drops in silence** (2026-10-12). The roster, the field saves and the starts are keyed by `normalizeHrIdForAccess` (lower case, every dash stripped: `ai0020`, `b170`); the place-case reader built `AI-0020` instead, so the widened Integrity pillar emitted a row per case and added it to nobody — 9 live cases, 0 score changes, nothing thrown. 🔴 **A fixture with canonical keys can never catch this**, which is why `tests/rep-ranks.test.ts` now pins every `const repKey =` in `compute.ts` to `keyOf(` in source. Measure a per-rep read by joining it to the roster before believing its effect. Account: `docs/rep-ranks-place-case-rep-key.md`.

- 🔴 **A CASE A LATER READING HAS WITHDRAWN COSTS THE PILLAR NOTHING — the board drops it, so `readIntegrityPlaceCases` must too** (2026-10-13). A withdrawn signboard case has **no settle button by design** (nobody is left to decide it), so reading the integrity table alone charged a rep five saves' worth for a finding his own evidence had overturned, with no click anywhere that could clear it. Ask the board's pure rule `judgeLaterSignboardReading` about the place's CURRENT `signboard_check`, and drop on **`withdrawsFlag`, never `!supportsFlag`** — an unreadable re-read answers nothing and leaves the case standing. The place read fails towards CHARGING, so the two screens still agree. Three live cases, three reps — Nada Saied 85→90, Esraa fotooh and Ahmed Farag both to 100 — none of whom had seen it, the nightly publishing at 04:17. Account: `docs/phoenix-crm-integrity-settlement.md` §9.
- 🔴 **THE RANKS BOARD DRAWS EACH INSIGNIA ONCE — `RankInsigniaSprite` at the top of the board, every badge a `<use>` into it — AND THE BOARD AND THE PROFILES ARE REMEMBERED FOR AN HOUR UNDER `REP_RANKS_CACHE_TAG`, WHICH `rebuildWindows` DROPS** (2 Nov 2026, the speed root cause, Stage 2: 64 badges each carrying the 21 KB eagle made the page 2.8 MB of HTML, and every open read ~3,000 standings rows). The sprite is hidden by size, never `display: none`; a page that renders a badge outside the board must render the sprite too. The cache key carries kind, window and AUDIENCE, so the admin twin's metrics never reach a portal entry. Pinned by `tests/phoenix-crm-territory-bundle.test.ts`.
