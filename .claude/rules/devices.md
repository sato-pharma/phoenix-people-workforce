## Rules

- 🔒 **A new rep tablet enters Device Custody only when a PERSON confirms it — neither the Headwind fleet read nor the Google "Rep tablets" page ever auto-registers** (owner, 2026-10-22). `getHeadwindFleet` and `getRepTabletsState` only COUNT unregistered tablets (`pendingRegistration`); a Super Admin adds each one — `POST /api/devices/headwind/register` (`registerOneHeadwindTablet`) or the USB register on the Google page — audited. Never restore the auto-create. ManageEngine's auto-register is gone with the rest of its code, deleted on 2026-10-23 (last copy: commit `78a9f90ba`); never bring the bridge back. Account: `docs/devices/headwind-rustdesk.md` §8.11.
- 🔴 **A whole-configuration PUT to Headwind must carry the app links — the by-id read returns `applications: []` and the PUT deletes every link it is not sent.** Read them from `/rest/private/configurations/applications/{id}` and send `action !== 0` (`configurationWriteBody`); a bare `{ ...current, ...patch }` takes every app, and the home-screen app, off every tablet on those rules. Account: `docs/devices/headwind-rustdesk.md` §8.14.
- 🔴 **Linking one app to a configuration must send the existing link's `id` — an entry without one adds a SECOND link row beside the old one** (production, 2026-10-23: Telegram, WPS Office and WhatsApp each ended on "Rep tablets" twice, a remove and an install). `writeHeadwindAppLink` reads `/rest/private/applications/configurations/{applicationId}` first; `applicationLinkEntries` updates the lowest existing id, sends any other link for that pair with `action: 0` (which deletes it), and only a pair with no link goes without an id. Account: `docs/devices/headwind-rustdesk.md` §8.15.
- 🔴 **"Reset the screen lock" sends a one-time six-digit PIN in `password` — `passwordReset: true` alone reaches the tablet as null and does nothing.** The PIN is shown once in the reply and never audited. Account: `docs/devices/headwind-rustdesk.md` §8.7.
- 🔴 **The tablet server refuses its two public uploads at Tomcat — `/rest/public/applications/upload` and `/rest/videos` — and the rule lives at HOST level.** `rewrite.config` + `RewriteCheck.java` in `infra/headwind-phoenix-actions/` (2026-10-22): `ROOT.xml` is regenerated at every start, `server.xml` is not, and a rule Tomcat cannot parse fails the build, never the start (Railway calls a dead Host green). Verify 403 on all three hosts after the `phoenix-headwind` redeploy; never test with a real upload. The console still answers on every name until the `mdm-console` split. Account: `docs/devices/headwind-rustdesk.md` §8.3, §8.10.
- 🔒 **Every Headwind add-on endpoint lives under `/private/` or `/public/` AND under a filter `PhoenixRestModule` registers** (2026-10-22). The full path is the class `@Path` joined to the method `@Path`; a method written as `@Path("/status")`, a verb on the bare class path, or a resource bound without a filter entry serves with no login. `runPluginPathTests` in `tests/headwind-bridge.test.ts` reads both halves as Jersey does and refuses it — fix the path, never the test. Account: `docs/devices/headwind-rustdesk.md` §6.1.
- 🔒 **`mdm.satopharma.com` serves ONLY the tablet agent's paths; the console, the token endpoint and the private API answer only on `mdm-console`, whose requests the add-on checks for a Cloudflare Access pass** (owner, 2026-10-22). Tomcat rewrite patterns match the WHOLE path, so write `(/.*)?$`, never a prefix. Phoenix's `HEADWIND_MDM_BASE_URL` must move to `mdm-console` BEFORE the split deploys. Account: `docs/devices/headwind-rustdesk.md` §8.3, §8.10.
- 🔴 **Headwind 2FA is UNAVAILABLE in this build — its console UI is hard-disabled upstream (`ng-if="false"`), so never put "enable 2FA" to the owner as a click; Cloudflare Access on `mdm-console` is the console's only second factor** (verified 2026-10-22 against upstream `h-mdm/hmdm-server`).
