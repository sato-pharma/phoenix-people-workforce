## Rules

🔴 **`employees.md` (the joiner's HR lifecycle) and `notifications.md` (email delivery) load BESIDE
this file, not instead of it** — this module's globs add to theirs. The four rules below were filed
under `employees` on 2026-10-02, before this module existed; they are the CONSOLE's rules, so the
leaver side needs them too, and they moved here the same day rather than being copied.

- 🔴 **TURBIFY HAS NO AUTHENTICATOR-APP 2FA — its only second factors are a code to a mobile or to an email address** (its own help, SLN29023, read 2026-10-02). There is no TOTP secret to hold, so unattended console automation needs two-step verification OFF on the admin account, which it is. A session told to make this robot unattended reaches for TOTP because that is the right answer nearly everywhere else; it was built here, proved against RFC 6238, and then deleted unused. **Check the platform before building the second factor.**
- 🔴 **AN APP PASSWORD SURVIVES A LATER PASSWORD CHANGE, and that one fact decides two opposite things.** It is why resetting a leaver's password does NOT revoke their mailbox (`a-password-reset-does-not-revoke-a-turbify-mailbox` — delete the app passwords or suspend it), and equally why adopting a joiner's existing mailbox is safe: once Phoenix holds its app password the employee can change their own password immediately and Phoenix keeps working. Never reason from one half without the other.
- 🔴 **THE CONSOLE'S SEARCH IS A SUBSTRING MATCH, SO "EXACTLY ONE ROW" MUST BE AN IDENTITY CHECK AND NEVER A COUNT.** Every one of the 288 rows carries the same `aria-label="Reset password"`, so a first-match click resets the WRONG employee — and filtering does not fix it: searching `el.sayed@satopharma.com` returns the single ACTIVE row for `adel.sayed@satopharma.com`, with its own Reset password button, so a count answered "safe to click" and the leaver driver's `includes()` dialog check then confirmed the wrong reset as the right one (2026-10-03). Use `rowIdentityRefusal`, `readExistenceFromRows` and `dialogNamesAddress` in `src/lib/turbify/resolve.ts`; `rowCountRefusal` and `readExistence` were DELETED so nobody reaches for them. 🔴 **And only the FIRST search after a page load actually filters** — a second search in the same page answers from the previous one, which once reported 34 of 35 addresses absent when 28 existed. One page load per address, with a positive control. Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **ADOPTION NEVER RUNS ON A SCHEDULE** — it resets a mailbox somebody reads every day, so its only caller is the Super-Admin-only route behind the New Hire Mailboxes card, and `tests/new-hire-mailbox-adopt.test.ts` fails if a cron route or the sweep so much as names it. Wiring it into the daily sweep is the obvious-looking way to "finish the remaining mailboxes" and would lock people out overnight with nobody told. The joiner robot is the scheduled one, because a mailbox it has just created belongs to nobody yet.
- 🔴 **A COORDINATE CLICK THAT REPORTS SUCCESS IS NOT EVIDENCE THE CONTROL WAS CLICKED** (measured in the production container, 2026-10-02). The joiner ran at puppeteer's default 800×600 with no viewport set; the console's cookie banner — fixed, `z-index: 99999`, 188px — covered everything below y=412, the "Email user" button sat at y=430, and `handle.click()` hit the banner, reported no error, and failed a later step naming an innocent selector. Every click now hit-tests with `document.elementFromPoint` first and re-delivers on the node when covered (`src/lib/turbify/click-delivery.ts`), failing open.
- 🔴 **`handle.type()` APPENDS, and the driver reuses one page per candidate** — the search box once read `adel.srour@satopharma.comasmaa.zaghloul@satopharma.com`. That is worse than a bad search: `createMailbox`'s "does this address already exist?" check reads the filtered page, so it can answer about a string nobody searched for. Clear the field before typing, and treat an existence answer as belonging to the address you can prove is in the box.

- 🔴 **A MAILBOX TURBIFY CREATES LANDS IN `Pending`, AND `Active mailboxes` DOES NOT COUNT IT — so "the count did not move" is NOT proof nothing was created.** Create does not behave like reset: it makes the mailbox Pending and hands the password over by INVITATION, never through the `One-time password` dialog a reset opens, so the robot threw and reported `provisioned: 0` while `ahmed.mohamed@` and `asmaa.zaghloul@` really existed (2026-10-03). A Pending row carries NO `Reset password` button, so counting those reports it absent, and its address must be read from its OWN cell — the display name runs straight into it, so the row's text parses as `Abd-Elnaimahmed.mohamed@satopharma.com`. The post-save view offers `send invite` and `print`; **print** is what still needs calibrating. Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **`textContent` GLUES THIS CONSOLE'S LABELS TOGETHER WITH NO SEPARATOR, AND IT HAS NOW HIDDEN AN ADDRESS TWICE — read an element's OWN text, or put the boundary back.** First the display name ran into the address in a table row (`Abd-Elnaimahmed.mohamed@satopharma.com`), fixed by reading the address from its own cell; then the `One-time password` dialog ran the address into the NEXT LABEL (`Email account:hr.mailbox@satopharma.comOne-time password: …`), so the only `@`-bearing token was `hr.mailbox@satopharma.comone-time`, neither the address nor its local part survived, and the owner was told the dialog "belongs to a different mailbox" about his own mailbox (2026-10-03). `dialogNamesAddress` now splits at a lowercase→uppercase transition, which is where the glue always falls because what follows is the next label's capitalised first word — **and that can only ever SPLIT a token, so it cannot turn a near miss into a match**, which is what keeps the substring rule above intact (`adel.sayed@…comOne-time` still yields `adel.sayed@…com`, still ≠ `el.sayed@…com`). Both directions are pinned with the real dialog as the fixture. 🔴 **And the LEAVER driver held a SECOND COPY of that tokenisation, with the same defect** — it lowercased before splitting too, so the first live leaver reset would have refused itself exactly the same way, on a path nobody had run yet. It calls `dialogNamesAddress` now, and `tests/mailbox-offboarding-robot.test.ts` refuses a re-implementation: two copies is how one fix lands on one path and leaves the other broken. Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **A STEP THAT CLICKS BEFORE IT READS CAN ONLY EVER REPORT "MAY HAVE" — arm the damage flag BEFORE the call, never after it.** `resetAndCapture` clicks Reset and then reads the dialog, so a failure while reading exists *because* Turbify already reset the mailbox — and `invite-inbox-runner.ts`, arming its flag after the call returned, told the owner `hr.mailbox@satopharma.com was not reset` about a mailbox that had been (2026-10-03). He went looking for the wrong problem, and the outstanding one-time password went unmentioned. The flag is `mayBeReset` now: it may only OVERSTATE the damage, which is the right way round for a mailbox Phoenix owns, and a test asserts a reset-step failure can never report the mailbox untouched.
- 🔴 **THERE ARE TWO TURBIFY LOGIN PAGES AND THEIR EMAIL FIELDS SHARE NO SELECTOR — `login.turbify.com` renders `input[type="email"]`, `mail.turbify.com` renders `input#email[name="email"][type="text"]` and ZERO `type="email"` inputs.** `MAILBOX_LOGIN_URL` is a login.turbify.com URL whose `.done` points at mail, and Turbify REDIRECTS it to the “Bizmail Login” page — so `setMailboxPassword` sat out its full 45-second wait for a field that page does not have, every time, and the adoption died there AFTER the reset had happened: the owner's click simply span, twice, each run leaving another outstanding one-time password (2026-10-03). Use `MAILBOX_EMAIL_FIELD`, the union of both shapes; neither page carries the other's field, so it cannot select the wrong input. 🔴 **AND A SIGN-IN PROOF ASKS WHETHER WE LEFT THE FORM, NEVER WHICH HOST WE ARE ON** — the old proof read `!url.includes("login.turbify.com")`, and the page it lands on is `mail.turbify.com/login`, so a REFUSED login satisfied it and a wrong one-time password would have been reported as signed in. 🔴 **AND NO URL CAN ANSWER IT EITHER — a GOOD one-time password lands on “Set up your mailbox password” at the SAME url AND the same title as the form it came from** (`https://mail.turbify.com/login`, inputs `password` + `confirmPassword`, submit **“Generate mailbox password”**). So the host check accepted a refusal and the `/login` path check that replaced it rejected a success — two wrong answers from one mistake, three dead clicks for the owner. The discriminator is the FORM: **the setup page has no address field, a refused login still asks for one.** And `CHANGE_PASSWORD_WORDINGS` held four guesses, none of which was the real button, so that step would have failed the moment the sign-in started working — the measured wording goes FIRST. Both pinned by `tests/new-hire-mailbox-robot.test.ts`. Account: `docs/mailbox-robot-calibration.md`.
- 🔴 **IN-PAGE CODE IS A REAL FUNCTION, NEVER A STRING — in the driver and in a throwaway probe alike.** A string crosses the template-literal and shell-heredoc layers and arrives changed: one lost a backslash, turning `/\s+/g` into `/s+/g`, which replaced every literal `s` and made the console's `Email user` button read `Email u er` — read for an hour as a Turbify rendering bug, when the page's bytes spell `Email user`. An earlier one passed in-page code to `page.evaluate(expr, handle)`, which never binds the handle, so every click became a silent no-op that reported success. `readMailboxRowCells`, `readHitTest`, `clickNode` and `clearField` are real exported functions, unit-tested against fake elements. Account: `docs/mailbox-robot-calibration.md`.

- 🔴 **THE NEW HIRE'S ADDRESS IS THE ONE THE OWNER TYPES, AND NOTHING DERIVES ONE** (owner, 2026-10-03). The generator that built `first.second` from the name turned "El Sayed Rady" into `el.sayed@satopharma.com` — his first name is **Elsayed**, one word — and the robot created that mailbox on the live domain before anyone read the register; undoing it took a console deletion. The Employee Master now types the local part against a fixed, greyed `@satopharma.com`; `openNewHireMailboxTasks` stores the typed company address **or null**; and `loadJoinerCandidates` SKIPS a task with no address so the robot waits a sweep rather than inventing one. `mailboxAddressCandidates` and `proposeMailboxAddress` are DELETED and pinned absent. Account: `docs/mailbox-robot-calibration.md`.

- 🔴 **TURBIFY'S CREATE HANDS BACK NO PASSWORD — IT EMAILS A `Temp Password:` LINE, AND THAT EMAIL IS THE ONLY CREDENTIAL THE MAILBOX EVER HAS** (measured 2026-10-03). The `One-time password` dialog belongs to the RESET path only, so a create that waits for it strands the mailbox `Pending` for ever — three real ones, while the sweep reported `provisioned: 0`, because `TURBIFY_INVITE_RECIPIENT` was `""` and the email went nowhere. It is now `hr.mailbox@satopharma.com`, a mailbox Phoenix owns and reads, kept as a CONSTANT because `railway variables --set` bypasses the CI deploy gate. `readInvitation` matches the invitation to its mailbox by IDENTITY — one inbox receives every hire's, and `adel.sayed@` contains `el.sayed@` — refuses on a changed label instead of guessing, never reads the body's own `*Password:* {The password you create...}` help line, and never quotes the credential in a refusal. Account: `docs/mailbox-robot-calibration.md`.

- 🔴 **ADOPTING THE INVITE INBOX RUNS A PASSWORD RESET, SO ITS ADDRESS IS COMPARED AND NEVER CHOSEN** — `evaluateInviteInboxAdoption` matches `TURBIFY_INVITE_RECIPIENT` by identity, the route passes the constant rather than the request body, and the card has no address field; the same chain pointed at an employee locks them out of their mail with nobody told. No `force`/`override` parameter, ever — that is how a reset-ONE flow becomes a reset-ANY flow. A missing company password is refused BEFORE the reset, because a reset with nothing set afterwards leaves the mailbox unreachable. 🔴 **And `addMonitor` is what proves it**: it runs `testMailboxConnection` and refuses a credential that cannot open the mailbox, so `adopted` means a real IMAP login succeeded — not that a password was typed and assumed to work. Never scheduled (it would reset the inbox mid-read). Account: `docs/mailbox-robot-calibration.md`.
