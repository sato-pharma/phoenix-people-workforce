## Rules

- 🔴 **AN APK HEADWIND HAS INSTALLED IS NOT AN APP THAT HAS RUN — application 98's `runAfterInstall` was false, so Phoenix Position landed on two tablets and nothing ever started it** (production, 26 Nov 2026: 1.0.0 installed on PHX-TAB-0007 and PHX-TAB-0008, both checked in that morning, `device_position_agents` **0 rows**). The agent shows the rep nothing, so nobody can open it, and Android keeps a never-run app in the **stopped** state where not even `BOOT_COMPLETED` arrives. `setHeadwindAppRunAfterInstall` (now sent on every upload, false included) governs the NEXT install only; a tablet already holding the APK needs Headwind's own `runApp` push — `startPositionAgentOnTablet`, job `start-tablet-agent`, which refuses a tablet whose app list lacks the agent and says "could not be read" for an empty list. 🔴 **Start them ONE AT A TIME** — two identical Lenovos give identical introductions, so bind each new install before pushing the next. Account: `docs/devices/headwind-rustdesk.md` §8.20.
- 🔴 **THE FULLEST TRAIL IS THE ONE THE TABLET UPLOADS ITSELF, AND OUR OWN ADD-ON RECEIVES IT SINCE 26 NOV 2026 — the free server answered those uploads 404, so every tablet threw its own record away after a day.** From 6.41 the launcher PUTs its stored fixes to the premium plugin's path `/rest/plugins/devicelocations/public/update/{number}` and deletes them only on a 2xx (measured 404 for PHX-TAB-0008 at 02:13 and 02:14 Cairo) — that, not the launcher, is why the `deviceinfo` history has never held one row. `DeviceLocationsResource` + `PhoenixLocationStore` keep them in `phoenix_device_locations` (`recorded_at_ms` is the tablet's own epoch milliseconds, NEVER a `timestamp`), and Phoenix reads them back FIRST as source `"upload"`, which outranks the plugin and the check-in on the trail line. A 404 on that read means this server has no receiver and must be rebuilt with the Phoenix image; anything else is "could not be read", never an empty history. Supersedes the "red herring" line in `headwind-location-never-registered-gps-provider`. Account: `docs/devices/headwind-rustdesk.md` §8.19.
- 🔴 **AN INSTALL IS NOT A TABLET — THE REP TABLETS' OWN PHOENIX POSITION APP ENROLS ITSELF AND LANDS UNBOUND, AND A PERSON SAYS WHOSE IT IS** (owner, 26 Nov 2026: "Build the app", after "both"). The app posts straight to Phoenix (`POST /api/devices/positions/hello` mints a token ONCE and stores only its SHA-256; `POST /api/devices/positions` takes a Bearer and a batch), so the trail survives the tablet server being down. 🔴 A SECOND HELLO FOR A KNOWN INSTALL MINTS NOTHING, and an unknown install and a wrong token answer the SAME 401 — a Headwind configuration is world-readable, so nothing long-lived may be provisioned into the app and no answer may say which install ids exist. The app shows the rep nothing and asks nothing (the golden rule), so binding is three owner-ops jobs — `tablet-agents`, `bind-tablet-agent`, `revoke-tablet-agent` — behind `company_devices / approve` and audited as `tablet_position_agent`. 🔴 **THE BIND BACK-STAMPS THE FIXES THAT INSTALL ALREADY SENT**, or the days before anybody claimed it read as a tablet that never moved; one LIVE install per tablet (a partial unique index), and a reset tablet is revoked and its new install bound. On the movements read the agent is source `"agent"`, drawn FIRST of the four (agent → upload → plugin → check-in). Account: `docs/devices/headwind-rustdesk.md` §8.20; recipe: `docs/owner-operations-recipes.md`, "Rep tablets".
- 🔴 **The deviceinfo location history is asked for by `deviceNumber` — `deviceFilter` is refused with `error.notfound.device` inside an HTTP 200, and the read's catch turned that refusal into an empty trail** (measured on the live server, 1 Nov 2026). `getHeadwindLocationHistory` in `src/lib/devices/headwind/locations.ts`; pinned in `tests/headwind-bridge.test.ts`. An OK reply with zero rows is still not proof the filter matches a real row — no tablet had ever sent a fix when this was found.
- 🔴 **A POSITION IS NEVER SHOWN WITHOUT ITS OWN TIME, AND NOTHING THE TABLET DID NOT SAY IS SAID** (9 Nov 2026, the location audit). `locatedAt` is the fix's own time, never the check-in's (`lastContactAt` made a days-old fix read "less than two minutes old" after a Locate-now wake); a 0/0 pair is no fix; a number not in the fleet throws `HeadwindDeviceNotFoundError`; a history-plugin refusal is printed word for word, never an empty trail; the history has NO sort field (the server orders `ts DESC`); repeated identical reports fold into one row; a trail line is ONE source and timed fixes only; a fleet pin older than `TABLET_NO_FIX_LIMIT_HOURS` or undated is faded; "never fixed" is decided by coordinates. 🔴 Reading movements NEVER writes a server setting — switching history on is the audited POST `action: "location-history-on"`. All pinned in `tests/headwind-bridge.test.ts` (`runLocationHonestyTests`).
