# Phoenix CRM — the door's name key, the place cap, the unmeasured fix, and who was on the visit

The account of **Phase 2** of the second-pass CRM audit (3–11 Oct 2026). Phase 1 — the four readers
of `phoenix_crm_location_integrity` — is §5 of
[phoenix-crm-integrity-settlement.md](phoenix-crm-integrity-settlement.md); this file picks up at the
gaps that are not about that table.

Five gaps were examined. **Three were real defects — one of them a live finding the owner ruled on
the same day — and two were not: one was already shipped, and one is a deliberate behaviour that a
test had pinned in words, so the change written for it was reverted.** Everything measured here was
read against the production project `ozucdzovmcqvepbozvqf` on 2026-10-12, read-only except for the two
migrations this file describes.

🔴 **Two of the five went the audit's way and three did not, which is the main finding.** An audit
line saying "X is not checked" is a claim about intent as much as about code, and in this module the
intent is usually written down — in an owner rule, or in a test that quotes one. Read the pin before
believing the gap.

---

## D5 · Gap 12 — the door and the rename still compared `lower()`

The bulk loader and the SFE's move have folded the customer name since 2026-10-05
(`phoenix_crm_fold_name`), under the owner's rule *"ONE CUSTOMER, ONE NAME KEY — THE LOADER FOLDS THE
NAME, IT DOES NOT `lower()` IT"*. That rule was written about the **loader**, and the loader was the
only thing the change touched. The two places a rep's own phone creates or renames a customer —
`phoenix_crm_validate_customer` and `phoenix_crm_rename_customer` — went on comparing
`lower(c.name) = lower(v_name)`. So the system still disagreed with itself about what one customer
is; the disagreement had simply moved one door further in.

**Measured inside the door's own scope** (seat + `is_test` + `list_type` + `active`/`pending`/
`outside`, 12,272 customers):

| | |
| --- | --- |
| fold-groups already holding more than one live row | **183** |
| of those, groups the fold catches and `lower()` could not | **7** (9 rows) |
| what every one of those 7 is | the same doctor — a `د.` honorific, or أ/إ/ى against ا/ي |

`lower()` could never have seen any of the seven: they differ in the characters the fold normalises
and `lower()` leaves alone.

**The four fences on the remedy, all the owner's, and all asserted rather than trusted**
(`tests/phoenix-crm-customer-name-fold.test.ts`, which already pinned the loader's half):

1. **It only ever SKIPS.** The folded hit raises the existing `phoenix_crm:same_name`. Nothing
   merges, deletes, renames or overwrites a customer.
2. **No unique index.** 183 live fold-groups could not satisfy one.
3. **Never widened past the seat.** 594 of 624 production pairs straddle two lines and are correct.
4. **Never `identityNameKey`**, which collapses محمود onto محمد.

One detail the fold's own header forces: it returns `''` for a name that folds away to nothing, and
`''` is never a key — comparing it would collide every such row onto one customer. Both functions
therefore skip the check when `v_name_key = ''`, which is how the loader reads it. In
`validate_customer` the key is computed in the **body**, not the `declare` block, because `v_name`
there has no initialiser; in `rename_customer` `v_name` is initialised above it, so the declaration
may read it.

## D6 · Gap 20's real defect — the five-place cap had a hole

The audit said "one customer can hold two live places". That is by design: up to **five** are
allowed. But the cap lived only in `phoenix_crm_add_place`, and `phoenix_crm_validate_customer`
calls `phoenix_crm_insert_place` **directly** — so validating a listed customer who already held
five clinics added a sixth. Nothing pinned its absence, and the comment on the retired `restore`
mode had been saying *"outside the five-clinic cap"* about exactly this shape since 2026-10-02.

**Not exploited.** 1,203 customers hold a live place; the most on any one is **2**, and nothing is at
or over the cap. This is prevention.

The check is lifted from `add_place` **verbatim**, including the error name, and sits before the
insert — a cap checked afterwards is not a cap. The error name is the half that matters:
`src/lib/phoenix-crm/server/db.ts` already answers `phoenix_crm:too_many_places` with a 409 and the
sentence *"A customer can have at most five places."*, and `list-screens.tsx` already handles it, so
the rep reads an explanation rather than an unexplained failure. A new error code would have cost
that for nothing.

Both functions are reproduced in full in
`supabase/migrations/20261012090000_phoenix_crm_door_name_fold_and_place_cap.sql`, generated by
copying the live blocks out of the migrations that last defined them (`20261003130536` and
`20260930235705`) and applying only the substitutions above — the `validate_customer` block alone is
12,102 characters, and a transcription slip in a `security definer` function that writes the customer
list is the worst kind of silent change.

**One thing a regenerated function file must carry that the generator will not think of.**
`check:migrations` is a required step of `validate`, and it refuses a migration that creates a public
`security definer` function without revoking EXECUTE **from PUBLIC** — `anon` and `authenticated`
inherit it through PUBLIC membership, so revoking only those two is a no-op. The first push of this
file was red for exactly that. Nothing was ever exposed: `create or replace function` **preserves the
existing ACL**, and `pg_proc.proacl` on production reads `service_role=X/postgres` for all three
functions and nothing for PUBLIC, `anon` or `authenticated` — so the four restated statements are a
no-op against the live database and exist so the file is true standing alone.

## D7 · Gap 15 — NOT a defect, and the attempt to "fix" it was reverted

The audit said an unknown accuracy passes the 250 m gate. It does, and that is the **owner's
decision**: *"An UNKNOWN accuracy is still taken, as it always was"* (`entry-rules.ts`, pinned at
`tests/phoenix-crm-accuracy-gate.test.ts`). The gate was never in question.

What looked like a residue one line further on was not one. `isCoarse` in `location-integrity.ts`
requires a **non-null** accuracy, so a fix whose phone reported no accuracy at all is not suppressed
from the four precision detectors: it is taken as unmeasured at the capture gate and still judged on
its coordinates afterwards. That reads like the two halves disagreeing about one null — and the
reasoning for widening the suppression was written out in full before anything was changed.

🔴 **It is deliberate, and it was already pinned.** `tests/phoenix-crm-location-integrity.test.ts`
has said so in words since the detector was built:

> A fix that never reported an accuracy is "not asked", never "coarse" — the same reading the mock
> flag gets. **An older build that sends no accuracy must keep being judged as before.**
>
> `assert.ok(silent.flags.includes("coordinate_replay"), "and it is still judged on its coordinates");`

The change was written, pushed, and **went red on that assertion** — which is the assertion doing
exactly its job. A null accuracy is treated as *not asked*, not as *too coarse to judge*, and an
older build that sends none keeps being judged on its coordinates; the same reading `mock_provider`
gets. **It was reverted in full** — the detector, the `rep-ranks/field-quality.ts` twin that had to
move with it, and both sets of new assertions.

**Nothing was lost by reverting it.** Of 129 non-test integrity rows, **1** holds an unknown accuracy
and **0** of those carry a precision flag, so the change moved no flag and no rep's score either way.
It bought nothing and contradicted a documented decision.

🔴 **Do not re-chase this.** If the asymmetry is ever to be closed it is the owner's call, not an
audit line's: the behaviour is intended, stated in prose, and pinned by a required check. Satisfying
the audit here would have meant editing that assertion — which is precisely what it exists to catch.

## D8 · Gap 22 — a manager may approve an off-plan visit he was on

The only gap examined with **no owner rule and no test either way**, and the one that turned out to
be a real live finding.

**Measured on production, 4–12 Oct 2026:**

| | |
| --- | --- |
| off-plan visits that carried a companion | 31 |
| of those, decided by that companion | **27** |
| which companion, in every one of the 27 | the **named manager** |
| how many of the 27 went forward | **27 — nothing was refused** |
| managers involved | 8 |
| largest single day | Nermeen Salah, 8 in one day (7 Oct), for Khaled Saied |

It is absent at all three layers: `canDecideUnplannedVisit` is never given the visit,
`decideUnplannedVisit` reads `phoenix_crm_unplanned_visits` joined to the customer only and never
loads `manager_hr_id` / `senior_hr_id` / `product_manager_hr_id`, and the RPC writes `v_actor`
without comparing it. **This is a missing guard, not fraud** — a manager on the ride-along is the
person who actually knows why the rep went, and nothing told him the system had noticed.

**The visibility half.** The read loads the three companion columns and their names, and the decider's
card states *"On the visit: …"* and, where it applies, *"Approved by X, who was on the visit"*. It is
a fact about the visit, it reaches only the decider's Team tab (never a rep's screen —
`tests/phoenix-crm-blind-half.test.ts` sweeps the rep-facing roots), and it changes no step.

### The owner's ruling, 2026-10-12 — the SFE approves it instead

He was asked in plain words, with the measurement above, and chose: **"No — the SFE approves it
instead."** So a manager who was on the visit does not decide it; his step is **unavailable** and the
visit goes straight to the SFE.

**It is the rule already here, not a new one.** A territory whose manager chain is vacant has always
started at the SFE stage, for the same reason: there is nobody at that step who can honestly take it.
So the ruling is one argument on `unplannedFirstStatus` rather than a new stage —

| Layer | What it does |
| --- | --- |
| `unplanned-rules.ts` | `unplannedFirstStatus(hasReviewer, reviewerWasOnTheVisit)`, plus `reviewerWasOnTheVisit`, which compares through `personKey` because these hr ids differ in case and padding between the columns that store them |
| `server/visits.ts` | resolves it at save time, beside the reviewer himself — the only place holding both the organogram's answer and the companions the rep just recorded. The phone never chooses a stage |
| `server/unplanned.ts` | the third fence, and the only one that reads whoever is actually **clicking**: the manager step is refused to a companion, with *"You were on this visit, so SFE decides it rather than you."* |
| `20261012140000_…_offplan_reviewer_on_the_visit.sql` | moves the rows that were **already** waiting |

🔴 **His chain is untouched.** Direct manager, then SFE; one refusal ends it; the Administrator is
not a step and may only refuse. Nothing is flagged, nothing is called fraud, no rep is told anything,
and the manager keeps every other visit she has always decided.

**The four rows that were already waiting, and why a migration was needed.** The application only
chooses a first status as a visit *saves*, so four live rows would have been stranded — the new fence
refuses their manager, and the SFE cannot take a step the row is not at. Measured and moved on
production on 2026-10-12: **4 non-test rows**, all of them Nosiba Salah Hassanin Moussa (District
Sales Manager) on four of Ahmed Mohamed Abd-Elnaim's off-plan visits of 10–11 October. All four now
read `sfe_pending` at `version` 2, and **`manager_decided_at` is still null** — which is the point of
the next paragraph. The 27 already approved were **not** reopened: restating a rep's counted month
would be a far larger act than the gap it closes, and this was never a finding against anybody.

**The one defect this change would otherwise have introduced.** `sfe_pending` is reached two different
ways, and only one of them means a manager approved something — yet `unplannedVisitRepNote` told every
such rep *"Your manager approved it; it counts once SFE does."* On a visit whose manager step was never
available that is a plain untruth about the rep's own visit, and it was **already** wrong for every
vacant-chain visit before this change; the ruling simply multiplies the cases. The note now takes
`managerStepTaken`, read from the row's own `manager_decided_at` (a timestamp, never a name — Golden
Rule #1), and says *"Off the plan. It counts once SFE approves it."* when nobody has taken that step.

**The one window left open, stated rather than hidden.** A visit saved by an older server instance
during the deploy, or one that somehow gains a companion after its approval row was raised, can reach
`manager_pending` in this state. The third fence refuses its manager rather than letting him decide,
which leaves that row waiting; re-running the migration's statement moves it. It is idempotent.

## D9 · Gap 13 — already shipped, and the audit had it wrong

The audit said "Validated by" never names the reviewer. Two things were already true:

1. **The rep's own tree names the REP, deliberately** — *"the customer is validated in the REP's own
   name, never the admin's"*, pinned verbatim at `tests/phoenix-crm-refuse-validation.test.ts:102`.
   Golden Rule #1 and his 2026-10-08 ruling keep any person's name off what a rep receives.
2. **The admin side already prints it.** `phoenix_crm_validation_reviews.decided_by_hr_id` is written
   on both branches, `server/validation-reviews.ts` already selects it and resolves
   `decidedByName`, and the Decided tab of `validation-reviews-board.tsx` renders
   `decidedByName · decidedAtText` at `validation-review-queue.tsx:227`. The route is
   `app/(admin)/admin/field-crm/validation-reviews/`, which is admin-only.

So the plan's own reading — *"the real gap is narrower: no admin-side surface prints it"* — was also
wrong. **Nothing was changed for D9.** It is recorded here as a correction so the next session does
not go looking for a defect that is not there.
