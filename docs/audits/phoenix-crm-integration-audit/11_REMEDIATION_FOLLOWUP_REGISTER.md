## Evidence and impact

### ISS-001 — Outside heartbeat monitoring covers 20 of 49 enabled scheduled jobs

- **Severity:** MEDIUM · **Basis:** VERIFIED LIVE
- **Evidence:** T-HC-01: 20 checks, the free plan's ceiling; T-CJ-01: 49 enabled jobs; src/lib/cron-control/job-schedule.ts:298-319 lists the 20 watched slugs.
- **Impact:** 29 jobs — among them Phoenix Ranks nightly, the CRM integrity sweep, retention sweeps and interview reminders — can stop without any alarm from outside the app. The in-app heartbeat sweep cannot alarm if the app itself is down.
- **Fix:** Keep the 20 most money- and people-critical jobs on Healthchecks; watch the rest with a database-side freshness check that alerts through Telegram, or self-host a checker (INT-068, INT-069).

### ISS-002 — Three daily jobs end in a 30-second scheduler timeout; nine more run within reach of it

- **Severity:** HIGH · **Basis:** VERIFIED LIVE
- **Evidence:** T-CJ-01: mailbox-offboarding-sweep 30,172 ms, reconciliation-check 30,155 ms (job set to 300 s), notify-daily 30,141 ms — all `timeout`; private-calendar-gap-notice 28,987 ms; two sheet-token rotations 16.1 s; their Healthchecks pings still arrive (T-HC-01), so the work finishes after the caller hangs up.
- **Impact:** The scheduler records a failure every day for work that succeeded, hiding real failures. The provider's terms disable a job after more than 25 consecutive failures, which would silently stop the daily notification run. One slow day pushes nine more jobs over the line.
- **Fix:** Make long routes answer 202 at once and finish in the worker, or schedule them from the database with pg_cron + pg_net where no 30 s cap applies (INT-061).

### ISS-003 — Four of ten connection attempts to the production and worker hosts timed out from the audit's network

- **Severity:** MEDIUM · **Basis:** VERIFIED LIVE — single vantage point
- **Evidence:** T-RW-04: 4 of 10 healthz calls got no TCP connection in 15 s; T-RW-05: same on the worker host; T-SB-05: 10 of 10 to the database host answered in the same minute from the same machine.
- **Impact:** Unknown: either a local network path problem or an edge problem real users in Egypt also meet. No outside-in monitor exists to tell which.
- **Fix:** Probe /api/healthz every minute from a second network for a week (INT-066 or INT-067) and compare with client error logs before changing anything.

### ISS-004 — Public sign-up is not disabled at the authentication provider

- **Severity:** MEDIUM · **Basis:** VERIFIED LIVE
- **Evidence:** T-SB-02: signup_disabled=false, e-mail provider on, auto-confirm off. T-SB-19: 79 tables carry a grant to the signed-in role and 11 SECURITY DEFINER helpers are callable by it.
- **Impact:** Anyone holding the project's anon key could create an auth user the app never issued. Row policies should give such a user nothing, but the only barrier is then policy correctness on 79 tables. The anon key is read server-side only today.
- **Fix:** Turn sign-up off in the provider settings; the app creates users through the admin API, which is unaffected.

### ISS-005 — Three public tables have row-level security switched off

- **Severity:** LOW · **Basis:** VERIFIED LIVE
- **Evidence:** T-SB-12, T-SB-19: ats_whatsapp_template_sends, ats_whatsapp_message_templates, business_card_requests have RLS off; none holds a grant to anon, authenticated or public.
- **Impact:** Not reachable through the Data API today. One stray GRANT in a future migration would expose them with no policy behind it.
- **Fix:** Enable RLS on the three tables in a migration (no policy needed — the service role bypasses it).

### ISS-006 — 40 functions are executable by the anonymous role

- **Severity:** LOW · **Basis:** VERIFIED LIVE
- **Evidence:** T-SB-17, T-SB-19: 40 functions, all SECURITY INVOKER; the anonymous role holds no table grant.
- **Impact:** They run with the caller's rights, so they can read nothing today; they are still callable surface that grows with every default grant.
- **Fix:** Revoke EXECUTE from anon and public on the public schema and set default privileges so new functions are not granted.

### ISS-009 — No point-in-time recovery and no rehearsed restore for the payroll database

### ISS-010 — Map key restrictions, quotas and the monthly bill could not be read; one autocomplete path sends no session token

- **Severity:** MEDIUM · **Basis:** FROM CODE — console NOT VERIFIED

- **Impact:** Without a session token each keystroke is billed as its own request. An unrestricted browser key could be used by anyone who reads it from the page.
- **Fix:** Send a session token on every autocomplete path; confirm referrer and API restrictions and a daily quota cap in the Cloud console; cache place_id lookups (storage of place IDs is allowed).

### ISS-011 — Seven outbound call sites have no timeout

### ISS-012 — A production board loads map tiles from the public OpenStreetMap servers

### ISS-013 — The Brevo delivery webhook trusts a shared bearer secret with no signature and no replay window

- **Severity:** MEDIUM · **Basis:** FROM CODE
- **Evidence:** app/api/webhooks/brevo/route.ts:16-23; the provider does not sign payloads. The Sentry alert webhook checks an HMAC but no timestamp (app/api/webhooks/sentry/route.ts:14-18).
- **Impact:** A leaked secret lets anyone forge or replay delivery and bounce events, corrupting delivery records.
- **Fix:** Allow-list the provider's published sender IPs, reject events older than five minutes, and move all inbound hooks to one verification helper (INT-073).

### ISS-014 — Two schedulers call the same five routes, and the notification drain's overlap lock is per process

- **Severity:** MEDIUM · **Basis:** FROM CODE + LIVE
- **Evidence:** .railway/railway.ts:82-84 (curl loop on five routes) and T-CJ-01 (the same routes on cron-job.org); the drain's lock lives in process memory while two services (web, worker) can both run it.
- **Impact:** Two drains can pick the same outbox rows at the same moment; idempotency keys protect Resend sends, other channels rely on row state.
- **Fix:** Name one owner per route; take the lock in the database (advisory lock or a queue with visibility timeouts — INT-062).

### ISS-015 — The server fetches applicant-supplied Drive and Docs links and follows redirects

- **Severity:** HIGH · **Basis:** FROM CODE — NOT VERIFIED (host validation not read)
- **Evidence:** src/lib/recruitment/inbound/cv-link.ts:94-164 downloads a URL taken from a candidate's message with redirect: follow and a 15 s timeout.
- **Impact:** If the host check can be bypassed or a redirect leaves the allow-list, a candidate could make the server request internal addresses (the private Railway network hosts the tablet server and its database).
- **Fix:** Re-check the host after every redirect hop, refuse private and link-local addresses, cap the response size. Verify first — the check may already be strict.

### ISS-016 — The Migration Drift Check has failed five days in a row

- **Impact:** The check that proves production's schema matches the repository is red, so a real drift would not stand out. Its Telegram alarm has been firing daily.
- **Fix:** Record the acknowledged exceptions for migrations applied outside the ledger, and either add policies to the three new tables or raise the baseline with a reason.

### ISS-017 — The Actions cache is at 9.83 GB of its 10 GB limit; 6.8 GB of it is stale code-analysis data

- **Severity:** MEDIUM · **Basis:** VERIFIED LIVE
- **Evidence:** T-GH-05: 94 caches, 9,828,991,924 bytes; two CodeQL overlay databases of 5.1 GB and 1.7 GB left from a set-up that is now switched off.
- **Impact:** At the limit GitHub evicts the newest-needed dependency caches first-come, so every job reinstalls from scratch; the repository's own notes record this slowing every job once before.
- **Fix:** Delete the CodeQL overlay caches; stop caching the package store twice (ISS-049).

### ISS-018 — The CI cost alarm cannot see its budget and reports success
