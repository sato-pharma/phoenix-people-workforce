# Session-level traps — the clusters

**This file is the body of `AGENTS.md` §2.1, moved out of the auto-loaded context on 2026-09-12.**
It is not loaded on every request. `.claude/hooks/trap-injector.mjs` (PreToolUse) matches what a
session is about to run and injects the matching cluster ONCE per session, so the git traps arrive
when you touch git and the ExcelJS traps when you build a workbook — instead of all of them
arriving on every turn. 🔴 **Since 2026-10-08 it injects each bullet's bold HEADLINE only, not the
bullet** (owner's choice, perf plan P2-3: this file had grown to 131 KB, and one `gh pr merge` pasted
46 KB into a single call). So **every bullet must open with a bold sentence that can stand alone as
the cue** — a bullet without one is sent whole, and anything after the bold run reaches a session
only when it reads this file. A session acting on a headline searches here for its words first.

**Each line is a cue, not the fact.** The account of every one — measurements, dates, PR numbers,
the diagnosis traps — is in **[docs/agents-session-traps.md](agents-session-traps.md)**; search it
for the hook's wording. Which memory backs which hook:
[docs/agents-memory-map.md](agents-memory-map.md).

**The heading format is load-bearing.** The injector parses a cluster as a bold run alone on a line
(`**Git**`, `**Worktrees** (see also §5)`) and takes everything up to the next such line. Do not
change a cluster name without changing `RULES` in the hook, and do not introduce a bold-only line
inside a cluster — it starts a new one silently.

**Read this file in full when the injector is not loaded** — a session started before the hook
merged, or any environment with no `.claude/hooks/`. The hook fails open and says nothing when it
does not fire, so its silence is not evidence that no trap applies.

**Shell and tooling**

- 🔴 **A QUOTED HEREDOC HERE COLLAPSES `\\x` INTO `\x`, SO A PYTHON PATCH SCRIPT WRITES THE REAL CONTROL CHARACTER INTO THE FILE INSTEAD OF THE ESCAPE.** Bit three times in one session on 2026-10-09: a `python - <<'PY'` heredoc carrying `\\u0000` reached Python as `\u0000`, which a NON-raw string turns into a NUL — twice into prose in a doc, where the required `validate` job caught it as *no raw NUL bytes in tracked source* after a full 275-second suite, and once into a search pattern, which then matched nothing and read as *the file is not what I just wrote*. **Write every pattern and replacement as a Python RAW string, and after any heredoc patch that mentions an escape, check the bytes** — `perl -0777 -ne 'print scalar(() = /\x00/g)' <file>` answers in one line, and `git grep -lI --cached` lists what git has already decided is binary. 🔴 **And never put a heredoc inside a `-c` string**: bash takes the `<<` for itself, python drops into its REPL, and the command hangs until it is timed out with the file untouched.

- 🔴 **NEVER PIPE A COMMAND WHOSE EXIT CODE IS THE ANSWER — A PIPELINE'S STATUS IS THE LAST STAGE'S, SO `| tail` TURNS EVERY FAILURE INTO A SUCCESS.** Exactly the `; echo $?` trap in a shape that does not look like it: `node scripts/wait-pr.mjs 4950 --timeout 15 | tail -6` reported **exit 0** on 2026-09-30 while the script had exited **3** for `SETTLED RED`, and a backgrounded task's notification reports the shell's status — so a red PR was announced as a green one. It bit twice that afternoon, in two sessions, the other time on `| tail -3` around a refusal test that had exited 2. Both were caught only because the script's own stdout said what happened; a script that answered in its exit code alone would have been believed. **Redirect to a file and read `$?` from the command itself** (`cmd > out.txt 2>&1; echo $?`), or `${PIPESTATUS[0]}` where the pipe is unavoidable. The same mistake lands inside a `&&`/`||` chain: `git cat-file -e <sha> | head -1 || echo missing` never runs the `||` branch, because `head` succeeded. Instance of the fail-open shape in the Validation cluster — an ABSENT answer arriving in the shape of a NEGATIVE one. [docs/agents-session-traps.md](agents-session-traps.md).
- **`grep -r` of a repo or worktree root (`.`, no path) or its `.claude` gets `--exclude-dir` for node_modules, .git, .next, worktrees and .codex-worktrees ADDED by `bash-guard.mjs` C1 (~3.5 s), and `~/.claude` gets projects, backups and file-history — its three stores, 13.7 GB of its 13.9 GB (2026-10-23); a drive, home or Temp ROOT, the workspace folder, `node_modules`, `.claude/worktrees` and `~/.claude/projects` are still refused, as is a bare `*`/`.*`/`*/src` glob and a path it cannot place; any other named folder, file or small absolute path passes untouched — a FILE glob anywhere included (`instrumentation*.ts`, `eslint.config.*`, `src/**/*.ts`, `src/lib/expense*/*.ts`), since grep never recurses into a file, and a path built from `$TEMP`/`$TMP`/`$TMPDIR`, which are seeded (2026-10-23: those two shapes were 15 of the 21 refusals in the two days after the 22 Oct fix).**

The run then loads the page and exits with `Failed to write file ../examples/x.png: The system cannot find the path specified. (0x3)`, because Chrome resolves the screenshot path against its OWN working directory and not the shell's — so **pass an absolute Windows path to `--screenshot` too**. - 🔴 **A BACKGROUND `cat` WITH NOTHING FEEDING IT WAITS FOR EVER — no file, no heredoc on THAT cat, no `<`, no pipe — and while it waits it holds its worktree and blocks its session's archive; bash-guard C17 refuses it.** 8 Oct 2026: `cat > "$TMPDIR/q.mjs" 2>/dev/null; …; cat > probe.mjs <<'EOF'` put the heredoc on the SECOND cat, and the first hung for over an hour with a production read queued behind it. - 🔴 **A BARE `python`, `python3` OR `py` DOES NOT WAIT QUIETLY — IT FLOODS ITS TASK LOG AT 2.2 GB AN HOUR, AND SO DOES A `python - <<DELIM` WHOSE CLOSING DELIMITER IS MISSING OR INDENTED; bash-guard C19 refuses both.** With no console attached, 3.13/3.14's `_pyrepl` dies inside `Lib/_pyrepl/windows_console.py getheightwidth` with `OSError: [WinError 123]` and reprints that traceback for ever: measured 2026-10-15, **1,774,873 bytes in 3 s** and 3,948,442 in 6 s, identical on both interpreters here. - 🔴 **A GENERATOR'S OUTPUT AND ITS INPUT ARE TWO FILES, AND `--check` READS YOUR WORKING TREE WHILE `remote-check` SENDS YOUR COMMIT — so an uncommitted half of the fix reads HEALTHY here and ORPHAN on the box.** Measured 2026-10-05: `scripts/sync-cloud-context.mjs` added a mirrored memory note **and** filed it in `scripts/module-memory/assignments.json`; a `git add -A .claude/cloud-context .claude/rules` committed the note and the generated rules file but not the assignment, so `node scripts/module-memory/build.mjs --check` said *module memory: healthy* locally and the suite failed on the box with `ORPHAN: ... is filed under no module` plus a *stale* rules file. **After running any generator, `git status --porcelain` and stage by reading that list — never by naming the directories you expected it to touch**; `remote-check` prints the uncommitted files it is ignoring, and that print is the warning. Same family as the Validation cluster's fail-open shape: the local check was answering about a tree nobody was going to ship.
- 🔴 **`flock` DOES NOT EXIST IN MSYS BASH, AND A SINGLE-INSTANCE GUARD BUILT ON IT FAILS SHUT, SILENTLY.** `flock -n 8 || exit` prints `flock: command not found` to stderr and exits **non-zero**, so the `||` branch fires and the script decides *another instance already holds the lock* and exits 0 — the guard refuses the only instance there is, and reports a clean no-op. Measured 2026-10-05. On the Linux side of the same work `flock` is present and behaves normally, which is exactly why the shape looks safe. Use a pid file checked with `kill -0` plus `trap ... EXIT`, and test the guard by running the script once and watching it actually DO the work.
- 🔴 **`TaskStop` KILLS THE WRAPPER AND LEAVES THE SCRIPT RUNNING — so stopping a shipping chain does not stop it, and three can end up racing to push the same branch.** The known half of this is the dev server that keeps the port (§5). The dangerous half is a background `bash <script>` that commits, pushes or merges: measured 2026-10-05, three `run-all-build.sh` were alive at once after two `TaskStop`s, one of them spawning a fresh child 20 minutes after its wrapper was stopped, and two were minutes from pushing the same head. **After stopping a background task that runs a script, confirm with `ps -ef | grep '[s]cript-name'` and kill the survivors by PID** (`taskkill //F //PID n`), and give any chain that can push a single-instance guard. It also strands work on the far side of an ssh — a remote run keeps going with its own stdout gone, so the verdict is unrecoverable and the box stays occupied.
- **MSYS mangles paths silently, four ways:** `git show <ref>:<path>` **FAILS when the path starts with a DOT** (`.github/…`, `.gitignore`, `.env.example`) — a stderr `fatal:` that a pipe turns into `0`; a non-dot path such as `docs/…` or `package.json` is untouched, which is why this looks intermittent, and a `./` in front disarms it with no variable at all (next line); `grep -c $'\r'` matches EVERY line of a pure-LF file; a `git grep`/`rg` PATTERN holding a leading-slash path matches NOTHING — 41 hits read as 0, i.e. *the code is clean*; and **a NATIVE Windows binary cannot resolve `/tmp` at all** (it is `C:/Users/<you>/AppData/Local/Temp`) — bash writes the file and `wc`/`grep` read it, while `rg` says *cannot find the path* and `curl -o` exits 23. Export `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'` first; save with `>` rather than `-o`; never quote a count without it.
- **That `git show <rev>:<path>` mangling is a STDERR `fatal:`, not an empty file — and piped to `grep -c` it prints `0`, which reads as *the fix is NOT in the shipped file*.** MSYS rewrites the argument to `origin\main;.github\workflows\ci.yml` (colon → SEMICOLON), and the pipeline’s exit status is `grep`’s own "no match", so nothing anywhere looks broken. Quoting, `git cat-file -p` and `> file` do NOT help — the redirect writes **0 bytes**. Verifying #4148’s guard this way read **0** against a real **4 of 4**. `export MSYS_NO_PATHCONV=1`, or use the PowerShell tool, and check the line count is PLAUSIBLE before believing a zero. 🔴 **When the answer you want IS a count, ask `git grep -c <pat> <rev> -- <path>` instead — it carries no colon for the conversion to fire on**, so it needs neither the variable nor a `./`, and it is the one form that cannot hand you this zero (measured 2026-10-02, on `.claude/rules/…`, after a `git show … | grep -c` read `0` for a rule line that was really on `main`). Cousin of `tz-africa-cairo-silently-returns-utc-in-msys`. `git-ref-colon-path-is-mangled-by-msys-returns-empty`
- **`git grep -E` is POSIX ERE, where a backslash inside `[...]` is a LITERAL BACKSLASH — so a character class written for `rg` silently matches NOTHING.** Same pattern, same file, measured: `-E` **0**, `-P` **9**, `rg` **9**. The 0 reads as *the code is clean*, and the pattern looks right because it IS right everywhere else. Use `-P`, or keep the class free of `\[`/`\]`.
- **`TZ=Africa/Cairo date` silently returns UTC in MSYS — 3h early, no error**, so recent work reads as old. The tell is a Cairo reading at `+0000`; the clock is ALREADY `+0300`, so use plain `date` or node, never `TZ=`. `tz-africa-cairo-silently-returns-utc-in-msys`
- **A role probe cannot trust the HTTP status code**, and **a POST to ANY `/api/**` path returns 403 even when the route does not exist** — probe with GET.
- **`curl -d "@-"` creates NOTHING on Windows** — write the JSON to a file, pass `-d @file.json`.
- **`pg_dump` piped through stdout on Windows writes CRLF into every `COPY` row — exit 0, plausible size, empty stderr, and the restore puts a stray `\r` in the last column of every row.** Use `pg_dump -f <file>`, which writes clean LF, and verify the archive's row counts against the live tables *before* the drop.

- 🔴 **`TaskStop` ANSWERS `Successfully stopped task` AND THE WORK KEEPS RUNNING — it kills the WRAPPER shell, and the `bash` child running your script survives it.** Measured 2026-09-28: a background **Git**

- 🔴 **COMMIT AND PUSH IN TWO COMMANDS — `bash-guard.mjs` C12 REFUSES ONE COMMAND THAT DOES BOTH, BEFORE ANY OF IT RUNS.** The secret scan runs before the whole command starts, when the new commit does not exist, so `git add … && git commit … && git push` would send the one commit it never read. Commit, then a plain `git push` on its own. Account: `docs/hook-dispatcher.md`, "bash-guard C12".
- **Deleting a branch does not remove its pushed commit**, and **reusing a squash-merged branch makes a conflicting PR.**
- **`git branch -d` gates NOTHING after a squash merge** — it compares the branch to its OWN STALE tracking ref, so genuinely UNMERGED work deletes just as quietly as merged work. Gate on the merged PR (`gh pr list --head <branch> --state merged` — **by NUMBER on a reused branch name**, see the Worktrees cluster) and archive the tip first. `git-branch-d-is-not-a-safety-gate-after-a-squash-merge`
- **`git push` hangs — kill at ~60s and retry.** The OOM was a 500MB `http.postBuffer`, now 8MB; do NOT restore it.
- **A merge to `main` mid-session silently orphans your next push.**
- 🔴 **"THE PRIMARY" AND "`main`" ARE DIFFERENT THINGS — a WORKTREE usually holds `main`.** **NEVER state a branch's ahead/behind from `HEAD`** — every number comes back real with the wrong LABEL on it; name the ref (`git rev-list --count origin/main..main`) and run `git branch --show-current` first.
