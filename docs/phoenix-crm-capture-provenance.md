# Phoenix CRM — capture provenance: when the phone took the position, and which install sent it

The account behind the two rules in `.claude/rules/phoenix-crm-visits.md` ("A one-tap visit now files
WHEN the phone took the reading" and "Every capture names the BROWSER INSTALL that sent it"). Gaps 1
and 3 of the second-pass CRM audit (3–11 October 2026), implemented 12 October 2026.

## Gap 1 — `captured_at` was the only clock on a one-tap visit

`src/components/phoenix-crm/use-silent-fix.ts` has watched the phone's position since the visit form
opens, keeping the sharpest reading it has seen. `position.timestamp` — the instant the **phone**
took that reading — was read on arrival (`fix.at`) and then dropped. What the save stored was
`captured_at`, the instant the **tap** reached the server.

They are not the same instant, and the gap between them is not small by accident: a kept reading is
replaced only by a sharper one, or once it is 15 seconds old (`STALE_MS`), and when no further
reading arrives the kept one stays for as long as the form is open. So a visit saved from a form left
open carries a position older than its own `captured_at`, and module memory is explicit that
`captured_at` must not be read as a position in time. Nothing on the row said how old the reading
was, which is precisely the number the behaviour detectors need in order to be honest about what a
coordinate proves.

`fix_taken_at` is that instant. `fix_age_seconds` is how old the reading already was at the tap.

🔴 **Both ends are measured on the PHONE's own clock** — `fixTakenAt` against `deviceCapturedAt`,
never against the server's receipt. That is the whole reason the number is trustworthy: a handset
whose clock is an hour out still reports the age correctly, because the error is in both terms and
cancels. The phone's disagreement with the server is a different fact and already has a home, on
`phoenix_crm_visits.device_skew_minutes`. Pinned by the first assertion in
`tests/phoenix-crm-capture-provenance.test.ts`, which is first in the file deliberately so that a
"simplification" onto the server's clock is answered by the assertion that explains it.

A **negative** age — a reading stamped after the tap — is filed as `NULL`, not as a clamped `0`.
A clamped `0` would read as "taken at the instant he tapped", which is the single most favourable
reading the field can carry; `NULL` is NOT MEASURED and the migration's CHECK keeps it that way.
Nothing is lost, because `fix_taken_at` is stored raw beside it.

## Gap 3 — no capture named the device

Nothing on a capture identified the device at all, so "two reps saving from one phone" had no answer.
`src/lib/phoenix-crm/device-install.ts` answers it with a random v4 id the browser keeps in its own
storage (`phx-crm-install`), generated by `crypto.randomUUID` or, outside a secure context, by hand
from `getRandomValues` — a rep on plain http over hotel wifi still has one.

What it is, exactly:

- **A browser install, not a person.** A rep signing in on a colleague's phone sends the colleague's
  id. Two saves carrying the *same* id came from one browser profile; two carrying different ids say
  nothing either way. It can only corroborate, never accuse.
- **Not a handset.** No serial, no model, no advertising id. 🔴 **Not a package or APK scan — the
  owner forbids one by name**, and `tests/phoenix-crm-capture-provenance.test.ts` sweeps the client
  file for `getInstalledRelatedApps`, `PackageManager`, `.apk`, `navigator.plugins`, `userAgentData`,
  IMEI and serial-number reads.
- **Not permanent, and that is accepted.** Cleared site data, a private window or a new browser each
  answer with a new id. An id that could not be cleared would be a device fingerprint, which is a
  different thing from the question being asked.

`app_revision` (the running build) and `user_agent` (the request header) are read on the **server**,
so a patched client cannot report them falsely. `fix_taken_at` and the install id come from the body
and a patched build could of course lie about either — which is why neither refuses anything and
neither is ever the only evidence on the row.

## Where it is written, and why not on the visit

`src/lib/phoenix-crm/server/capture-provenance.ts` writes one row into
`phoenix_crm_visit_capture_provenance` immediately after the save, exactly where `judgeCapture`
already runs. `recordCaptureProvenance` returns `Promise<void>` and swallows everything it can
produce: the worst case is one unwritten row about a visit that is already safely on file, never a
rep standing in front of a doctor watching a save fail.

🔴 **`phoenix_crm_save_visit` is deliberately NOT re-emitted.** It is a ~300-line database function
that three migrations already replace in turn and that inserts into `phoenix_crm_visits` at two
sites; re-stating it to carry four fields nothing on the save path reads would put every visit at
risk for evidence not needed until somebody asks a question weeks later. The migration
(`20261012233000_phoenix_crm_visit_capture_provenance.sql`) adds one table, four lock statements and
two indexes, and touches no existing row. `drop table public.phoenix_crm_visit_capture_provenance;`
restores the previous schema exactly.

**No `subject_kind` column, deliberately.** Only a visit is captured this way today, and a CHECK is
the only record a column has of what may be in it — one admitting a place or a venue that nothing
writes would throw that record away for nothing. A place's provenance, if it is ever wanted, is a
migration of its own.

## The silence

Golden Rule #1's blind half holds all of it: the row is written after the save, no rep-facing surface
reads it, nothing here refuses a visit or flags one, and a browser with storage switched off saves
exactly as it always did. The registries in `tests/phoenix-crm-blind-half.test.ts` (`SILENT_COLUMNS`,
`SILENT_TABLES`, `BLIND_READERS`, `SILENT_RUNNERS`) are what keep that true as the module grows.
